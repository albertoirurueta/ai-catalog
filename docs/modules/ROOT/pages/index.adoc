AI Catalog is a collection of https://docs.claude.com/en/docs/claude-code/skills[Claude Code Skills] —
reusable, version-controlled playbooks for common software engineering workflows. Instead of re-explaining
the same process to Claude in every project (how this team bootstraps a Java library, how a pull request
should be reviewed, how release notes get written), each workflow is captured once as a `SKILL.md` file and
invoked on demand with a slash command such as `/iru-plan` or `/iru-pr-review`.

== Why this exists

Prompting an AI assistant to repeat a multi-step process consistently is hard: the steps drift between
sessions, edge cases get forgotten, and every teammate ends up with a slightly different mental model of
"how we do X". A skill fixes that by writing the procedure down once — what to check first, what to skip,
what "done" looks like — so any repository that adopts it gets the same behavior every time it's invoked.

[[core-concepts]]
== Core concepts

=== A skill

Each skill lives in its own directory under `.claude/skills/` and contains a single `SKILL.md` file with:

* A short **description** used by Claude Code to decide when the skill is relevant.
* Step-by-step instructions written for an agent to follow, including what to survey before acting, what
  to leave untouched, and how to report back.

Skills in this catalog range from small, single-purpose checks (`iru-check-license`, `iru-java-test`) to
orchestrators that call other skills in sequence.

=== An agent

Several skills in this catalog spawn a sub-agent through the `Agent` tool, to run a sub-task in an isolated
context (so its detailed output — a full test log, a static-analysis report, an entire nested skill run —
doesn't clutter the main conversation) or to search the codebase without derailing the current flow. This
repository defines three **custom** agents under `.claude/agents/` for its most-duplicated sub-agent shapes:

* **`iru-gate-runner`** — runs a single verification/quality-gate skill (tests, coverage, code-quality/lint, license
  headers, doc-comment audits, security scans, a full build), optionally diffs it against a baseline, and
  reports back only a compact summary.
* **`iru-isolated-skill-executor`** — runs one named skill end to end in a completely fresh context so an earlier
  exploration/planning transcript can't bias it, while the caller keeps running afterward.
* **`iru-change-summarizer`** — fans out over a git commit/tag range and returns only the user-facing changes.

Skills that need ad hoc context isolation beyond those three shapes still use Claude Code's **built-in** agent
types: the **`Explore`** agent (a fast, read-only search agent) is used explicitly by the `iru-explore` skill, and
the **`general-purpose`** agent (Claude Code's default when no specific type is named) covers one-off cases like
bootstrapping the `iru-setup-antora` skill mid-run.

See xref:agents/overview.adoc[] (built-in types) and xref:agents/iru-gate-runner.adoc[],
xref:agents/iru-isolated-skill-executor.adoc[], xref:agents/iru-change-summarizer.adoc[] (custom agents) for detail on
where and why each is used.

=== A CLAUDE.md file

`CLAUDE.md` is a plain markdown file that Claude Code loads automatically, without being invoked, at the
start of every session — unlike a skill or agent, which only act when called on. It holds the persistent
facts Claude would otherwise need re-explaining every session: build/test commands, coding conventions,
architectural notes, and "always/never do X" rules specific to a project or a person.

Claude Code reads it from several locations at once (project root, a personal `~/.claude/CLAUDE.md`, nested
subdirectory files, and an enterprise-managed policy file, if any) and concatenates them rather than picking
one — see xref:guides/claude-md.adoc[] for exact locations, precedence, and how to create or update one
without letting it bloat the context window.

=== A plugin

A **plugin** is not a new kind of artifact alongside skills, agents, and CLAUDE.md — it's a packaging and
distribution mechanism for them. A plugin is a directory (with a `.claude-plugin/plugin.json` manifest) that
can bundle any combination of skills, custom agents, slash commands, hooks, and MCP server configs into one
installable, versioned unit, published to a marketplace (a private, organization-internal one or a public
one) and installed into a repository with `/plugin install` instead of copying files by hand.

This repository does not currently package itself as a plugin — its skills are adopted by copying the
`.claude/skills/<name>/` directories directly — but xref:guides/plugins.adoc[] and
xref:guides/packaging-and-distribution.adoc[] cover when a plugin is worth the extra packaging step instead.

== Purpose groups

[[group-bootstrap]]
=== Repository Bootstrap

Scaffolding a repository's build, docs, CI/CD, and top-level files from nothing — or updating an older or
partial setup — so a new Java library starts out matching the same conventions as every other repository in the catalog.

[TIP]
====
Reach for this group when standing up a **brand-new repository**, or when bringing one with an older or partial
setup in line with the house pattern. `iru-setup-repository` is the catalog-wide front door: it detects a
non-empty repository (via `iru-explore`, reading its `Project type:` line to pre-select), otherwise asks the
project type over up to five `AskUserQuestion` rounds of three options each (JVM services & libraries, Web & Node,
PHP, Python, Mobile & Apple — each with a "Something in the next group" escape hatch, the last ending in "None of these";
.NET is detected but has no orchestrator to offer), asks the shared inputs once — `open-source`, the repository's `visibility` (detected via
`gh` when possible), whether GitHub workflows are wanted at all (`ci`), Sonar, whether CI runs unit tests only or
the full suite (`ci-tests`), GitHub Pages (`pages`), and `publish`-or-`distribution` — quoting the cost
differences for private repositories (Actions minutes, macOS runners, SonarCloud pricing, Pages availability),
and delegates to exactly one matching stack
orchestrator — `iru-setup-java-library-repository`, xref:index.adoc#group-service-bootstrap[`iru-setup-java-springboot`]
(Java or Kotlin), xref:index.adoc#group-quarkus-bootstrap[`iru-setup-quarkus-repository`],
xref:index.adoc#group-typescript-bootstrap[`iru-setup-typescript-repository`],
xref:index.adoc#group-php-bootstrap[`iru-setup-php-repository`],
xref:index.adoc#group-python-bootstrap[`iru-setup-python-repository`],
xref:index.adoc#group-android-bootstrap[`iru-setup-android-repository`], or
xref:index.adoc#group-swift-bootstrap[`iru-setup-swift-repository`] — via `iru-isolated-skill-executor`. Every
run announces whether it is setting the repository up **from scratch** or **updating an existing one** (with an
inventory of what already exists), and each component skill warns about every pre-existing artifact and asks
**Update** (merge, keep customizations), **Keep as is**, or **Replace** (regenerate) — or applies `on-existing` in
scripted runs. `iru-setup-java-library-repository`, the Java library orchestrator below, also runs
standalone and runs the rest of this group in order; each member also works standalone to fill a single gap in a
repository that already has some of this in place (e.g. just `/iru-setup-antora` to add docs to a repository that
already has a `pom.xml`).
====

* xref:skills/iru-setup-repository.adoc[`iru-setup-repository`] — catalog-wide front door: detects/asks a
  repository's project type and delegates to one of eight stack orchestrators.
* xref:skills/iru-setup-java-library-repository.adoc[`iru-setup-java-library-repository`] — orchestrator: bootstraps
  or updates a Java library repository end to end in one pass.
* xref:skills/iru-setup-java-library.adoc[`iru-setup-java-library`] — generates `pom.xml` and the standard Maven
  source layout.
* xref:skills/iru-setup-antora.adoc[`iru-setup-antora`] — scaffolds the Antora documentation site.
* xref:skills/iru-setup-java-gitignore.adoc[`iru-setup-java-gitignore`] — creates or refreshes the root `.gitignore`
  for any JVM project (Java/Kotlin, Maven/Gradle, Quarkus); also reused by the Spring Boot and Quarkus orchestrators.
* xref:skills/iru-setup-java-github-workflows.adoc[`iru-setup-java-github-workflows`] — scaffolds/updates the CI/CD
  GitHub Actions pipeline.
* xref:skills/iru-setup-changelog.adoc[`iru-setup-changelog`] — bootstraps `CHANGELOG.md` from release history,
  or appends missing releases to an existing one.
* xref:skills/iru-setup-readme.adoc[`iru-setup-readme`] — creates or refreshes the root `README.md`.

[[group-service-bootstrap]]
=== Spring Boot Service Bootstrap

Standing up (or updating) a Spring Boot **service** — as opposed to a library — with Domain-Driven Design and
hexagonal (ports and adapters) architecture imposed from the first commit: a Maven multi-module reactor, a
contract-first API layer, reproducible integration tests, infrastructure-as-code, CI/CD, and a documentation
page set derived from the code. The service can be written in Java (Maven) or Kotlin (Maven or Gradle Kotlin DSL),
read from the manifest's `project.language`/`project.buildTool`.

[TIP]
====
Reach for this group when starting a **deployable microservice**, and reach for
xref:index.adoc#group-bootstrap[Repository Bootstrap] instead when starting a **publishable library** — the two
differ in more than scale. A library is signed and published to Maven Central; a service is built into a
container image, deployed to a cloud with OpenTofu, and can be torn down again.

`iru-setup-java-springboot` is the single entry point and the only member that asks the user anything: it
interviews once, writes the answers to a `springboot-stack.yml` manifest, and every other member reads that
manifest back. Each also runs standalone against an existing service to fill one gap — adding a database
adapter, a new API contract, or another deployment environment. When the manifest records `frontend: hilla`,
the orchestrator also runs `iru-setup-java-springboot-hilla` to scaffold a Hilla React frontend into the
reactor's web module.
====

The architecture this group imposes is deliberately not configurable. Dependencies point inward only —
`domain` depends on nothing, `application` sees only `domain`, each `infrastructure` and `api` adapter sees
only `domain` (plus `application` for the inbound side), and `boot` is the composition root that wires
everything. That direction is enforced twice over: by `maven-enforcer-plugin` `bannedDependencies` rules at
module granularity, and by an ArchUnit test at package granularity. Every dependency version is declared in
the root `pom.xml` and nowhere else, and Java 21 is the enforced minimum.

* xref:skills/iru-setup-java-springboot.adoc[`iru-setup-java-springboot`] — orchestrator: interviews the user,
  resolves the stack against the live Spring Initializr API, and runs the six sub-skills below plus the
  documentation skill in order.
* xref:skills/iru-setup-java-springboot-pom.adoc[`iru-setup-java-springboot-pom`] — generates the reactor: the
  root pom holding every version and the full quality plugin set, plus one pom per module.
* xref:skills/iru-setup-java-springboot-modules.adoc[`iru-setup-java-springboot-modules`] — scaffolds the source
  tree: domain ports, one worked adapter per kind, use cases, profiles, migrations, and the ArchUnit test.
* xref:skills/iru-setup-java-springboot-apis.adoc[`iru-setup-java-springboot-apis`] — sets up the `apis/`
  contract tree and the OpenAPI/protobuf/GraphQL/AVRO code generators plus the AsyncAPI documentation generators,
  including all of their HTML documentation.
* xref:skills/iru-setup-java-springboot-hilla.adoc[`iru-setup-java-springboot-hilla`] — scaffolds a Hilla React
  frontend into the reactor's web module (Vitest, ESLint, Sonar wiring), run only when the manifest records
  `frontend: hilla`.
* xref:skills/iru-setup-java-springboot-testcontainers.adoc[`iru-setup-java-springboot-testcontainers`] — writes
  one `compose.yaml` and the Testcontainers harness that launches it, so local runs and CI cannot drift apart.
* xref:skills/iru-setup-java-springboot-platform.adoc[`iru-setup-java-springboot-platform`] — generates the

* xref:skills/iru-setup-java-springboot-github-workflows.adoc[`iru-setup-java-springboot-github-workflows`] —

* xref:skills/iru-update-java-springboot-documentation.adoc[`iru-update-java-springboot-documentation`] — creates

=== Spring Boot Development Tooling

The `java-springboot` and `kotlin-springboot` language/framework backends for the `iru-code` pipeline — the pairs of

convention — xref:skills/iru-plan.adoc[] derives the `java-springboot` key from the `*-code-one-task` directory
name, and xref:skills/iru-code-one-task-group.adoc[] dispatches that key's tasks to the group skill — so no
orchestrator mentions Spring Boot anywhere in its own instructions.

[TIP]
====
This group pairs with xref:index.adoc#group-service-bootstrap[Spring Boot Service Bootstrap]: that group creates
the service, this one implements work in it. Both assume the same module layout, and the split of responsibility
between the two skills here exists for one concrete reason — **integration tests run once per task group, never
once per task**, because a task-level run would start the same Testcontainers stack repeatedly.

You rarely invoke either directly; the xref:index.adoc#group-cycle[Issue-to-PR Development Cycle] reaches them
through `iru-code`.
====

* xref:skills/iru-java-springboot-code-one-task-group.adoc[`iru-java-springboot-code-one-task-group`] — implements a
  bucket of Spring Boot tasks (in parallel where safe) and validates the whole bucket once, reusing the same
  language-level skills as the plain-Java group skill (`iru-java-test`, `iru-java-coverage`,
  `iru-java-code-quality`, `iru-java-javadoc`). It owns the two stages the per-task skill deliberately omits: the
  module-boundary checks (`maven-enforcer-plugin` banned-dependencies plus the ArchUnit test, run early because
  they fail in seconds) and the Testcontainers-backed integration tests (run last, because they cost minutes). Its
  80% coverage gate is measured from **unit tests alone** — integration tests raise the aggregate afterwards and
  that delta is reported, but it never satisfies the gate, so the coverage verdict holds even on a machine with no
  Docker.
* xref:skills/iru-java-springboot-code-one-task.adoc[`iru-java-springboot-code-one-task`] — implements a single
  task's code and **unit tests only**, resolving which hexagonal module the code belongs in before writing
  anything. Like xref:skills/iru-java-code-one-task.adoc[`iru-java-code-one-task`] it ships its own `reference/`
  library, here covering the architecture rather than the language — hexagonal architecture
  and module boundaries, DDD tactical patterns, SOLID, the distributed patterns (CQRS, transactional outbox, saga,
  eventual consistency, listen-to-yourself), and this catalog's Java code style — read by progressive disclosure so
  a small task doesn't pay for all of it.
* xref:skills/iru-kotlin-springboot-code-one-task-group.adoc[`iru-kotlin-springboot-code-one-task-group`] — the
  `kotlin-springboot` counterpart of the group skill above, on Maven or Gradle: gates with
  `iru-kotlin-code-quality`/`iru-kotlin-kdoc` (plus the Java gates for any Java sources), keeps the unit-only 80%
  coverage gate, and runs the Testcontainers integration stage behind the repo-wide `.integration-test.lock`.
* xref:skills/iru-kotlin-springboot-code-one-task.adoc[`iru-kotlin-springboot-code-one-task`] — implements a single
  Kotlin Spring Boot task with unit tests only, first verifying the Kotlin/Spring build plumbing (all-open/no-arg).
* xref:skills/iru-java-springboot-performance-tests.adoc[`iru-java-springboot-performance-tests`] — generates an
  Apache JMeter suite under `performance/` covering only the happy paths of the service's main use cases, in three
  scenarios (low flat concurrency, high flat concurrency, and a symmetric scale-up/scale-down ramp). Unlike the two
  skills above it is never reached through `iru-code`: it is run by a person, after real endpoints exist, and it
  deliberately sits outside the Maven reactor so `mvn verify` never triggers a load test.

whichever platform hosts the repository (GitHub, Bitbucket, Azure DevOps, or TFS).

[NOTE]
====
Used automatically as the last leg of `iru-issue`'s pipeline once `iru-code` finishes, but just as useful standalone
— e.g. after making changes outside the `/iru-issue` flow and wanting a PR description drafted, or a second,
convention-aware review pass before asking a teammate for one.
====

* xref:skills/iru-pr-description.adoc[`iru-pr-description`] — drafts a PR description from the real diff, and
  optionally opens/updates the pull request.
* xref:skills/iru-pr-review.adoc[`iru-pr-review`] — reviews an open pull request against the linked ticket's intent
  and this codebase's conventions.

[[group-maintenance]]
=== Repository Maintenance

Keeping an already-bootstrapped repository correct and current, well after its initial setup.

[NOTE]
====
Intended for whoever **maintains the repository over time** rather than someone mid-feature: cutting
releases, keeping docs from drifting after unrelated code changes, periodically verifying license headers,
and scanning for accidentally committed secrets.
====

* xref:skills/iru-release.adoc[`iru-release`] — cuts a release branch, bumps versions via the ecosystem's
  `iru-<key>-bump-version` skill (Java/Kotlin, TypeScript, Android, Swift, PHP, Python), drafts release notes/changelog, and
  opens the release PR.
* xref:skills/iru-update-docs.adoc[`iru-update-docs`] — brings the Antora documentation module up to date with
  changes already made to the code.
* xref:skills/iru-build-docs.adoc[`iru-build-docs`] — builds the existing Antora documentation site as-is (no content
  edits), scaffolding it first via `iru-setup-antora` if it doesn't exist yet.
* xref:skills/iru-check-license.adoc[`iru-check-license`] — verifies (and backfills) license headers against the
  repository's actual license.
* xref:skills/iru-check-security.adoc[`iru-check-security`] — scans for accidentally committed secrets via
  `detect-secrets`, maintaining a `.secrets.baseline` so repeat runs surface only what's new.

[[group-knowledge]]
=== Knowledge Base Management

Turning meeting transcriptions and their attached documents into a durable, queryable knowledge base at
`knowledge/` — filed meeting summaries, per-person profiles, tracked agreements, and open pending tasks — and
closing the loop as those tasks get done.

[TIP]
====
Reach for this group in a repository used to track meetings and decisions rather than just code.
`iru-knowledge-setup` is a one-time bootstrap; `iru-knowledge-process-inbox` is run every time new
transcriptions/documents land in `knowledge/inbox`; `iru-knowledge-complete` is run whenever a tracked
agreement item actually gets done; `iru-knowledge-briefing` is run any time someone needs to catch up on a
subject; `iru-knowledge-compact` is run as periodic housekeeping when the base has drifted. Most of these are
standalone entry points run at a different point in the knowledge base's lifecycle, and
`iru-knowledge-briefing` is read-only, never editing what the others produce. Two carry dependencies worth
knowing: `iru-knowledge-process-inbox` finishes by invoking `iru-knowledge-compact` once per run, so a batch
of freshly filed meetings is immediately reconciled against what earlier meetings already produced; and
`iru-knowledge-compact` in turn delegates each completed item it finds to `iru-knowledge-complete` rather than
editing those files itself. Because this catalog's skills are adopted individually, `iru-knowledge-compact`
may not be installed alongside `iru-knowledge-process-inbox` — that's handled as a skipped step, not an
error. `iru-knowledge-to-issue` and `iru-knowledge-to-jira` reach furthest outside the group: run whenever a
pending/not-completed agreement needs to become tracked work, each reaches out to
xref:index.adoc#group-cycle[`iru-explore`] plus xref:index.adoc#group-intake[`iru-create-github-issue`] or
xref:index.adoc#group-intake[`iru-create-jira-ticket`] respectively to ground and file the resulting issue/
ticket, then annotates (but doesn't complete) the agreement it came from — pick whichever matches the tracker
the work should land on.
====

* xref:skills/iru-knowledge-setup.adoc[`iru-knowledge-setup`] — creates the `knowledge/` directory and its five
  subdirectories (`inbox`, `meetings`, `people`, `agreements`, `pending`), each seeded with a `.gitkeep`.
* xref:skills/iru-knowledge-process-inbox.adoc[`iru-knowledge-process-inbox`] — files every transcription/document in
  `knowledge/inbox` into a per-meeting summary, updated people profiles, and tracked agreements/pending tasks.
* xref:skills/iru-knowledge-briefing.adoc[`iru-knowledge-briefing`] — read-only: searches
  `knowledge/people`/`meetings`/`agreements`/`pending` for a given subject (optionally scoped by person or
  meeting) and reports back a summary — no file in `knowledge/` is edited.
* xref:skills/iru-knowledge-complete.adoc[`iru-knowledge-complete`] — checks off a completed agreement item and
  removes its pending file, given the task's id.
* xref:skills/iru-knowledge-compact.adoc[`iru-knowledge-compact`] — only ever reduces the base: collapses
  duplicate pending tasks across meetings (keeping the one that already carries a tracker issue), closes out
  agreements whose GitHub issue/Jira ticket reads as completed, and repairs drift between
  `knowledge/pending` and `knowledge/agreements` — always after confirming the full plan.
* xref:skills/iru-knowledge-to-issue.adoc[`iru-knowledge-to-issue`] — resolves a pending/not-completed agreement,
  gathers its meeting and codebase context, then hands it to `iru-create-github-issue` to draft and file a
  GitHub issue for it.
* xref:skills/iru-knowledge-to-jira.adoc[`iru-knowledge-to-jira`] — the Jira counterpart: resolves a
  pending/not-completed agreement, gathers its meeting and codebase context, then hands it to
  `iru-create-jira-ticket` to draft and file a Jira ticket for it.

[[group-agents]]
=== Sub-Agent Infrastructure

The custom agents this catalog's skills delegate to for its most-duplicated sub-agent shapes, cutting across
every group above rather than belonging to any single workflow.

[NOTE]
====
Not something invoked directly the way a skill is — an agent is only ever reached indirectly, through a
skill's own instructions naming it in an `Agent()` call. See xref:guides/creating-skills-and-agents.adoc[] for
how agents differ from skills in how they're triggered.
====

* xref:agents/iru-gate-runner.adoc[`iru-gate-runner`] — runs a single verification/quality-gate skill and reports back
  only a compact summary, optionally diffed against a baseline. Used throughout `iru-code`, `iru-code-one-task-group`,
  and every `<key>-code-one-task-group` skill (Java, Spring Boot in Java or Kotlin, Quarkus, PHP, FastAPI, Django,
  .NET, TypeScript, NestJS, Next.js, Android, Swift), plus the `generate-all-tests` skills for every language and several bootstrap
  skills (verifying a scaffold or generated workflow actually builds).
* xref:agents/iru-isolated-skill-executor.adoc[`iru-isolated-skill-executor`] — runs one named skill end to end in a
  fresh context so the caller can keep running afterward. Used by xref:skills/iru-issue.adoc[`iru-issue`] to delegate the
  entire `iru-code` run for a ticket, by xref:skills/iru-code.adoc[`iru-code`] itself to delegate each task group to
  `iru-code-one-task-group`, by every parallelizable `<key>-code-one-task-group` skill to delegate each task in a
  bucket to its matching `<key>-code-one-task` skill, and by
  xref:skills/iru-setup-repository.adoc[`iru-setup-repository`] and every stack orchestrator
  (xref:skills/iru-setup-java-library-repository.adoc[`iru-setup-java-library-repository`],
  xref:skills/iru-setup-java-springboot.adoc[`iru-setup-java-springboot`],
  xref:skills/iru-setup-quarkus-repository.adoc[`iru-setup-quarkus-repository`],
  xref:skills/iru-setup-typescript-repository.adoc[`iru-setup-typescript-repository`],
  xref:skills/iru-setup-php-repository.adoc[`iru-setup-php-repository`],
  xref:skills/iru-setup-python-repository.adoc[`iru-setup-python-repository`],
  xref:skills/iru-setup-android-repository.adoc[`iru-setup-android-repository`],
  xref:skills/iru-setup-swift-repository.adoc[`iru-setup-swift-repository`]) to delegate each of the bootstrap
  skills it orchestrates.
* xref:agents/iru-change-summarizer.adoc[`iru-change-summarizer`] — fans out over a git commit/tag range and returns
  only the user-facing changes. Used by xref:skills/iru-setup-changelog.adoc[`iru-setup-changelog`] to summarize one
  release at a time when backfilling a long tag history, and by xref:skills/iru-release.adoc[`iru-release`] to summarize
  the single range since the previous release.

== Common workflows

These sections walk through how the catalog's skills compose for a few recurring jobs. Each is a real,
supported path through the graph above — not every skill in the catalog appears in one, since some
(the xref:index.adoc#group-java[Java] and xref:index.adoc#group-dotnet[.NET] Development Tooling skills,
`iru-check-license`) are more often invoked as building blocks of a larger flow than run standalone by a person.

=== Setting up a new repository

`iru-setup-java-library-repository` collects the project's identity and CI/CD parameters once, then
orchestrates six other skills in a fixed order so nothing is asked twice:

[mermaid]
....
flowchart TD
    A["/iru-setup-java-library-repository"] --> B["iru-setup-java-library\n(pom.xml + source layout)"]
    B --> C["iru-setup-antora\n(docs site)"]
    C --> D["iru-setup-java-gitignore\n(.gitignore)"]
    D --> E["iru-setup-java-github-workflows\n(CI/CD)"]
    E --> F["iru-setup-changelog\n(CHANGELOG.md)"]
    F --> G["iru-setup-readme\n(README.md, last — sees everything above)"]
....

Before asking anything else it announces whether it is setting the repository up from scratch or updating an
existing one, with an inventory of every component it found. Each sub-skill then warns about any file it would
write that already exists and asks **Update / Keep as is / Replace**, explaining what each one costs you. The
orchestrator also asks the repository's visibility, whether GitHub workflows are wanted at all (with `ci: no` the
`iru-setup-java-github-workflows` step is skipped entirely), whether CI runs unit tests only or the full suite, and
whether docs deploy to GitHub Pages — recommending the cheaper options for private repositories.

Any of these six can also be run standalone against an existing repository to fill a single gap (e.g. just
`/iru-setup-antora` to add docs to a repository that already has a `pom.xml`).

The same six-step shape is shared by the other `*-repository` orchestrators — only the scaffold, gitignore, and
workflows skills change per stack:

[mermaid]
....
flowchart TD
    FD["/iru-setup-repository\n(front door: detect or ask project type,\nshared inputs asked once)"] --> J["iru-setup-java-library-repository"]
    FD --> SB["iru-setup-java-springboot\n(Java or Kotlin)"]
    FD --> Q["iru-setup-quarkus-repository"]
    FD --> T["iru-setup-typescript-repository"]
    FD --> PH["iru-setup-php-repository"]
    FD --> PY["iru-setup-python-repository"]
    FD --> A["iru-setup-android-repository"]
    FD --> SW["iru-setup-swift-repository"]
    Q --> Q1["iru-setup-quarkus-service → iru-setup-antora →\niru-setup-java-gitignore → iru-setup-quarkus-github-workflows →\niru-setup-changelog → iru-setup-readme"]
    T --> T1["library / react / nextjs / angular / nestjs /\nreact-native / ionic scaffold → iru-setup-antora →\niru-setup-typescript-gitignore → iru-setup-typescript-github-workflows →\niru-setup-changelog → iru-setup-readme"]
    PH --> P1["iru-setup-php-laravel / -wordpress / -prestashop →\niru-setup-antora → iru-setup-php-gitignore →\niru-setup-php-github-workflows → iru-setup-changelog → iru-setup-readme"]

`iru-setup-repository` is the usual way in: it detects a non-empty repository's type via `iru-explore` (or asks
over up to five rounds — JVM services & libraries, Web & Node, PHP, Python, Mobile & Apple), collects the shared,
cost-aware inputs once, and delegates to exactly one orchestrator via `iru-isolated-skill-executor`, forwarding
`mode: existing` when the repository already has content.

=== Setting up a new Spring Boot service

`iru-setup-java-springboot` is the service-shaped counterpart to the flow above. It interviews the user once —
project identity, language (Java on Maven, or Kotlin on Maven or Gradle Kotlin DSL), target cloud, reactive or blocking, and every technology choice — resolving versions and
dependency ids against the live Spring Initializr API, records everything in `springboot-stack.yml`, and then runs
seven sub-skills in a fixed order that each read that manifest back:

[mermaid]
....
flowchart TD
    A["/iru-setup-java-springboot"] --> B["Interview + Initializr API\n(versions, dependency ids, reference pom)"]
    B --> C["springboot-stack.yml\n(the manifest every sub-skill reads)"]
    C --> D["iru-setup-java-springboot-pom\n(reactor: root pom holds every version)"]
    D -- no usable reactor pom --> STOP["Stop — no reactor to attach to"]
    D --> E["iru-setup-java-springboot-modules\n(ports, adapters, profiles, ArchUnit)"]
    E --> F["iru-setup-java-springboot-apis\n(apis/ contracts + code generation)"]
    F --> G["iru-setup-java-springboot-testcontainers\n(compose.yaml + integration-test harness)"]
    G --> H["iru-setup-java-springboot-platform\n(OpenTofu for AWS or Google Cloud)"]
    H -- ci: yes --> I["iru-setup-java-springboot-github-workflows\n(build, deploy, undeploy)"]
    H -- ci: no --> J
    I --> J["iru-update-java-springboot-documentation\n(Antora site, last — derives from finished code)"]
....

The order carries real constraints rather than being a preference: poms before modules (a module needs its parent),
modules before APIs (generated sources need somewhere to land), APIs before the container stack (it must know
whether a schema registry is needed), and everything before the workflows and documentation, both of which survey
what is actually on disk. Only the first step is fatal if it stops — every later sub-skill that stops is recorded
in the final report and the run continues. With `ci: no` the workflows sub-skill is skipped, so there are no
build, deploy, or undeploy workflows — deployment is then a manual `tofu apply`. On a repository that already has
some of this in place, the run announces an update, and each sub-skill asks Update / Keep as is / Replace for
every file it owns that already exists; only a genuinely incompatible repository (e.g. a Gradle build) gets a
hard stop.

Two decision points are worth knowing about before starting. The **concurrency model** (blocking, reactive, or
both) is asked early because it decides which starter every other technology resolves to, and "both" is flagged as
the hardest to reason about. The **deployment platform** (AWS or Google Cloud) determines the whole OpenTofu layout
and the recommended dynamic-configuration mechanism, so it can't be deferred either.

    C2 --> D["Draft (+ estimated difficulty)\n+ confirm + file\n(gh issue create /\nJira MCP tools)"]
    D --> E(["/iru-issue &amp;lt;id-or-key&amp;gt;\n(separate, later invocation)"])
....

Both skills work the same way up to filing; which one to use depends on which tracker the repository/team
uses. Neither is required — `/iru-issue` and `/iru-plan` work fine against a ticket filed by hand, or against no ticket
at all (a free-form description). Only `iru-create-jira-ticket` supports an epic assignment and delegates to
xref:skills/iru-jira-custom-context.adoc[`iru-jira-custom-context`] for organization-specific context — there is
no GitHub equivalent for either.

=== Typical development cycle, starting from a ticket

`iru-issue` is the single entry point for taking a tracked ticket — a GitHub issue or a Jira ticket — to an open,
reviewed pull request. See xref:guides/common-workflows.adoc#typical-development-cycle[] for a more detailed
walkthrough — this is the main workflow for day-to-day work in this catalog.

[mermaid]
....
flowchart LR
    A["/iru-issue &amp;lt;ticket-id&amp;gt;"] --> B["iru-explore\n(understand the ticket)"]
    B --> C["iru-plan\n(write implementation_plan.md,\ngroup tasks by dependency,\ntag each with a language/framework)"]
    C --> D{Hand off to /iru-code?}
    D -- yes --> E["iru-code\n(dispatch each task group to\niru-code-one-task-group, via a sub-agent)"]
    D -- no --> H[Stop for manual review]
    E --> EA["Attach archived plan\nback onto the ticket\n(GitHub comment / Jira attachment)"]
    EA --> F["iru-pr-description\n(open PR as a draft)"]
    F --> G["iru-pr-review\n(review the new PR)"]
....

`iru-code` itself doesn't implement anything directly: for every task group it dispatches to
xref:skills/iru-code-one-task-group.adoc[`iru-code-one-task-group`], which resolves each task's language and delegates
to whichever `iru-<key>-code-one-task-group` skill matches (Java, Spring Boot in Java or Kotlin, Quarkus, PHP, FastAPI,
Django, .NET, TypeScript, NestJS, Next.js, Android, or Swift — e.g.
xref:skills/iru-java-code-one-task-group.adoc[`iru-java-code-one-task-group`]) — each of which captures
one quality baseline for the whole bucket, implements its tasks (in parallel when the group allows it), and
validates the bucket once via its own group's tests/coverage/quality/doc skills, instead of once per task. A
bucket tagged `database` instead goes to xref:skills/iru-database-code-one-task-group.adoc[
`iru-database-code-one-task-group`], which is deliberately simpler — always sequential, with no baseline or
bucket-wide validation of its own. The whole run is bracketed with project-wide quality
(the plan key's own `iru-<key>-code-quality` skill — Java, Kotlin, PHP, Python, .NET, TypeScript, Android, or Swift) and security (`iru-check-security`) baselines — if quality regresses,
follow-up issues can be filed on whichever tracker the plan itself originated from (GitHub via `gh issue create`,
or Jira via xref:skills/iru-create-jira-ticket.adoc[`iru-create-jira-ticket`]) — updating documentation via
`iru-update-docs` once both pass, and archiving the plan under a filename that embeds the originating ticket id
(see xref:skills/iru-code.adoc[]). `iru-issue` then attaches that archived plan back onto the ticket before opening
the PR, so a later `iru-explore` of the same ticket finds it as precedent. `iru-explore` and `iru-plan` can also be run
individually (`/iru-explore`, `/iru-plan`) ahead of, or instead of, the full `/iru-issue` flow, and either a GitHub issue or
a Jira ticket works the same way throughout — for a Jira ticket, `iru-explore` also pulls in its epic, linked
tickets, and any attached prior implementation plans for extra context.

=== Generating a release

`iru-release` must be run from `develop`, is ecosystem-agnostic (Java/Kotlin on Maven or Gradle, TypeScript/npm,
Android/Gradle, Swift/Apple, PHP/Composer, or Python/FastAPI/Django), and delegates the actual version-file edit to that ecosystem's own installed
xref:skills/iru-java-bump-version.adoc[`iru-java-bump-version`]/xref:skills/iru-typescript-bump-version.adoc[`iru-typescript-bump-version`]/
xref:skills/iru-android-bump-version.adoc[`iru-android-bump-version`]/xref:skills/iru-swift-bump-version.adoc[`iru-swift-bump-version`]/
xref:skills/iru-php-bump-version.adoc[`iru-php-bump-version`]/xref:skills/iru-python-bump-version.adoc[`iru-python-bump-version`]
skill (called with `sync-files: yes`, which folds in refreshing `README.md`/`docs/antora.yml`/Antora dependency
snippets), keeping only the release notes and PR description as its own work. See
xref:guides/common-workflows.adoc#generating-a-release[] for a more detailed walkthrough.

[mermaid]
....
flowchart LR
    A["/iru-release"] --> B["Pick release + next\npre-release version"]
    B --> C["Bump version via matching\niru-&amp;lt;key&amp;gt;-bump-version skill\n(sync-files: yes refreshes README.md,\ndocs/antora.yml, Antora version snippets)"]
    C --> E["Write whats-new.adoc + CHANGELOG.md"]
    E --> F["Commit, push release_x.y.z"]
    F --> G["iru-pr-description\n(fill in the release PR)"]
....

=== Updating an existing repository with new functionality

There is no single orchestrator for this — it's a set of independent skills, each scoped to one artifact,
run after code has already changed:

[mermaid]
....
flowchart TD
    Code["Code change already made\n(uncommitted or on a branch)"] --> UD["iru-update-docs\n(Antora pages)"]
    Code --> RM["iru-setup-readme\n(README.md, if it already exists: proposes a diff)"]
    Code --> CLI["iru-check-license\n(license headers on touched files)"]
    Code --> CSEC["iru-check-security\n(scan for secrets before committing)"]
    UD -.->|only if no Antora module exists yet| AS["iru-setup-antora"]
....

`iru-setup-changelog` is deliberately **not** part of this flow: it only bootstraps a changelog that doesn't
exist yet and stops immediately if `CHANGELOG.md` is already present (see xref:skills/iru-setup-changelog.adoc[]).
Keeping an existing changelog current on each release is `iru-release`'s job, not a standalone update skill's.

=== Managing a knowledge base of meetings

A separate, standalone lifecycle from the code-focused workflows above: turning meeting transcriptions into a
durable record and closing the loop as tracked agreements get done. `iru-knowledge-setup` runs once;
`iru-knowledge-process-inbox`, `iru-knowledge-briefing`, `iru-knowledge-complete`, and `iru-knowledge-compact`
each run repeatedly, on their own schedule. The one internal hand-off is at the end of a filing run:
`iru-knowledge-process-inbox` invokes `iru-knowledge-compact` once it has filed every meeting in the inbox, so
an item a new meeting re-raised gets collapsed into the task an earlier meeting already produced instead of
accumulating as a near-duplicate — and `iru-knowledge-compact` hands each already-finished item to
`iru-knowledge-complete`. `iru-knowledge-compact` also runs standalone as periodic housekeeping, and confirms
its full plan before deleting or editing anything. `iru-knowledge-to-issue` and
`iru-knowledge-to-jira` also run repeatedly, but reach into the
xref:index.adoc#group-cycle[Issue-to-PR Development Cycle] and xref:index.adoc#group-intake[Ticket Intake] groups
(via `iru-explore` plus `iru-create-github-issue`/`iru-create-jira-ticket` respectively) to turn a pending
agreement into tracked work on whichever tracker fits, without itself completing that agreement:

[mermaid]
....
flowchart TD
    A["/iru-knowledge-setup\n(once, before first use)"] --> B["knowledge/inbox, meetings,\npeople, agreements, pending"]
    B --> C["New transcriptions/documents\nland in knowledge/inbox"]
    C --> D["/iru-knowledge-process-inbox\n(run repeatedly)"]
    D --> E["knowledge/meetings/meeting-&amp;lt;timestamp&amp;gt;/\n+ knowledge/people/*.md\n+ knowledge/agreements/*.md\n+ knowledge/pending/*.md"]
    E --> Cp["/iru-knowledge-compact\n(final step of every process-inbox run,\nalso standalone housekeeping)"]
    Cp --> Cq{"User confirms\nthe proposed plan?"}
    Cq -- no --> E
    Cq -- yes --> Cr["Duplicate pending tasks merged into\nthe tracked/earliest survivor,\nfinished agreement items checked off,\ndrift between the two dirs repaired"]
    Cr --> E
    E -.-> Br["/iru-knowledge-briefing &amp;lt;subject&amp;gt;\n(run any time, read-only,\nno effect on E)"]
    E --> F{"Pending task\nactually completed?"}
    F -- yes --> G["/iru-knowledge-complete &amp;lt;task-id&amp;gt;\n(run repeatedly)"]
    Cr -.->|per completed item| G
    G --> H["Agreement item checked off,\npending file removed"]
    F -- not yet --> I{"Needs to become\ntracked work?"}
    I -- GitHub --> J["/iru-knowledge-to-issue\n(iru-explore + iru-create-github-issue)"]
    I -- Jira --> J2["/iru-knowledge-to-jira\n(iru-explore + iru-create-jira-ticket)"]
    J --> K["Issue URL appended to the\npending file + agreement item\n(agreement stays unchecked)"]
    J2 --> K2["Ticket key/URL appended to the\npending file + agreement item\n(agreement stays unchecked)"]
    K --> E
    K2 --> E
    I -- no --> E
....

== Keeping this documentation current

[IMPORTANT]
====
This documentation site can be created or updated in two ways:

* **Preferred — run the `iru-generate-skill-docs` skill** (`/iru-generate-skill-docs`).
It (re)generates this page — the reference table, purpose groups, dependency graph, and common
workflows above — plus one detail page per skill/agent under `skills/` and `agents/`, directly from
whatever `.claude/skills/*/SKILL.md` files and agent definitions actually exist in the repository.
It's idempotent, so it's safe to re-run any time a skill or agent is added, removed, or changed; see
xref:index.adoc#_keeping_this_documentation_current[Keeping this documentation current] above.
* **Manual edits.** This page and the detail pages are plain AsciiDoc files under
`docs/modules/ROOT/pages/`, and can be edited directly like any other Antora content. This is fine for
wording or structural fixes, but anything describing what a skill or agent actually does should instead
go through the skill above — hand-written content there will be overwritten the next time it runs.
====

This page and every detail page under xref:index.adoc#group-tooling[Catalog Tooling] are themselves
generated — by `iru-generate-skill-docs`, from whatever skills/agents actually exist under
`.claude/skills/` (and `.claude/agents/`, if any) at the time it runs:

[mermaid]
....
flowchart LR
    A["/iru-generate-skill-docs"] --> B["Discover every SKILL.md\n+ agent usage on disk"]
    B --> C["Build the dependency graph\n+ purpose groups + workflows"]
    C --> D["Write index.adoc, skills/*.adoc,\nagents/*.adoc, nav.adoc"]
    D --> E["npx antora — verify the\nsite still builds"]
....

Re-run it (`/iru-generate-skill-docs`) after adding, removing, or materially changing a skill or
agent, so this page and the detail pages it links to don't drift from what's actually on disk.

Each skill's own detail page (linked from the table above) covers its exact inputs, outputs, and execution
flow. Each skill is also self-contained under its own `.claude/skills/<name>/SKILL.md` — copy the ones you
need into another repository's `.claude/skills/` directory to adopt them there.
