= Setup Readme
:description: Creates or refreshes a repository's root README.md with badges, a multi-stack status table, API doc links, and install/run instructions.
:keywords: iru-setup-readme, claude code skill, readme, badges, ci, sonarqube, npm, maven central, swift package index, android, swift, typescript, documentation, installation instructions

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Create or refresh a repository's root `README.md` by exploring what actually exists — build files, CI
workflows, quality-tool config, documentation, license, and source code — and composing only the sections that
real material supports.

== Purpose

`iru-setup-readme` never invents version numbers, badge URLs, dashboard links, or example code that don't
correspond to something actually present in the repository. It gathers project identity (repository/host,
description, license, build tool, current and latest-released versions), detecting the stack across the full
range this catalog supports — Java/Maven, Gradle/Kotlin, Vite+React, Angular CLI, Java/Spring Boot + Hilla,
Expo/React Native, Ionic/Capacitor, Android library/application, Swift/Apple (SwiftPM, Xcode, XcodeGen, Tuist),
and plain TypeScript/npm — reusing an `iru-explore` report's `Project type:` line from earlier in the
conversation instead of re-detecting from scratch when one is already available. It gathers badge sources (CI
status, SonarCloud/SonarQube, and package-registry badges for npm, Maven Central, and the Swift Package Index),
a project status table that grows extra rows (platforms, Android min/target SDK, Kotlin/AGP, Swift tools/
deployment targets, Node engine, TypeScript, framework) only for the stacks they apply to, documentation links
(Antora site, Maven site report, Sonar dashboard, generated API docs — TypeDoc, Compodoc, Storybook, Dokka,
DocC — confirmed wired into a GitHub Pages publish step, `CHANGELOG.md`), installation instructions matched to
the actual build tool (Maven, Gradle Kotlin DSL with an optional version-catalog form, npm plus pnpm/yarn when
the lockfile shows it, SwiftPM, Python, or — for distributed apps — store links or a "run it locally" command),
and a "how it works" section with a runnable example grounded in the current public API — reusing an existing
Antora overview/example rather than writing a divergent one if the docs site already covers it. A section whose
source material doesn't exist yet (e.g. a brand-new, mostly empty repository) is omitted rather than filled
with placeholders. If `README.md` already exists, the skill warns the user, preserves any hand-written section
it doesn't know how to regenerate (e.g. "Contributing"), and shows the proposed new content as a diff before
writing anything, requiring explicit approval.

== Inputs

|Argument |Required |Description |Default

|No
|An `args` line — the only key this skill accepts. `none` suppresses every SonarCloud/SonarQube badge and the

== Outputs

* `README.md` at the repository root — newly created, or updated after explicit user approval.
* If `README.md` didn't previously exist: it is written directly, no approval step needed.
* If `README.md` already existed: the full proposed content (or diff) is shown first, and the file is only
  overwritten if the user explicitly accepts; any partial-apply request is handled by revising the draft in
  free text before writing.
* A closing report naming which sections were included versus omitted and why (e.g. no Installation section
  because no build/package config was found), any fact that had to be inferred rather than confirmed, and a
  reminder to double-check the "How It Works"/example section specifically since it depends on this skill's
  reading of the current API.
