= Plan
:description: Produces a dependency-aware, checkbox-driven implementation plan for a GitHub issue, Jira ticket, or free-form task, grounded in the codebase's real state.
:keywords: iru-plan, claude code skill, implementation plan, github issue, jira ticket, task groups, checkbox plan

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Produce a concrete, step-by-step implementation plan for a task — grounded in the real state of the
codebase — and write it to `implementation_plan.md` at the repository root. This skill does not modify
source code; its only output artifact is the plan file itself.

== Purpose

`iru-plan` turns a tracked ticket (a GitHub issue or a Jira ticket, auto-detected like `iru-explore`) or a
free-form task description into a reviewable, checkbox-driven list of implementation steps before any code
changes begin. If `implementation_plan.md` already exists at the repository root, it determines whether that
plan matches the requested task and asks the user whether to resume it as-is, discard and regenerate it, or
update it while preserving already-completed work. It grounds itself in the actual codebase (via `iru-explore`),
resolves only genuinely ambiguous decisions with the user, groups tasks into dependency-aware task groups (each
marked whether its tasks can be implemented in parallel), and determines which `<key>-code-one-task` skill (e.g.
`iru-java-code-one-task`, `iru-dotnet-code-one-task`, `iru-typescript-code-one-task`, `iru-android-code-one-task`,
`iru-swift-code-one-task`, `iru-java-springboot-code-one-task`, `iru-kotlin-springboot-code-one-task`,
`iru-quarkus-code-one-task`, `iru-php-code-one-task`, `iru-nestjs-code-one-task`, `iru-nextjs-code-one-task`, `iru-fastapi-code-one-task`, `iru-django-code-one-task`, `iru-kmp-code-one-task`, `iru-react-native-code-one-task`, `iru-windows-code-one-task`, `iru-rust-code-one-task`, `iru-go-code-one-task`) each
task belongs to — tagged on every top-level task — so the `iru-code` skill that later executes it, via
`iru-code-one-task-group`, knows exactly which language-specific group skill to dispatch each task group to
without re-inferring it. When a tracked ticket is involved, the plan's Task summary records an explicit `Source:`
line (e.g. `Source: GitHub issue #42` or `Source: Jira PROJ-123`) so `iru-code`'s own archiving step can name the
archived plan after the exact ticket it resolved, rather than falling back to a timestamp. When the base branch
the work forks from is known — typically because `xref:skills/iru-issue.adoc[]` already resolved and confirmed it
with the user before invoking this skill — the Task summary records that too, as a `Base branch:` line, so that a
later `/iru-pr-description` run in a separate session can recover the choice and target the pull request at the
same base rather than the repository default. For user-interface work (screens, pages, windows, components or controls on any stack) it decomposes the design
top-down into screens, regions and components, plans one task per component or screen with its own UI tests, groups
them bottom-up (leaves, composites, screens, flows) and ends with a documentation task for `/iru-update-docs`; see
xref:guides/building-user-interfaces.adoc[Building user interfaces]. Everything is written to
`implementation_plan.md` — the artifact `iru-code` later executes group by group.

== Outputs

* `implementation_plan.md` at the repository root — overwritten if the user chose to discard an existing plan,
  merged into (preserving completed tasks) if the user chose to update one, or left completely untouched if the
  user chose to skip planning and resume execution of the existing file as-is.
* The plan is structured as: a task summary (including a `Source:` line naming the originating GitHub issue or
  Jira ticket, if any, and a plan-wide **Language/framework** line if every task shares one key), a summary of the
  current relevant code state (concrete file paths and class/method names), and implementation steps organized
  into task groups — each group naming its `Parallelizable` verdict and containing its tasks/sub-tasks, every one
  carrying its own empty markdown checkbox (`[ ]`) for `iru-code` to check off later, numbered continuously across
  the whole plan (`Task N` / `Task N.M`) and tagged with its own language/framework key.
* The distinct set of `<key>-code-one-task` keys involved. `iru-explore`'s `Project type:` is mapped to the most
  specific installed key: `java-springboot` and `kotlin-springboot` (Hilla frontends stay `typescript`), `quarkus`
  for both Java and Kotlin Quarkus, `php` for every PHP flavor (Laravel, WordPress, PrestaShop, library), and
  `nestjs`/`nextjs` — never plain `typescript` for NestJS or Next.js code — `react-native` for every `react-native-app` (Expo or Metro; never `typescript`/`android`/`swift`), `kmp` for every `kmp-app` (including the Swift code in its `iosApp/` host; never `android`), `windows` for every `windows-app (wpf|winui|winforms)` (the UI-free `src/<App>.Core` code, the app project's XAML/forms, MSIX manifests and their tests — never `dotnet`; the plan's "Current code state" states the UI stack and MVVM/MVC architecture), `swift` for a `macos-app (swiftui|appkit)` (the Swift coding skill detects the UI framework and architecture itself, also stated in "Current code state"), `rust`/`go` for Rust and Go projects and for `cli-tool (rust)`/`cli-tool (go)` (every task in the crate or module, including the command tree, terminal UI and doc generators), `swift`/`dotnet` for `cli-tool (swift)`/`cli-tool (dotnet)` (their coding skills detect the command-line shape themselves; the plan's "Current code state" names the argument parser, any terminal-UI library and which commands are read-only vs. destructive, and CLI tasks are phrased as observable contracts: stdout/stderr, `--json` schema, exit codes), and `fastapi`/`django` for `python-fastapi`/`python-django` (a `python-library` has no coding key in this catalog and is recorded as plain `python`). Keys are resolved against which such skills are actually
  installed in this repository (`find .claude/skills -maxdepth 1 -type d -name "*-code-one-task"`) — a task
  whose language/framework has no matching skill installed is still recorded accurately, just without a
  dispatchable tag.
* For UI work: a `Screen › Region › Component (in: …; out: …)` tree in "Current code state" with each node marked
  new/changed/reused; one task per component or screen (inputs, events, visual states, plus its tests across
  left-to-right/right-to-left × light/dark, `.ui-screenshots/` captures and the accessibility check at the
  `.ui-quality.yml` level, per the coding skill's `reference/ui-contract.md`); collections planned as a virtualizing
  collection component plus one item component; groups ordered leaves first; and a final untagged documentation task
  that runs `/iru-update-docs`.
* Any decisions made on the user's behalf (per the ambiguity-resolution step) are stated in the plan itself,
  with a one-line rationale, rather than asked upfront.
* No source code, configuration, or documentation outside `implementation_plan.md` is ever modified.
* A short summary in the conversation once the plan is written — including how many task groups were formed
  and which, if any, are non-parallelizable and why — asking the user to review it before implementation starts.

=== Related agents

`iru-plan` itself does not spawn any Agent — it calls the `iru-explore` skill directly and otherwise only reads the
codebase and writes the plan file. However, the `implementation_plan.md` it writes explicitly instructs
whoever executes that plan (normally the `iru-code` skill, via `iru-code-one-task-group` and the language-specific
`<key>-code-one-task-group` skill it dispatches to) to delegate each task's test run to the
xref:agents/iru-gate-runner.adoc[`iru-gate-runner`] agent, if installed, rather than running tests inline, so test
output doesn't consume the executing agent's main context window. This is an instruction `iru-plan` embeds in its
output file for a later execution step to follow — not an `Agent()` call `iru-plan` makes itself.
