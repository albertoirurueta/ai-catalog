= Setup Swift Library
:description: Scaffolds a SwiftPM library's Package.swift, Sources/Tests layout, SwiftLint, formatter config, DocC page, and Sonar config from a house template.
:keywords: iru-setup-swift-library, claude code skill, swift, swiftpm, swiftlint, swift-format, docc, sonarcloud, package.swift, scaffold

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Generate the standard Swift Package Manager library toolchain at the repository root — `Package.swift`, the
`Sources/<Name>/` and `Tests/<Name>Tests/` layout, `.swiftlint.yml`, a formatter config, a DocC catalog page, and,
when opted in, `.spi.yml` and `sonar-project.properties`.

== Purpose

`iru-setup-swift-library` bootstraps a new Swift/SwiftPM library from an explicit, genericized house template
embedded in the skill itself. It announces up front whether it is creating the package from scratch or updating an
existing one, and for every file of its own that already exists it warns and asks Update / Keep as is / Replace /
Stop (or applies `on-existing` from `args`). Every file starts from `swift package init --type library`'s own scaffold, then this
skill rewrites it: `Package.swift` gets `// swift-tools-version: 6.0`, a `platforms:` array derived from the
selected Apple platforms, a `swift-docc-plugin` dependency, and `swiftLanguageModes: [.v6]`; `Sources/<Name>/`
gets a placeholder `Sendable` type; `Tests/<Name>Tests/` gets both a Swift Testing `@Test` example and an XCTest
example; and `.swiftlint.yml`, a `.swift-format`/`.swiftformat` config, and a DocC catalog page round out the
toolchain. It is the Swift/Apple equivalent of xref:skills/iru-setup-java-library.adoc[],
xref:skills/iru-setup-typescript-library.adoc[], and xref:skills/iru-setup-android-library.adoc[] for this
catalog's other ecosystems.

== Outputs

* `Package.swift`, rewritten in full after `swift package init --type library --name <Name>`.
* `Sources/<Name>/<Name>.swift` (a placeholder `Sendable` struct), `Tests/<Name>Tests/<Name>Tests.swift` (Swift
  Testing `@Test`), and `Tests/<Name>Tests/<Name>XCTests.swift` (XCTest), sharing one test target.
* `.swiftlint.yml` (opt-in strict rules, `excluded: .build`) and either `.swift-format` or `.swiftformat`,
  depending on `formatter`.
* `Sources/<Name>/<Name>.docc/<Name>.md`, a DocC catalog page.
* `.spi.yml`, only when `publish: yes`.
* `sonar-project.properties`, only when `sonar` is not `none`.
* A report of the resolved `package-name`/`<Name>`, platforms and deployment targets, license, and every
  yes/no/gated choice; the mode announced up front (from scratch or update); per file whether it was created,
  updated, replaced or kept as is (with each mismatch listed for a kept file, and how `visibility`/`ci` shaped the
  Sonar recommendation); whether
  `swift build`/`swift test` succeeded; and explicit warnings (review before build/commit, `SONAR_TOKEN` and a CI
  step still needed for `sonar-project.properties` to mean anything, `.spi.yml` alone doesn't submit to the Swift
  Package Index, no `.gitignore` touched, SwiftLint/`swiftformat`/`.spi.yml` submission unverified locally).
