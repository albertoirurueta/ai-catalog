= Setup KMP App
:description: Scaffolds a Kotlin Multiplatform Android and iOS app with a shared module, Android app, XcodeGen iOS host, quality gates, Kover coverage and Dokka docs.
:keywords: iru-setup-kmp-app, claude code skill, kotlin multiplatform, kmp, compose multiplatform, xcodegen, kover, detekt, gradle

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

`iru-setup-kmp-app` generates a complete, buildable Kotlin Multiplatform app for Android and iOS at the repository
root: a Gradle Kotlin DSL build, a `shared/` KMP module, an `androidApp/` application module and an `iosApp/`
SwiftUI host app whose Xcode project is generated by XcodeGen. Its templates live in four reference files
(`gradle-templates.md`, `shared-templates.md`, `android-templates.md`, `ios-templates.md`) and were verified against
the real toolchain.

== Purpose

The skill produces the *scaffold contract* that the KMP coding and gate skills (`iru-kmp-code-one-task`,
`iru-kmp-test`, `iru-kmp-coverage`, `iru-kmp-code-quality`, `iru-kmp-dokka`, `iru-kmp-bump-version`) and
`iru-setup-kmp-github-workflows` detect and call. It wires the version properties (`VERSION_NAME`/`VERSION_CODE` in
`gradle.properties`), a version catalog, a `shared/` module on the AGP `com.android.kotlin.multiplatform.library`
plugin with `iosArm64` and `iosSimulatorArm64` targets producing a static `Shared` framework, an `androidApp/`
module with env-driven release signing, and an `iosApp/` project driven by `iosApp/project.yml`. The `ui` input
chooses between Compose Multiplatform (one `App()` in `shared/commonMain`) and native UI (shared logic only, with
Jetpack Compose on Android and SwiftUI on iOS).

It also configures detekt, ktlint, Android Lint, Kover (aggregated at the root with an 80% `koverVerify` bound),
Dokka 2, SwiftLint and an optional `sonar {}` block, with sample code and tests in every source set so coverage
starts at 100%. It announces whether it is scaffolding from scratch or updating an existing project, asks
Update / Keep as is / Replace / Stop for each existing file group (unless `on-existing` decides), never overwrites
hand-written source, and treats the JetBrains wizard's single `composeApp/` layout as foreign. Every toolchain
version is looked up at run time, with a verified fallback table. Like `iru-setup-android-app`, it writes no
publishing block.

== Outputs

* Gradle build files: wrapper (`gradlew`, `gradlew.bat`, `gradle/wrapper/*` with `distributionSha256Sum`),
  `settings.gradle.kts`, root `build.gradle.kts` (Kover aggregation, optional `sonar {}`), `gradle.properties`,
  `gradle/libs.versions.toml`, `detekt.yml`, `.editorconfig`.
* `shared/` module: `build.gradle.kts` and sample sources and tests in `commonMain`, `commonTest`, `androidMain`,
  `androidHostTest`, `iosMain` and `iosTest` (plus `App.kt` and `MainViewController.kt` for `ui: compose`).
* `androidApp/` module: build file, ProGuard rules, manifest, resources, `MainActivity.kt` and a Robolectric test.
* `iosApp/`: `project.yml`, `Configuration/Config.xcconfig`, `.swiftlint.yml`, Swift sources, `Info.plist` and
  `iosAppTests` (plus `GreetingModel.swift` for `ui: native`). The generated `.xcodeproj` and `local.properties`
  are never written.
* A verification run (Step 7) of the build, the gate tasks and, on macOS, the iOS framework, XcodeGen and
  `xcodebuild test` steps; anything not runnable is reported as unverified.
* A closing report with the resolved inputs, the setup mode, the per-group action (created / updated / replaced /
  kept as is), what was included or omitted and why, live versus fallback toolchain versions, and ignored keys.
