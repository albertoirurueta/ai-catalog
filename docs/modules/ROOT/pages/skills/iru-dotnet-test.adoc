= .NET Test
:description: Runs a .NET project or solution tests via dotnet test by selector, Windows-desktop aware, with a lock-serialized ui selector for FlaUI UI tests.
:keywords: iru-dotnet-test, claude code skill, dotnet, csharp, unit testing, xunit, nunit, mstest, run unit tests, windows desktop, flaui ui tests

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Run a .NET project or solution's test suite through the .NET CLI (`dotnet test`), scoped to whatever the caller
asked for — everything, a single class, a single method, a wildcard/namespace pattern, or a trait/category
expression. This is the .NET/C# equivalent of `iru-java-test`. It is a read-only reporting skill: it runs tests and
summarizes the outcome, it does not fix failures unless asked to as an explicit follow-up.

== Purpose

`iru-dotnet-test` turns a loosely-specified request ("run the FooTests", "just the fast ones", "everything") into the
correct `dotnet test --filter` invocation and a concise pass/fail summary. It exists so that running and
narrowing down tests doesn't require hand-composing filter-expression syntax each time, and so that a calling
skill (or a human) gets back a short report instead of a full raw test-run log.

It is Windows-desktop aware. A new Step 0 parses the arguments, detects the host (Windows or not), classifies every
`*.csproj` (portable, `net*-windows*`, WinUI, UI-test projects) and detects the test runner (VSTest or
Microsoft.Testing.Platform, where `dotnet test` takes `--project`/`--solution`). On a Windows-desktop repository it
adds `TestCategory!=UI` to every ordinary run so FlaUI UI tests never run by default, and appends
`-p:EnableWindowsTargeting=true` on a non-Windows host. Off Windows it never runs the whole solution — a
`net*-windows*` test project aborts the run even though the portable projects passed ("Microsoft.WindowsDesktop.App
not found", exit 1 under VSTest, exit 150 under MTP) — but runs each portable test project separately and lists every
Windows test project (or one referencing a WinUI project) as **unverified (needs Windows)**. Multiple solution files or
test projects with no solution make it ask which to target. A "Known quirks" section records what was verified on
macOS with the .NET 10 SDK.

The new `ui` selector (also accepted with a `lock: held` line when the caller already owns the lock) runs
`--filter "TestCategory=UI"` on the UI-test project only on a Windows host with an interactive desktop session:
it takes the repository-wide `.integration-test.lock` (atomic `mkdir`, owner file, stale after 60 minutes, released on
every exit path), builds the app the tests launch, runs them, and otherwise reports **unverified**. Skipped or not-run UI
tests are never reported as passed.

== Inputs

[cols="1,1,3,2", options="header"]
|===
|Argument |Required |Description |Default

|`selector`
|No
|Names what to run: a test class, a class+method, several classes, a wildcard/namespace pattern, a trait/category
expression, or a specific project/solution path. Mapped to the correct `--filter` expression per the table below.
|None — omitting it runs the full suite (`dotnet test`; on a Windows-desktop repository UI-category tests are excluded and, off Windows, portable projects run one by one).

|`ui` (selector)
|No
|Windows-desktop only: run the FlaUI desktop UI tests (`TestCategory=UI`) behind the shared `.integration-test.lock`. Not run on a non-Windows host or without an interactive desktop session — reported unverified.
|Not applicable.

|`lock: held`
|No
|A `key: value` line, only meaningful with `ui`: the caller already holds `.integration-test.lock`, so this skill neither takes nor releases it.
|Lock is taken and released by this skill.
|===

The selector maps to `dotnet test` parameters as follows:

[cols="3,3,3", options="header"]
|===
|What the caller wants |Parameter |Example

|Everything
|_(none)_
|`dotnet test`

|A specific project or solution
|positional path
|`dotnet test MySolution.sln`

|One test class
|`--filter` with `FullyQualifiedName~`
|`dotnet test --filter "FullyQualifiedName~FooTests"`

|One method in a class
|`--filter` with `FullyQualifiedName~Class.Method`
|`dotnet test --filter "FullyQualifiedName~FooTests.TestSomething"`

|Several classes/methods
|`--filter` with `\|` between clauses
|`dotnet test --filter "FullyQualifiedName~FooTests\|FullyQualifiedName~BarTests"`

|Classes matching a name pattern
|`--filter` with `~` (contains match)
|`dotnet test --filter "FullyQualifiedName~ServiceTests"`

|All classes in a namespace
|`--filter` with the namespace as a `~` prefix
|`dotnet test --filter "FullyQualifiedName~MyProject.Services"`

|Excluding some classes/methods
|`--filter` with `!~`
|`dotnet test --filter "FullyQualifiedName!~SlowTests"`

|Tests tagged with a category/trait
|`--filter` with the trait's property name
|`dotnet test --filter "Category=fast"`

|Excluding a category/trait
|`--filter` with `!=`
|`dotnet test --filter "Category!=slow"`

|Trait/category boolean expression
|`--filter` with `&`, `\|`, `!`, parentheses
|`dotnet test --filter "Category=fast&Priority=1"`

|Windows desktop: ordinary run
|the selector's filter AND `TestCategory!=UI`
|`dotnet test tests/App.Core.Tests --filter "(FullyQualifiedName~FooTests\|FullyQualifiedName~BarTests)&TestCategory!=UI"`

|Windows desktop: UI tests (`ui`)
|`--filter "TestCategory=UI"` on the UI-test project (Windows only, lock)
|`dotnet test tests/App.UITests --filter "TestCategory=UI"`
|===

Which trait/category property name applies depends on the test framework in use (MSTest: `TestCategory`/
`Priority`; NUnit: `Category`; xUnit: whatever key was passed to `[Trait("Key","Value")]`) — checked against the
test project's `<PackageReference>` entries if unsure. A selector matching nothing reports "No test matches the
given testcase filter" and exits successfully having run zero tests, rather than failing the build the way Maven
Surefire does — called out explicitly in the report rather than treated as a pass.

== Outputs

* A plain-text summary in the conversation — never a written file.
* Total tests run, passed, failed, and skipped, per test project.
* If everything passed: a brief confirmation, without pasting the full log.
* If there are failures: the failing test names and the relevant assertion/exception output (falling back to the
  `.trx` log under `TestResults/` if console output was truncated) — without unrelated passing-test noise.
* For a Windows-desktop repository: which test projects ran, which were **unverified (needs Windows)** and why, whether the default UI exclusion applied, and — for `ui` — how the lock behaved.
* No source or test code is ever modified.
