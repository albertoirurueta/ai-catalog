Carry out one task from a NestJS `implementation_plan.md` — the implementation, its tests, and the checkbox update — against a Nest application, and nothing else. It is the narrowest execution unit for Nest projects in the `iru-code` pipeline and runs on a medium model, since the plan already carries the hard reasoning and the guidance lives in `reference/`.

== Purpose

`iru-nestjs-code-one-task` differs from its plain TypeScript counterpart in two ways. Nest punishes some mistakes silently — a DTO imported with `import type`, a wrong `.js` import suffix for the module format, a global pipe registered only in `main.ts`, per-request state on a singleton — so the reference files exist mostly to prevent those. And because Nest unit specs build a small testing module in well under a second, it runs the unit specs it touched, leaving e2e specs, coverage and the full suite to the group.

It detects, from files, the Nest app root and major version, ESM versus CommonJS, Vitest versus Jest, Express versus Fastify, the ORM (TypeORM, Prisma, Mongoose, Drizzle, MikroORM), class-validator versus Standard Schema validation and where global enhancers are registered, standard versus monorepo mode, layered versus hexagonal architecture, and the package manager. It then reads `reference/README.md` and only the reference files the task needs (`code-style.md` and `testing.md` always; modules and DI, validation and DTOs, enhancers, configuration, persistence, security, CLI generators or hexagonal on demand).

== Outputs

* Source changes for the single task, optionally scaffolded with the project's own `nest g` (dry run first, then every placeholder replaced and every enhancer registered). Prisma schema changes get `prisma generate` and a migration; touched files are formatted with the project's formatter.
* Unit specs next to the source (placeholder specs replaced) that are run and green, and e2e specs for changed HTTP contracts that are written through the project's shared bootstrap but never run, since they boot the whole `AppModule` and may need Docker or a database.
* Enforced rules: module-format-consistent imports, DTO and injected classes as value imports, full TSDoc with `@throws`, no `any`, no per-request state on singletons, no `synchronize: true`, no double-registered global enhancer, no new runtime dependency unless asked.
* The task's own checkbox (and covered sub-tasks) flipped to `[x]` in `implementation_plan.md` with a "group validation pending" note.
* A short report: detected flavor and reference files read, files touched and any `nest g` command, unit results, e2e specs left for the group, Prisma/migration actions, blockers, deviations from `reference/`, and silent-defect patterns noticed in surrounding code.
* It never runs e2e, coverage, lint/type-check, `nest build`, the full suite, license or TSDoc audits.
