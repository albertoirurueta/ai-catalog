= PHP Test
:description: Runs PHP tests via Pest, PHPUnit or artisan test on host, Sail, ddev or wp-env, or browser UI tests with the ui selector, and reports a compact summary.
:keywords: iru-php-test, claude code skill, php, pest, phpunit, laravel, wordpress, wp-env, playwright, ui tests, screenshots

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Run a PHP project's test suite through whichever runner and execution environment it actually has configured, scope the run to what the caller asked for, and report a compact pass/fail summary parsed from the runner's own JUnit XML log. It is a read-only reporting skill: it never fixes a failing test, edits code, installs dependencies, or provisions databases unless asked to as a follow-up.

== Purpose

PHP projects rarely run the same way twice: a library runs on host PHP, a Laravel app inside Sail, a WordPress plugin through `@wordpress/env`, a PrestaShop module only inside a shop. `iru-php-test` detects where PHP runs, which runner is wired (Pest, PHPUnit, `php artisan test`), and which suites are fast unit tests versus integration tests that need a real environment (a WordPress test library, a database, a shop). It then runs exactly the requested selection and reports counts and failures, or reports plainly what environment piece is missing instead of failing obscurely. A selector that matched nothing is reported as such, never as a clean run.

With the `ui` selector it runs the project's browser UI tests instead (Playwright, `wp-scripts test-playwright`, or Dusk/Pest browser where already used), behind the repository-wide `.integration-test.lock`. It captures `.ui-screenshots/` (states × left-to-right/right-to-left × light/dark), validates the capture file names, and reports accessibility (axe) violations as counts and rule ids at the level set in `.ui-quality.yml`. See xref:guides/building-user-interfaces.adoc[Building user interfaces].

Container environments need Docker; if `docker info` fails the skill stops with "Docker is not running" rather than letting the runner fail. The runner is Laravel's `php artisan test` (which wraps Pest or PHPUnit), then Pest, then PHPUnit; the composer `test` script is read to mirror the project's real flags and configs. Missing `vendor/` or no runner stops with a plain report, never "0 tests".

Unit versus integration is decided per project kind (plain library, Laravel with SQLite in-memory versus MySQL, WordPress Brain Monkey/WP_Mock versus `WP_UnitTestCase`, PrestaShop `tests/Unit` versus shop-backed bootstraps). For an integration selection the skill preflights the WordPress test library (it never runs `bin/install-wp-tests.sh` itself), the wp-env test environment (never the development one), database reachability, and the PrestaShop installation, and reports the command that would provision whatever is missing.

== Outputs

* A plain-text summary in the conversation: the environment and runner used, total/failed/error/skipped counts parsed from a JUnit XML log (written under `build/iru-php-test-junit.xml` and deleted afterwards), and for each failure the `Class::method` (or Pest description) with the first line of its assertion message. PHP errors are counted separately from assertion failures.
* A selector that matched nothing (0 tests in the log, or `No tests executed!`) is reported as "selector matched nothing", since exit codes for an unmatched selector are unreliable across PHPUnit and Pest versions. Exit code 255 is reported as a PHP fatal error with its first line.
* A missing environment is reported with the exact missing piece and the provisioning command, plus which tests could still run (for example the Brain Monkey `Unit` suite).
* For a `ui` run: the runner and target, passed/failed/flaky/skipped counts with each failure's first line, the screenshot count per kind and any malformed capture names in `.ui-screenshots/`, accessibility violations as count plus rule ids at the `.ui-quality.yml` level, and lock behavior. A missing browser, wp-env tests instance, shop or `node_modules/` is reported as unverified with the provisioning command; no browser-test setup is reported as "no UI test setup".
* No source or test code is ever modified.
