= .NET Bump Version
:description: Sets a .NET project's version to an exact value in Directory.Build.props or csproj files and in MSIX manifests as a four-part x.y.z.0 identity version.
:keywords: iru-dotnet-bump-version, claude code skill, dotnet, msbuild, directory.build.props, msix, appxmanifest, windows desktop, bump version, release

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Set a .NET project's version to an exact literal value in every place that must agree with it: the MSBuild `<Version>`
(or `<VersionPrefix>` plus `<VersionSuffix>`) and, for a packaged Windows desktop app, the MSIX package identity
version. This skill never computes a version itself; it applies exactly the string it is given, after validating its
shape, and never commits, tags, builds or packages anything.

== Purpose

`iru-dotnet-bump-version` is the .NET counterpart of `iru-java-bump-version`, `iru-php-bump-version` and the other
`iru-<key>-bump-version` skills. It works for a .NET library, a service or a Windows desktop app (WPF, WinUI 3,
Windows Forms) alike. An embedded, tested Python helper (with `--list` and `--dry-run` modes) rewrites the root
`Directory.Build.props` when it declares a version, otherwise every non-test `*.csproj` that does, plus the
`<Identity Version="x.y.z.0">` of every tracked `Package.appxmanifest` and `packaging/AppxManifest.xml` -- always the
four-part numeric value derived from the new version (pre-release suffix stripped, revision `0`, as the Microsoft
Store requires). It rewrites files in place preserving their BOM and CRLF/LF line endings, never touches test projects, reports but never rewrites
explicit `<AssemblyVersion>`/`<FileVersion>` values, and refuses to write when the `<Version>` locations disagree
until the user confirms. Projects whose version comes from git (MinVer, Nerdbank.GitVersioning, GitVersion) are
reported and left unchanged. Step 5 of the skill is the authoritative statement of this catalog's `x.y.z-dev`
development-version convention for callers such as `iru-release`.

== Outputs

* `Directory.Build.props` (or each non-test `*.csproj` when it declares none): `<Version>` set to the new version, or
  `<VersionPrefix>` set to `X.Y.Z` and `<VersionSuffix>` to the suffix (empty for a release).
* Every tracked `Package.appxmanifest` and `packaging/AppxManifest.xml`: `<Identity Version>` set to `X.Y.Z.0`.
* Optionally, README/Antora version mentions mapped by release versus development marker, if `sync-files` was accepted.
* A sanity check (`--list` agreement and `dotnet msbuild -getProperty:Version`), skipped on a dry run.
* A report of every location with its old value, the new values, explicit `AssemblyVersion`/`FileVersion` values left
  untouched, any MSIX identity that was out of step, and a warning to review the diff before committing.
* No commit or tag is created, and a committed `.appinstaller` file is reported but not rewritten.
