= Setup CLI Repository
:description: Bootstraps a Rust, Go, Swift or .NET command-line tool repository end to end: scaffold, docs, gitignore, CI and release workflows, changelog and README.
:keywords: iru-setup-cli-repository, claude code skill, cli, rust, go, swift, dotnet, github actions, bootstrap, orchestrator, release binaries

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

End-to-end bootstrap for a command-line tool repository in Rust, Go, Swift or C#/.NET 10 by orchestrating the language's scaffold skill and the shared repository-level skills in one pass, collecting every shared parameter once.

== Purpose

`iru-setup-cli-repository` is the command-line tool stack orchestrator, run stand-alone or from the `iru-setup-repository` front door (project type `cli-tool (<language>)`). Every generated tool follows one contract across languages: data on stdout and messages on stderr, a documented exit-code taxonomy (0-7, 130/143), `--format text|json|jsonl` with a JSON error envelope, TTY and `NO_COLOR` aware colour, no prompts without a terminal (`--no-input`, `--yes`), `--dry-run` for mutations, and generated `completion` and `schema` commands plus a CLI reference built from the command tree.

The skill resolves `language` (from `args`, from on-disk manifests such as `Cargo.toml`, `go.mod`, `Package.swift` or a .NET `Exe` project, otherwise asked), `ui` (`none` or `tui`, forced to `none` for Swift), `accessibility` (`enforce`, `report`, `off` or `none`, asked only with `ui: tui` and forwarded to the scaffold, which writes it to `.ui-quality.yml`), `branching` (`gitflow` or `main-only`) and `mode`, then collects the tool identity (`bin-name`, description, owner, license, developer details) and the shared pipeline parameters (`open-source`, `visibility`, `ci`, `cross-os-ci`, `sonar`, `ci-tests`, `pages`, `distribution`, `channels`, branches), each with visibility-aware cost guidance. It then runs, each through the `iru-isolated-skill-executor` agent so only a short summary returns: the language scaffold, `iru-setup-antora` (followed by wiring the generated CLI reference page into the site), the language's gitignore skill, `iru-setup-cli-github-workflows` (skipped entirely when `ci` is `no`), `iru-setup-changelog` and `iru-setup-readme`.

It announces the setup mode first (from scratch vs updating an existing repository, with a per-component inventory marked absent/present/partial); each sub-skill then asks Update / Keep as is / Replace for what it finds. A library-only crate, a web service or a desktop app is out of scope, and a repository with several languages' manifests stops the run.

== Outputs

* A scaffolded command-line tool (command tree, library unit, tests, quality configuration, docs generator and optional terminal UI) via the language's scaffold skill.
* With `ui: tui`, a root `.ui-quality.yml` (accessibility level, capture directions and themes) from the scaffold; its UI tests leave text captures in the gitignored `.ui-screenshots/`, which the workflows upload as a 7-day CI artifact.
* An Antora docs site with the generated CLI reference page in its navigation, a root `.gitignore`, `CHANGELOG.md` and `README.md`, via the delegated skills.
* Unless `ci: no`, GitHub Actions workflows (`build`, `release`, `sync` for gitflow, `security`) and Dependabot.
* A final report: the setup mode, resolved language, UI (with its `accessibility` level), branching and mode, identity and license, the pipeline parameters applied, a per-component action table (created / updated / replaced / kept as is / skipped (ci: no)), what was wired or omitted and why, the required-secrets table, every decision made on the user's behalf, and explicit warnings.
