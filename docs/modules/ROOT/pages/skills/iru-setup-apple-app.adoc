= Setup Apple App
:description: Scaffolds an iOS, iPadOS, macOS, watchOS or visionOS app with XcodeGen or Tuist, SwiftUI or UIKit, MVVM or MVC Core package, tests and lint.
:keywords: iru-setup-apple-app, claude code skill, swift, ios, visionos, uikit, swiftui, xcodegen, mvvm mvc architecture, scaffold

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Generate a complete, buildable native Apple application scaffold — a project-generator manifest (XcodeGen's
`project.yml`, or Tuist's `Project.swift` + `Tuist.swift`) declaring one application target `<AppName>-<Platform>`
per selected platform (iOS/iPadOS, macOS, watchOS, visionOS), a UI-framework-free `Packages/Core` local SwiftPM
package (`Models/`, `Services/`, plus `ViewModels/` for MVVM or `Controllers/` + a passive-view protocol for MVC)
whose Swift Testing suite covers 100% of its lines, the per-platform UI layer (SwiftUI everywhere, or programmatic
UIKit for the iOS/iPadOS target), per-platform Swift Testing unit-test and XCUITest UI-test targets, lint/format
config, a `.ui-quality.yml`, an optional gated `fastlane/Fastfile`, and `sonar-project.properties` — from the templates in the skill's
`reference/` files. It announces whether it
is scaffolding from scratch or updating an existing app, and warns and asks Update / Keep as is / Replace / Stop for
each of its files that already exists.

== Purpose

`iru-setup-apple-app` bootstraps a new native Apple application from a house template: one XcodeGen or Tuist
manifest per repository, one application target per selected platform with `SWIFT_STRICT_CONCURRENCY = complete`,
the app's `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` and a pinned unit-test host, a shared `Packages/Core` package
(Foundation + Observation only) that holds all testable logic outside any UI framework, and per-platform Swift
Testing/XCUITest targets driven by a `--uitesting` launch argument and accessibility identifiers on every control.
Following the catalog's UI contract (see xref:guides/building-user-interfaces.adoc[Building user interfaces]), the
UI tests also capture the sample screen in every left-to-right/right-to-left × light/dark cell into
`.ui-screenshots/` through a shared `Tests/Support/UIScreenshots.swift` helper, and run
`performAccessibilityAudit()` at the level configured in `.ui-quality.yml`.
With `ui: uikit` the iOS/iPadOS target becomes a programmatic UIKit app — `AppDelegate` + `UIWindowSceneDelegate`
with a scene manifest (mandatory with the 27 SDK), a `UINavigationController` root and a code-laid-out
`UIViewController`, no storyboards — backed by an MVC controller core (recommended) or an MVVM view model rendered
through UIKit Observation tracking (`UIObservationTrackingEnabled` added below iOS 26); watchOS, visionOS and macOS
targets always stay SwiftUI. visionOS is a native SwiftUI target, not "Designed for iPad"; tvOS, Mac Catalyst and
compatibility destinations are not supported. The resulting layout is the scaffold contract the Swift coding and
gate skills, `iru-explore` and xref:skills/iru-setup-swift-github-workflows.adoc[] rely on. It never commits the
generated `.xcodeproj`/`.xcworkspace` — those are always generator output, regenerated on demand by
`xcodegen generate`/`tuist generate` and gitignored by the companion xref:skills/iru-setup-swift-gitignore.adoc[].
It is the Swift/Apple equivalent of xref:skills/iru-setup-android-app.adoc[] and
xref:skills/iru-setup-react-native-app.adoc[] for the other app-shaped stacks in this catalog; use
xref:skills/iru-setup-macos-app.adoc[] for a macOS-only (SwiftUI or AppKit) desktop app and
xref:skills/iru-setup-swift-library.adoc[] for a pure SwiftPM library with no app target.

== Outputs

* `project.yml` (XcodeGen) or `Project.swift` + `Tuist.swift` (Tuist), per `generator`, with one target/scheme
  triple per selected platform.
* `Packages/Core/Package.swift` (with `swift-docc-plugin`), a DocC catalog, `Models/` (`Greeting`), `Services/`
  (`GreetingProviding`, `GreetingService`, `GreetingError`), `ViewModels/GreetingViewModel` (MVVM / any SwiftUI
  target) and/or `Controllers/GreetingController` + `GreetingView` protocol (MVC), and `Tests/CoreTests` at 100%
  line coverage.
* Per selected platform, `Targets/<Platform>/Sources` — SwiftUI `<AppName>App.swift` + `ContentView.swift`, or for
  the iOS target with `ui: uikit` `AppDelegate.swift`, `SceneDelegate.swift`, `GreetingViewController.swift` and
  `GreetingLayout.swift` — plus `LaunchOptions.swift`; `Tests/` (Swift Testing: `LaunchOptionsTests` and
  `<AppName>Tests`, or `GreetingViewControllerTests`/`AppShellTests` for UIKit); and `UITests/<AppName>UITests.swift`
  (XCUITest).
* `.swiftlint.yml`, `.swift-format` and `.ui-quality.yml` (UI contract settings: accessibility level, directions,
  themes) at the repository root.
* Per platform test target, `Tests/Support/UIScreenshots.swift` (the UI contract capture helper, also compiled into
  the UI-test target); the UI test writes the sample screen's captures to
  `.ui-screenshots/screen/<ScreenType>/default--<ltr|rtl>--<light|dark>--<platform-variant>.png` (gitignored) and
  attaches accessibility-audit issues to the `.xcresult`.
* `fastlane/Fastfile`, with only the lanes `distribution`/`signing` back — never a lane this skill can't support. The
  `platform :ios` lanes (`test`, `build`, `beta`, `release`) are written only when an iOS/iPadOS target was selected.
* `sonar-project.properties`, only when `sonar` != `none` — its SwiftLint input is
  `sonar.externalIssuesReportPaths=swiftlint-sonar.json`, the report the workflows skill's lint job produces.
* No `.xcodeproj`/`.xcworkspace` — those are `xcodegen generate`/`tuist generate` output, never written here.
* A report of every resolved input, the mode announced up front, per file whether it was created, updated,
  replaced or kept as is (with each mismatch listed for a kept file, and how `visibility`/`ci` shaped the Sonar
  recommendation), the Step 7 verification results, the scaffold contract table (targets, schemes, destinations,
  versions, architecture markers, test/coverage/lint commands, UI-test hooks, UIKit specifics), and explicit
  warnings (review before build/commit, run `iru-setup-swift-gitignore`, visionOS runtime needed for its tests,
  signing/Sonar credentials still needed).

== Dependencies

=== Invokes

None — `iru-setup-apple-app` is a leaf skill; it does not call any other skill in this catalog. Verification in
Step 7 runs through the xref:agents/iru-gate-runner.adoc[`iru-gate-runner`] agent, not another skill.

=== Invoked by

* xref:skills/iru-setup-swift-repository.adoc[] — runs `iru-setup-apple-app` for the app flavor, passing the shared
  bootstrap inputs (including `platforms`, `ui` and `architecture`) through `args` so this skill's own Step 2
  questions are skipped.

=== Related agents

* xref:agents/iru-gate-runner.adoc[`iru-gate-runner`] — Step 7 runs `swift test --enable-code-coverage` +
  `llvm-cov report` against `Packages/Core`, `xcodegen generate` (or `tuist generate --no-open`), `xcodebuild test`
  per platform scheme (serialized behind `.simulator-test.lock`), `swiftlint lint --strict` and
  `swift format lint --strict` through this agent so the caller gets a compact pass/fail summary. Missing tools,
  non-macOS hosts or a missing simulator runtime (typically visionOS, which falls back to `build-for-testing`) are
  reported as unverified.
