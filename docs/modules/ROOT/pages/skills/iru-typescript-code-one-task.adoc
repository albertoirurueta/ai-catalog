= TypeScript Code One Task
:description: Implements one TypeScript task from a plan, loading only its framework's reference material, handing React Native apps to their own key, then checks it off.
:keywords: iru-typescript-code-one-task, claude code skill, typescript, react, angular, react native, ionic, hilla, vitest, jest, tsdoc, implementation plan

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Carry out a single task's implementation, tests, and checkbox update against the real codebase — nothing else.
This is the narrowest execution unit in the `iru-code` pipeline: `iru-typescript-code-one-task-group` calls it
once per task in a bucket (potentially many at once, in parallel agents).

== Purpose

`iru-typescript-code-one-task` is the TypeScript-specific implementation worker `iru-typescript-code-one-task-group`
calls once per task. Given one task's own text (what to build, the named file(s)/component(s)/function(s), the
described behavior, its exact `implementation_plan.md` checkbox line(s), and any sub-tasks), it first detects the
project's framework from `package.json` (and, for a Maven-hosted frontend, the root `pom.xml`) — plain npm/TypeScript
library, React, Angular, Ionic, or a Vaadin Hilla frontend; a React Native app (`expo` or `react-native`) now has
its own key, so when `iru-react-native-code-one-task` is installed the task is handed to it and this skill stops,
with only a minimal built-in fallback otherwise — then loads only the matching guidance from
its own bundled `reference/` directory, re-checks the current code state, implements exactly what's specified, and
writes/updates tests. If the task didn't stop on a blocker, it then immediately checks off that task's own checkbox
(and its sub-tasks') in `implementation_plan.md` with a "group validation pending" note, before reporting back — so
an interrupted run doesn't re-attempt work that already landed. License headers, TSDoc audits, scoped tests,
coverage, the full suite, code-quality regression checks, and replacing the pending note with the final validation
outcome all happen once per task group in `iru-typescript-code-one-task-group` instead of once per task. It hands
back only a short summary; it never captures a quality baseline or runs any test/coverage/quality check itself.
Equivalent to `iru-java-code-one-task` for npm/TypeScript projects.

For a task that adds or changes UI (any framework except a plain library) it also applies the catalog's UI contract (see xref:guides/building-user-interfaces.adoc[Building user interfaces]): it writes the `Screen > Region > Component` decomposition first, builds leaves first with presentational components taking props/inputs and emitting typed events, uses the framework's virtualizing container for collections and logical CSS properties for right-to-left, and writes the UI tests (stories per visual state, Playwright component, screen and flow specs that capture every direction x theme and run the accessibility check) without running them.

=== The bundled reference library

This skill ships a `reference/` directory alongside its `SKILL.md`, holding this catalog's **general TypeScript
code agreements** — strict typing with no `any`, `readonly` and discriminated unions, named exports, ESM, error
handling, and async conventions — plus one file per supported framework for the conventions that only apply
there. It is read by **progressive disclosure**: `reference/README.md` is a short routing table, `code-style.md`
is always read, and everything else only when the task's shape and detected framework call for it, so a one-line
change inside a plain library doesn't pay for React, Angular, or Hilla guidance it will never use.

[cols="2,1,3", options="header"]
|===
|File |Read when |Covers

|`code-style.md`
|Always
|Strict typing with no `any` (use `unknown` plus a narrowing guard, a generic, or a proper union/discriminated
union instead), `readonly` and immutability as the defaults for new code, named exports (no default exports for
new modules, except where a framework requires one), ESM module conventions, error-handling and async patterns.

|`tsdoc.md`
|The task adds or changes an exported function, class, interface, type alias, or enum
|Full TSDoc as a hard requirement — `@param`, `@returns`, and `@throws` for every error a caller can handle,
the `@throws` list being what the tests in Step 4 are written against.

|`testing.md`
|The task writes or updates tests — nearly every task
|Matching the existing test style in the same directory (Vitest or Jest, Testing Library query priority, mocking
with `vi.mock`/`jest.mock` only where already used) and covering the new/changed behavior, including the edge
cases implied by the TSDoc `@throws` contracts.

|`ui-contract.md` + `ui-implementation.md`
|The task adds or changes a screen, component, list or other UI (any framework except library); read in addition to the framework file
|The catalog-wide UI rules (decomposition, composition, inputs/events, virtualized collections, UI tests, screenshots, accessibility) mapped onto React, Angular, Ionic and Hilla, Storybook stories and Playwright. `ui-screenshots.ts` is the shared screenshot/accessibility helper copied into the project as `e2e/support/ui-screenshots.ts` when it has none.

|`react.md`
|Detected framework is **react** (`react` + `vite` in `package.json`)
|Component/state/testing conventions for a Vite+React project.

|`angular.md`
|Detected framework is **angular** (`@angular/core` in dependencies)
|Component/state/testing conventions for an Angular CLI project.

|`react-native.md`
|Detected framework is **react-native** *and* `iru-react-native-code-one-task` is not installed
|A pointer to the `react-native` key plus a minimal fallback (toolchain detection, never editing Expo prebuild
output, Expo Router default exports, platform files, RNTL testing, security and UI basics). When the key is
installed, the task was already handed over and this file is not read.

|`ionic.md`
|Detected framework is **ionic** (`@ionic/angular`/`@ionic/react` with `@capacitor/core`)
|Component/state/testing conventions for an Ionic/Capacitor project.

|`hilla-frontend.md`
|Detected framework is **hilla-frontend** (`@vaadin/hilla`/`hilla-spring-boot-starter` in `pom.xml`, or a
`src/main/frontend/` directory)
|Component/state/testing conventions for a Vaadin Hilla frontend.
|===

`reference/README.md` also notes that the full React Native guidance and its sources live in
`iru-react-native-code-one-task/reference/`.

Exactly one framework file is read — the one matching the detected framework — never more than one, and none at
all when the classification is **library**; the UI pair is read in addition for UI tasks. The skill also notes the test runner (Vitest, Jest, or `ng test`) and
package manager (npm, pnpm, or yarn) while detecting the framework, since `reference/testing.md` and the task's
own shell commands depend on both. If `reference/` is missing entirely, the skill falls back to the repository's
own `CLAUDE.md` conventions and the surrounding code's existing style, and says so in its report rather than
guessing at what the reference would have said.

Every file states the same override: the rules are the default for **new** code, and a file that consistently
does something else wins. A divergence is reported rather than silently converted, because restyling untouched
code turns a two-line change into an unreviewable diff.

== Outputs

* Source and test files created/modified per the task, following the bundled `reference/` agreements — strict
  typing with no `any`, `readonly`/immutability defaults, named exports, full TSDoc on every exported symbol, and
  the detected framework's own component/state/testing conventions — plus this repository's own `CLAUDE.md`
  conventions where they are more specific, and the surrounding file's existing style wherever it consistently
  differs.
* Tests added/updated (Vitest or Jest, matching the detected runner) covering the new/changed behavior, including
  a case per documented `@throws` — not run by this skill; the caller runs them once for the whole bucket.
* For UI work: a story per visual state next to each added/changed component (minimal, typical, many-items/long-content and right-to-left fixtures), a Playwright component spec (behaviour once, then `captureUiMatrix` per state with the accessibility check), a screen spec and, for a new flow, a flow spec, using `e2e/support/ui-screenshots.ts` (created from `reference/ui-screenshots.ts` with `@axe-core/playwright` as a dev dependency when missing). With no Playwright setup at all it writes behaviour tests only and reports the gap as a deviation. Captures go under `.ui-screenshots/<kind>/<Id>/<state>--<direction>--<theme>.png` when the group's UI stage runs them.
* `implementation_plan.md` with this task's own checkbox (and its sub-tasks') checked off and a "group validation
  pending" note, written immediately once the task finishes cleanly — before this skill reports back, and before
  the caller's own group-wide validation runs. Left untouched if the task stopped on a blocker.
* For a React Native task with `iru-react-native-code-one-task` installed: that skill's report, relayed as this
  skill's Step 7 report with a note about the hand-off (and that the plan should tag such tasks `react-native`).
* A short summary handed back to the caller: the detected framework and which `reference/` file(s) were actually
  read (for react-native, whether the task was handed over or the minimal fallback was used), the file(s) touched, tests added/updated, for UI work the decomposition tree, the stories and UI specs added and the screenshot states they will capture, whether the run stopped on a blocker, and any deliberate
  deviation from `reference/` (a file that still uses `any`, a default export kept because the framework requires
  one, a file whose existing member order or style already diverges) so it reads as a decision rather than an
  oversight.

follows the surrounding code and reports the divergence in Step 7.

== Dependencies

=== Invokes

* xref:skills/iru-react-native-code-one-task.adoc[] — Step 1, when the detected framework is `react-native` and
  that skill is installed; it receives the task's full text unchanged and this skill stops after relaying its
  report.

Otherwise it calls no other skill in this catalog. It reads its own `reference/` directory and edits the code and test files the task names. License headers, TSDoc audits,
scoped tests, coverage, and quality checks all live in `iru-typescript-code-one-task-group`.

=== Invoked by

* xref:skills/iru-typescript-code-one-task-group.adoc[] — Step 2, once per task in a `typescript` bucket
  (concurrently, in a single batch of `Agent` calls, when the group is marked `Parallelizable: yes`; one at a time
  otherwise), via the xref:agents/iru-isolated-skill-executor.adoc[`iru-isolated-skill-executor`] agent, passing
  that task's full text including its exact checkbox line(s). That caller re-reads `implementation_plan.md`
  afterward to confirm the checkbox this skill already flipped landed, backfilling it only if a rare concurrent-
  write race clobbered it, then replaces the "pending" note with the final validation outcome once the whole
  bucket's validation passes.
* xref:skills/iru-react-native-code-one-task.adoc[] — names this skill as its counterpart and the basis for its
  conventions; it does not invoke it.

=== Related agents

the code/test files the task names.
