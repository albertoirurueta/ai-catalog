= Setup Python GitHub Workflows
:description: Creates or updates uv-driven GitHub Actions CI, release, sync and security workflows for FastAPI and Django repositories, with GHCR image publishing.
:keywords: iru-setup-python-github-workflows, claude code skill, github actions, python, uv, fastapi, django, ghcr, dependabot, pip-audit

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Scaffolds or updates the CI/CD and security pipeline for a Python web repository of either flavor — a FastAPI service
or a Django project — driving everything through the uv commands that the matching `iru-setup-python-*` scaffold
defines.

== Purpose

`iru-setup-python-github-workflows` writes the GitHub Actions files a FastAPI or Django repository needs, matched to
its flavor and to cost-aware choices made up front:

* `build.yml` — runs on pushes to the integration/stable branches, pull requests, and `workflow_dispatch`. It uses
  `astral-sh/setup-uv` with `uv sync --locked`, Ruff lint and format checks, mypy, and (for Django) `manage.py check`,
  `makemigrations --check --dry-run` and the DRF or Ninja schema validation. Fast tests run with Cobertura coverage
  (80% floor) and JUnit XML, across a Python matrix only for `ci-tests: full` on a public repository. A `migrations`
  job runs against a PostgreSQL service container (or a SQLite file): Alembic upgrade/check/single-head/downgrade for
  FastAPI, `check --deploy` with production settings plus `migrate --check` for Django. With `ci-tests: full` and
  `database: postgresql` it adds a testcontainers-backed integration job — for a Django project with the scaffold's browser UI tier (`tests/ui/` and the `ui` marker) that same job also installs Chromium, runs `pytest -m ui` (Playwright + axe-core at the `.ui-quality.yml` level) and uploads `.ui-screenshots/` as a 7-day `ui-screenshots-integration` artifact; no extra job is added. FastAPI, SQLite and `ci-tests: unit` variants run no UI tier in CI (it stays a local `uv run pytest -m ui`). When `.ui-quality.yml` has `accessibility: none`, no accessibility report is collected or uploaded and any accessibility-only step is dropped. It also builds the container image without
  pushing it, adds an optional SonarCloud/SonarQube job (skipped on fork pull requests), and a docs job (Antora plus
  Sphinx API docs and the OpenAPI document) deployed to GitHub Pages or uploaded as an artifact.
* `release.yml` per `distribution` — on a published GitHub Release: version check against the tag, `uv build`
  sdist and wheel attached to the release, and the root `Dockerfile` pushed to GHCR (private for `internal`, public for
  `store`). Not written with `distribution: none`. There is deliberately no PyPI publishing.
* `sync.yml` plus `.github/scripts/python_version.py` and `.github/scripts/sync_versions.py` — after a release from the
  stable branch, a pull request merges it back into the integration branch with the next PEP 440 `X.(Y+1).0.dev0`
  version and a refreshed `uv.lock`, the convention `iru-python-bump-version` and `iru-release` use.
* The shared security block — `security.yml` (dependency-review, CodeQL for `python` and `actions`, OSV-Scanner over
  `uv.lock`, gitleaks, plus this stack's `pip-audit` job) and `.github/dependabot.yml` (uv or pip, github-actions,
  docker, docker-compose, npm for the Antora toolchain).

It announces whether it is creating the pipeline from scratch or updating an existing one, and asks per workflow file
whether to Update, Keep as is, Replace, or Stop. Templates are validated with `actionlint`, and the commands the
workflows contain are run locally first, so nothing is a guess.

== Outputs

* `.github/workflows/build.yml`, and `release.yml` unless `distribution: none`.
* `.github/workflows/sync.yml` with `.github/scripts/python_version.py` and `.github/scripts/sync_versions.py`
  (made executable).
* `.github/workflows/security.yml` and `.github/dependabot.yml`.
* In the Django `build.yml` integration job, when `tests/ui/` exists: the `# ui` steps (Chromium install, UI test run, `pytest-ui.xml` report and the `.ui-screenshots/` artifact upload). See xref:guides/building-user-interfaces.adoc[Building user interfaces].
* A report with the required secrets (`SONAR_TOKEN` when Sonar is enabled), repository settings to check (workflow
  permissions for pull requests, Pages source, code scanning, GHCR package visibility), the choices made, per-unit
  created / updated / replaced / kept as is, and every open gap (missing contract tooling, no Antora setup, no
  `Dockerfile`, unverified Docker-based jobs, whether the integration job runs the UI tier and uploads screenshots or why not, and the UI steps being unverified without a browser).

The generated files' bytes come from template files under `templates/` (and, where a template needs variant-specific notes, `reference/`) in `.claude/skills/iru-setup-python-github-workflows/`; the skill reads only the files for the variant it resolved, not the whole set, which keeps its `SKILL.md` small.
