Scaffold or update the `develop.yml`, `main.yml`, `sync.yml`, and `security.yml` GitHub Actions workflows
(plus the companion `.github/scripts/sync_versions.py` script and `.github/dependabot.yml`) that make up a
Java/Maven library's CI/CD release and security pipeline.

== Purpose

`iru-setup-java-github-workflows` wires up the full house pipeline for a Java/Maven repository: build and test,
Checkstyle/PMD/SpotBugs static analysis, JaCoCo coverage and a Maven `site` report, an optional
SonarQube/SonarCloud scan (gated by `sonar`), an Antora documentation build, publishing both the Antora docs
and the Maven site report to GitHub Pages, and an optional publish of the release artifact to Maven Central
(gated by `publish`, along with its `setup-java` signing inputs and `mvnsettings.xml`). `develop.yml` runs this
pipeline on every push to the integration branch; `main.yml` runs the same pipeline when a GitHub Release is
published; `sync.yml` triggers on that same release-published event to open a pull request merging the
released branch back into the integration branch and bumping the development snapshot version across
`pom.xml`, `README.md`, and the Antora docs, via `sync_versions.py`. `security.yml` runs a
dependency-review/CodeQL/OSV-Scanner/gitleaks block on every pull request and push to the integration/stable
branches, each job individually gated by its own `security-*` argument (default `yes`); `.github/dependabot.yml`
(grouped weekly updates for `maven` and `github-actions`) is always generated with no opt-out. The skill ships
generic, genericized example templates (derived from a real repository's workflows) embedded in the skill file
itself, and resolves every placeholder in them from a survey of the target repository rather than guessing. If
any of the workflow files already exist, it asks the user whether to stop or attempt an update using the
templates as reference, preserving any step this skill doesn't own (e.g. a Slack notification).

== Outputs

* `.github/workflows/develop.yml`, `.github/workflows/main.yml`, `.github/workflows/sync.yml`, and
  `.github/workflows/security.yml` — created fresh, or updated in place if any already existed and the user
  chose to continue. The Maven Central deploy step and its `setup-java` signing inputs in `develop.yml`/`main.yml`
  are generated only when `publish: yes`; the SonarCloud analysis step only when `sonar` isn't `none`.
* `.github/scripts/sync_versions.py`, always written together with `sync.yml` — never one without the other.
* `.github/dependabot.yml` — grouped weekly updates for the `maven` and `github-actions` ecosystems, always
  generated/updated regardless of the `security-*` args.
* Supporting files created if missing: `sonar.*` properties and the `sonar-maven-plugin` added to `pom.xml`
  (only when `sonar` isn't `none`), the Maven settings file used for deploy — default `mvnsettings.xml` — (only
  when `publish: yes`), plus `.gitignore` entries for `/docs/build/` and `/target/` if absent.
* A report of required repository secrets and the repository setting that must be enabled for `sync.yml` to be
  able to open pull requests, plus any open gaps (missing Central plugin, missing signing profile, missing
  Antora setup, README/Antora wording that didn't match `sync_versions.py`'s default regexes).

None of `security.yml`'s four jobs need a secret beyond the automatically provided `GITHUB_TOKEN`.
