= Go Test
:description: Runs Go tests with go test -json, race detector and testscript, splits fast from integration tests, checks terminal-UI captures, reports a summary.
:keywords: iru-go-test, claude code skill, go, go test, testscript, testcontainers, gotestsum, race detector, ui screenshots, bubble tea

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Run a Go module's or workspace's tests, scoped to whatever the caller asked for, and report a compact pass/fail summary parsed from the `go test -json` event stream. It is a report-only skill: it never fixes a failing test, modifies source or test code, edits `go.mod`/`go.sum`, re-vendors, or starts containers unless asked to as a follow-up.

== Purpose

Go projects differ in layout and in how their tests are split. `iru-go-test` detects the toolchain, tells modules from `go.work` workspaces (where `./...` does not cross module boundaries), respects vendored dependencies (`-mod=vendor` is automatic, and inconsistent vendoring is reported rather than bypassed with `-mod=mod`), and decides whether the race detector can run. It separates fast, container-free tests from container-backed ones behind the `integration` build tag, runs exactly the requested selection with `-count=1` so cached results are never reported as a fresh run, and parses the event stream with an embedded stdlib Python parser. Only leaf subtests are counted and listed, in-process testscript failures are reported by their `FAIL: <script>.txtar:<line>` line, and build failures, package-level failures (timeouts, `TestMain`) and packages with no test files are reported separately and plainly, never as "0 tests".

For a Bubble Tea project it also applies the catalog's UI contract (see xref:guides/building-user-interfaces.adoc[Building user interfaces]): the project's UI tests are ordinary in-process tests that write the stripped view as `.txt` into `.ui-screenshots/`, so Step 4a only prepares the directory (`UI_SCREENSHOTS_DIR`, default `<repo root>/.ui-screenshots`, prefixed onto the `go test`/`gotestsum` command), clears it only on a full unscoped run, reads the `accessibility` level from `.ui-quality.yml` (`none` or `off` means the checks are not applicable and are reported as "accessibility: opted out" or "accessibility checks off", never unverified or failed), and afterwards validates capture names and counts captures and accessibility rule ids with an embedded stdlib Python script. No lock is needed.

== Outputs

* A plain-text summary in the conversation: the Go version, module and scope, flags used (`-race`, `-count=1`, fast or integration selection), counts of packages, tests, passed, failed and skipped, and for each failing leaf test `<package>.<Test/sub>` with the first line of its message.
* Build failures (`[build failed]`, `[setup failed]`) and package-level failures outside any test (timeouts, `TestMain`, `os.Exit`) listed separately; packages with no test files summarized in one line.
* A run that matched nothing is reported as "no test files" or "`run:` matched no test", and a missing race detector or gotestsum is said plainly.
* An integration run that could not happen is reported as unverified (Docker unavailable, blocked by a concurrent run), never as passed or as failed tests; environment failures such as an unreachable Docker daemon are classified as such.
* Wiring problems (inconsistent vendoring, missing `go.sum` entry, toolchain too old) are named as such, never papered over.
* For a terminal-UI project (Step 4a): the capture directory and whether it was cleared (full run) or kept (scoped run), captures per kind (`component`/`screen`/`flow`), malformed names (count + first few paths), accessibility violations as counts per rule id (from failing tests under `enforce`, from `a11y-report.txt` under `report`) and the `.ui-quality.yml` level applied. Terminal UIs have no automated accessibility audit; the checks are the asserted `tui-color-only`, `tui-help-line` and `tui-keyboard` ones, and the report says so.
* `build/test-results/go-test.json` (and `go-test.xml` with `junit: yes`), kept when `build/` is gitignored.
* No source or test code is ever modified.
