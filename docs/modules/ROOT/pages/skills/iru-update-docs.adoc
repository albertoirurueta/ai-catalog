= Update Docs
:description: Updates Antora AsciiDoc or Markdown docs from a git diff, with optional target, pages and content kinds and UI screenshots, never editing source code.
:keywords: iru-update-docs, claude code skill, antora, markdown, documentation, git diff, mermaid diagrams, code-to-docs sync, ui documentation

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Bring an Antora-based documentation module's `.adoc` pages (or, in a repository documented in Markdown, its `.md`
pages; and its `nav.adoc`/`antora.yml` if structure or version changed) up to date with changes already made to the codebase. This skill only edits documentation — it
never changes source code, and it never invents documented behavior that isn't actually in the code.

== Purpose

`iru-update-docs` closes the gap between a code change and a stale documentation site. It reads the actual diff, not
just file names, cross-checks every class/method/endpoint it plans to mention against the real current source,
and only touches the specific pages that diff actually concerns — leaving the rest of the site untouched. It
makes no assumption about a fixed docs path or a fixed set of page names; it discovers the real Antora module(s)
present and their real page map fresh each run, which is why it works the same way regardless of which
repository it's invoked in. If a documentation MCP (e.g. Confluence, Notion) is connected, it extends the same
diff-driven understanding to that external system too — finding the relevant existing page(s) there first, then
showing the user the exact proposed change for approval before anything is written. Before drafting anything
against that connector, it checks what its own tools actually expose: if the connector is read-only (search/read
only, no create-page/update-page tool), it warns the user by name and skips the external-docs enrichment
entirely instead of drafting an update it could never send.

Optional `target:`, `pages:` and `content:` arguments (defined in `reference/markdown-docs.md`) let a caller ask for
specific pages and content kinds — data model, UML class, sequence, workflow, architecture, API, configuration,
equations and figures — on a chosen target: the Antora module, GitHub-flavoured Markdown in the repository, or a
connected documentation MCP. xref:skills/iru-code.adoc[] passes them from the plan's `AC-DOC` documentation task.
`target` never narrows what is kept in sync: the repository's own pages that the diff affects are always updated too.
A repository with no `antora.yml` but a Markdown docs folder or README sections takes the Markdown path (Mermaid
fences, `$...$` equations, SVG figures beside the pages, Mermaid check only, no offer to set up Antora).

For repositories with a user interface it also maintains a **User interface** section (Step 4b, defined by `reference/ui-docs.md`): a
`ui/index.adoc` overview, a `ui/navigation.adoc` navigation-flows page, one page per screen/page/activity and one per
component/fragment/view/control, illustrated with the screenshots the UI tests captured under `.ui-screenshots/` (states x
left-to-right/right-to-left x light/dark; see xref:guides/building-user-interfaces.adoc[Building user interfaces]). On a first run
it documents the whole UI, afterwards only changed screens and components; a final synchronisation copies only the
referenced screenshots into `images/ui/`, replaces the images of changed components, deletes unreferenced ones and then
removes `.ui-screenshots/`. A repository with no UI skips it, and a missing `reference/ui-docs.md` means plain pages without screenshots.

== Inputs

[cols="1,1,3,2", options="header"]
|===
|Argument |Required |Description |Default

|`git-ref-or-range`
|No
|A commit, ref, or range (e.g. a tag, `main..HEAD`) to scope the documented diff to.
|None — defaults to uncommitted changes plus commits on the current branch not yet on the repository's base
branch (`git diff <base-branch>...HEAD` plus `git diff`).

|`target`
|No
|Where the requested `pages:` and `content:` go: `markdown` (GitHub-flavoured Markdown in the repository), `antora`
(the Antora module) or `mcp` (a connected documentation MCP, written only after approval). Never narrows the sync of
the repository's own affected pages.
|Detected: the Antora module if one exists, else the Markdown docs.

|`pages`
|No
|Comma-separated page paths to create or update (`.md`/`.adoc` under the docs folder, or a README heading).
|The pages the diff affects.

|`content`
|No
|Comma-separated content kinds to produce: `data-model`, `uml-class`, `sequence`, `workflow`, `architecture`, `api`,
`configuration`, `equations`, `figures`. An unknown kind is reported and skipped.
|Only what the diff warrants.
|===

Arguments arrive as `key: value` lines (as `iru-code` Step 8 passes them) or inline; any other text is the git ref or range.

== Outputs

* Updated `.adoc` pages (or `.md` pages on the Markdown path) reflecting only what the scoped diff actually changed —
  new/removed/renamed public APIs, behavioral changes, new variants of an existing abstraction, or changed documented commands.
* When `content:`/`pages:` are given: each requested content kind on the named pages, grounded in the real source
  (Mermaid `erDiagram`, `classDiagram`, `sequenceDiagram`, flowcharts, API and configuration tables, equations, SVG
  figures), falling back to a table or SVG figure when an extension is not wired in.
* On the Markdown path: GitHub-flavoured pages with ```` ```mermaid ```` fences, `$...$`/`$$...$$` equations and SVG
  figures linked relatively, checked only with the Mermaid validator (no Antora build).
* Search is detected as Pagefind or Lunr; an older Antora or Lunr is reported with a pointer to xref:skills/iru-update-antora.adoc[], never upgraded here.
  MathJax is written as `stem:[...]` or `[stem]` blocks (never bare `\( \)`), and `nav.adoc` follows the nav rules (no empty group headings, no `#fragment`
  entries); the dead-end check runs after a nav change when the nav override is installed.
* `nav.adoc`/`antora.yml` updated only if a page was added, removed, or renamed, or the component version should
  track a source version bump.
* Mermaid diagrams (`[mermaid]`) or MathJax equations added only where the Antora playbook already has the
  matching extension wired in, and only where they genuinely clarify a decision process, data flow, or formal
  definition better than prose.
* For a repository with a UI: the `ui/` pages (`index.adoc`, `navigation.adoc`, `screens/<Id>.adoc`, `components/<Id>.adoc`)
  with a **User interface** section in `nav.adoc`, and the screenshots they use copied under `images/ui/<kind>/<Id>/`
  (changed ones replaced, unreferenced ones and the pages of removed components deleted); `.ui-screenshots/` is deleted
  afterwards.
* If no `antora.yml` existed anywhere in the repository and the user agreed to bootstrap one: a newly scaffolded
  Antora module (via `iru-setup-antora`), then the rest of the run proceeds against it.
* If a documentation MCP (e.g. Confluence, Notion) is connected and exposes a write (create/update-page) tool: a
  proposed update to the relevant existing external page(s), sent only after the user reviews and approves the
  exact change shown to them.
* If a documentation MCP is connected but only exposes read tools: an explicit warning naming the connector, and
  the external-docs enrichment skipped entirely for this run — never a drafted change that couldn't be sent.
* A report naming, per page: what changed in the source that drove the edit and what was updated in the docs —
  plus, for a UI repository, the screenshot synchronisation result (images added, replaced, unchanged, deleted, pages added/removed, states left "screenshot pending"), pages deliberately left unchanged, any doc gap noticed but left out of scope, and what was sent (or
  proposed-but-declined) to a connected documentation MCP.
* No source code is ever modified.

== Dependencies

=== Invokes

* xref:skills/iru-setup-antora.adoc[] — Step 2, conditionally: only when no `antora.yml` is found anywhere in the
  repository, and only after asking the user whether to bootstrap Antora documentation now. Run via a sub-agent
  (the Agent tool) briefed with the actual code-change context, so `iru-update-docs` itself can resume once
  scaffolding finishes and continue with the rest of its run against the newly created module.

=== Invoked by

* xref:skills/iru-code.adoc[] — Step 8, updates the documentation for the whole run, passing `target:`, `pages:` and
  `content:` from the plan's `AC-DOC` entry when one is present and not declined.
* Also meant to be run directly by a person (or potentially by another skill in a different repository) after
  code changes have already been made outside the `/iru-code` flow.

=== Related agents

None directly — `iru-update-docs` delegates the conditional `iru-setup-antora` call in Step 2 to a sub-agent (see
xref:agents/overview.adoc[]), but that is calling a skill through a sub-agent wrapper rather than relying on an
agent's own unique capability, so no agent is listed as a direct dependency here.
