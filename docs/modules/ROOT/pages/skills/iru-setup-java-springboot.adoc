= Setup Java Spring Boot
:description: Bootstraps or updates a Spring Boot service as a hexagonal multi-module build in Java or Kotlin, with Maven or Gradle, CI, Sonar, OpenTofu and docs.
:keywords: iru-setup-java-springboot, claude code skill, spring boot, kotlin, gradle, hexagonal architecture, maven multi-module, spring initializr, microservice bootstrap, hilla, blue green deployment, canary, rolling deployment

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

End-to-end bootstrap for a new (or older, partially set-up) Spring Boot service repository built on Domain-Driven Design and hexagonal
(ports and adapters) architecture, realised as a multi-module build: a Maven reactor for Java, or for Kotlin either
a Maven reactor or a Gradle Kotlin DSL multi-project build. It interviews the user once, resolves
every Spring Boot version and dependency id against the live Spring Initializr API, records the answers — including
the language, build tool, Kotlin version, whether the project is open source, its visibility, its CI choices, its Sonar mode, and whether it ships a Hilla frontend — in a
`springboot-stack.yml` manifest, and then delegates all file generation to seven sub-skills (eight when
`frontend: hilla`).

== Purpose

`iru-setup-java-springboot` is the top-level entry point for starting a Spring Boot microservice from nothing, or for updating a repository
that already has an older or partial setup. It announces which of the two it is doing ("from scratch" or
"updating an existing repository", with an inventory of what is absent, present, or partial) and then lets each
sub-skill ask Update / Keep as is / Replace per pre-existing artifact it owns. It
is the **interviewer and orchestrator** of the Spring Boot family: no other skill in that family asks the user
anything about the stack, because this one asks everything exactly once and writes the answers to a manifest the
others read back.

Four things distinguish it from `iru-setup-java-library-repository`, the catalog's other bootstrap orchestrator:

* **It imposes an architecture.** The module layout (`domain`, `application`, `infrastructure/*`, `api/*`, `boot`,
  `coverage`), the direction dependencies may point, and the rule that every dependency version lives in exactly
  one place — the root `pom.xml` on Maven, `gradle/libs.versions.toml` on Gradle — are not options; they are what
  the skill exists to enforce.
* **It supports Java and Kotlin.** Step 3 asks the implementation language (Java recommended unless the repository
  already has Kotlin) and, for Kotlin only, the build tool (Gradle Kotlin DSL recommended for a new repository,
  Maven for an existing Maven one). Java is always Maven; Java on Gradle and Groovy-DSL Gradle builds are rejected.
  Kotlin uses detekt/ktlint and Dokka instead of Checkstyle/PMD/SpotBugs and Javadoc, no Lombok or MapStruct, and
  a Kotlin version resolved from the one the chosen Boot version manages rather than from memory. The choices are
  recorded as `project.language`, `project.buildTool` and `project.kotlinVersion`, and every sub-skill branches on them.
* **It resolves the stack from a live API rather than from memory.** Spring Boot renames starter artifacts across
  major versions (in Boot 4.x `spring-boot-starter-web` became `spring-boot-starter-webmvc`, the Testcontainers
  modules became `testcontainers-<engine>`, and every starter gained a `spring-boot-starter-<x>-test` companion),
  so the skill reads `https://start.spring.io/metadata/client` for the current version list and dependency
  catalogue, and fetches a reference `pom.xml` from `https://start.spring.io/pom.xml` for the exact artifact names.
  If that API is unreachable it stops rather than guessing.
* **It produces a deployable service, not a publishable library.** There is no Maven Central publishing or GPG
  signing; instead there is a container image, OpenTofu infrastructure-as-code for AWS or Google Cloud, and deploy
  and undeploy workflows.

Java 21 is the enforced minimum, in `maven.compiler.release`, `java.version`, and a `maven-enforcer-plugin`
`requireJavaVersion` rule on Maven, or the JDK toolchain on Gradle — even though Spring Initializr's own default
`javaVersion` is currently lower.

== Outputs

* `springboot-stack.yml` at the repository root — the manifest recording the resolved identity, every technology
  choice, and also `openSource`, `sonar` (`mode`/`organization`/`projectKey`/`hostUrl`), `frontend`
  (`none`/`hilla`), `visibility`, `ci` (`enabled`/`tests`/`pages`), and the optional `deploy.rolling` block
  (`enabled`, `strategy`, `advance`, `steps`, `bakeMinutes`; absent means rolling deployments are disabled), with
  container image tags pinned. If a
  manifest already existed, the user chooses Update / Keep as is / Replace (or `on-existing` applies). Meant to be committed; read by every sub-skill and later by
  `iru-update-java-springboot-documentation`.
* The full build (via `iru-setup-java-springboot-pom`): for Maven (Java, or Kotlin + Maven) a root reactor `pom.xml`
  plus one pom per module; for Kotlin + Gradle `settings.gradle.kts`, `gradle/libs.versions.toml`, the `build-logic/`
  convention plugins, one `build.gradle.kts` per module and the Gradle wrapper. Kotlin builds also get a root
  `detekt.yml`.
* The hexagonal source tree — ports, adapters, use cases, the `@SpringBootApplication` class, per-profile
  configuration, migration changelogs, and an ArchUnit test enforcing the dependency direction, as Java or Kotlin
  sources (via `iru-setup-java-springboot-modules`).
* The `apis/` contract tree, the OpenAPI/protobuf/GraphQL-SDL/AVRO generator wiring, and the AsyncAPI
  specification and documentation generators for messaging (via `iru-setup-java-springboot-apis`).
* When `frontend: hilla`: the Vaadin/Hilla React frontend in the `boot` module — the Vaadin BOM/starters, the
  `vaadin-maven-plugin` execution, `src/main/frontend/`, Vitest with lcov coverage, and ESLint/Prettier (via
  `iru-setup-java-springboot-hilla`), together with `.ui-quality.yml` and the Playwright UI tests that capture
  `.ui-screenshots/` across states, left-to-right/right-to-left and light/dark with axe-core checks at the chosen
  `accessibility` level.
* `compose.yaml` and the Testcontainers integration-test harness (via
  `iru-setup-java-springboot-testcontainers`).
* An `infra/` OpenTofu configuration for the chosen cloud (via `iru-setup-java-springboot-platform`).
* `build.yml`, `deploy.yml`, `undeploy.yml`, and `security.yml` GitHub Actions workflows plus
  `.github/dependabot.yml` (via `iru-setup-java-springboot-github-workflows`) — all skipped when `ci: no`. When
  rolling deployments are enabled, `deploy.yml` becomes a staged rollout and a `promote.yml` workflow is generated
  to advance, roll back or abort it (a `rolling` strategy keeps the single-job `deploy.yml` and generates no
  `promote.yml`); the OpenTofu configuration then also carries the rollout infrastructure and `rollout_*` outputs.
* An Antora documentation site with Mermaid and Kroki and the full service page set (via
  `iru-update-java-springboot-documentation`).
* Repository-level supporting files: `.gitignore`, `README.md`, `CHANGELOG.md`, `checkstyle.xml` (Java only; an
  existing one is kept), and optionally `LICENSE`. On Kotlin builds `detekt.yml` is expected from the pom sub-skill
  and reported as a gap if missing.
* A final report with the setup mode and, per component, the action taken (created / updated / replaced / kept as is /
  skipped (ci: no)), consolidating the open-source/visibility/CI/Sonar/frontend choices, whether rolling deployments are enabled (strategy,
  advance mode, steps and bake minutes, whether `promote.yml` was generated, the `rollout_*` outputs and
  prerequisites, the cost note that blue/green temporarily doubles capacity, and that
  `/iru-springboot-rolling-deployments enable|disable` switches it later) (and, when `frontend: hilla`, the `accessibility` level, the `.ui-quality.yml` action, and what
  `iru-setup-java-springboot-hilla` reported back), every secret and variable that must be supplied out-of-band
  (the Sonar token only when `sonar.mode` is not `none`, plus `GITLEAKS_LICENSE` if a Pro key is used), every open
  gap, and the result of the three verification builds (Maven or Gradle, as run).

== Dependencies

=== Invokes

Each of the following is invoked via the xref:agents/iru-isolated-skill-executor.adoc[`iru-isolated-skill-executor`]
agent rather than a direct `Skill` call, in this order — every sub-skill reads `springboot-stack.yml` and the
filesystem directly, so only a short completion summary needs to come back:

* xref:skills/iru-setup-java-springboot-pom.adoc[] — Step 8, first: the root reactor pom and every module pom.
  Generates the Maven reactor, or the Gradle KTS settings/catalog/convention plugins/wrapper for Kotlin + Gradle, reading
  the language and build tool from the manifest. Also receives the path to the Initializr reference build saved in Step 7. If this reports that the root pom was
  not written (or an existing non-reactor pom was kept), the whole run stops. Receives `mode`, and `on-existing` only when it arrived via `args`.
* xref:skills/iru-setup-java-springboot-modules.adoc[] — Step 8: the source tree (Java or Kotlin), ports, adapters,
  profiles, and the ArchUnit test. Runs after the poms because it writes sources into modules rather than creating them.
* xref:skills/iru-setup-java-springboot-apis.adoc[] — Step 8: the `apis/` contracts, the code generators, and the
  AsyncAPI documentation generators. Runs after the modules because generated sources need a module to land in.
* xref:skills/iru-setup-java-springboot-hilla.adoc[] — Step 8, sub-step 3b, only when the manifest's
  `frontend: hilla`: the Vaadin/Hilla React frontend scaffolded into the `boot` module. Runs after the APIs (the
  `boot` module and API-generated code it may call must already exist) and before Testcontainers (the compose
  stack and CI docs job need to know a frontend toolchain now exists on disk).
* xref:skills/iru-setup-java-springboot-testcontainers.adoc[] — Step 8: `compose.yaml` and the integration-test
  harness. Runs after the APIs (and Hilla, when present) because the compose stack must know whether a schema
  registry is needed.
* xref:skills/iru-setup-java-springboot-platform.adoc[] — Step 8: the OpenTofu configuration. When
  `deploy.rolling.enabled` is true it also receives `rolling: yes`, `deployment-strategy`, `advance`, `steps` and
  `bake-minutes` (alongside `mode`/`on-existing`) and generates the rollout infrastructure; `rolling: no` or nothing
  when disabled.
* xref:skills/iru-setup-java-springboot-github-workflows.adoc[] — Step 8: the build, deploy, undeploy and security
  workflows plus Dependabot, using Maven or `./gradlew` commands and Javadoc or Dokka per the manifest. When rolling
  deployments are enabled it generates a staged `deploy.yml` and the `promote.yml` workflow (receiving the same
  `rolling:`/`deployment-strategy:`/`advance:`/`steps:`/`bake-minutes:` lines). Reads `visibility`, `ci.tests` and `ci.pages` from the manifest. Skipped entirely when
  `ci.enabled: false`. Runs late because it surveys what is actually on disk.
* xref:skills/iru-update-java-springboot-documentation.adoc[] — Step 8, last: the Antora site and the service
  page set, derived from the finished codebase, with commands and samples matching the manifest's build tool and language.

Rolling deployments can be switched on or off after the bootstrap with xref:skills/iru-springboot-rolling-deployments.adoc[], which edits the manifest's
`deploy.rolling` block and re-runs the platform and workflows sub-skills.

In Step 9 it also invokes directly, if available, xref:skills/iru-setup-java-gitignore.adoc[],
xref:skills/iru-setup-readme.adoc[], and xref:skills/iru-setup-changelog.adoc[] for the repository-level files the
Spring Boot sub-skills don't own (forwarding `ci`, `pages` and `sonar` to the README skill, and `on-existing` when it
arrived via `args`). It additionally recommends — but does not invoke —
xref:skills/iru-check-license.adoc[] for license headers and xref:skills/iru-check-security.adoc[] for secret
scanning, the latter specifically if an LLM API token may ever have been committed.
