= React Native Code One Task Group
:description: Implements a bucket of React Native tasks for Expo or Metro apps, then validates once: Jest, coverage, tsc, native builds, Expo prebuild, and e2e.
:keywords: iru-react-native-code-one-task-group, claude code skill, react native, expo, metro, jest, e2e, maestro, detox, coverage

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Implement one bucket of React Native tasks from a plan's task group end to end: capture a single pre-change quality
baseline, run `iru-react-native-code-one-task` once per task (in parallel when allowed), then validate the entire
bucket once — headers, TSDoc, Jest, an 80% unit-only coverage gate, type-check, native stages, and a lock-guarded
device e2e run.

== Purpose

`iru-react-native-code-one-task-group` is built on the same TypeScript gate skills as
`iru-typescript-code-one-task-group`, each run through an `iru-gate-runner` agent so no raw report lands in its
context, and adds four React Native-specific concerns. Native code has its own gates and the toolchain decides who
owns it: for **metro** apps `android/` and `ios/` are committed source, so Step 3.7-3.8 build the side the bucket
touched; for **expo** apps they are generated, so an edit there is a defect and Step 3.9 validates config-plugin
changes by running `expo prebuild` in a throwaway copy. The coverage gate counts Jest unit tests only, since e2e
flows and native tests produce no coverage of the measured TypeScript. `tsc --noEmit` is its own gate, because Jest
presets strip types without checking them. The e2e stage needs a device, a build, and Metro, so it runs last and
only while holding the repository-wide `.integration-test.lock` (acquired in Step 3.10a, released in 3.10b on every
exit path; stale after 60 minutes, wait timeout around 45 minutes).

Step 1 detects the profile once and captures a baseline (plus an Android Lint baseline when metro tasks touch
`android/`). Step 2 implements tasks, but tasks that edit the same navigator/layout file or native registration point
run sequentially even in a parallelizable group. Step 3 runs license headers, TSDoc, scoped tests, coverage, the
full suite, quality diffed against baseline, the Android, iOS, and Expo native stages as applicable, then e2e. Steps
4-5 finalize the plan notes and report; any unverified stage is named with its reason rather than read as a pass.

== Outputs

* Source, native, and config files plus tests per task, via `iru-react-native-code-one-task`.
* License headers and TSDoc kept current for every file the bucket touched, checked once for the whole bucket.
* Unit-only coverage of at least 80% line and branch for changed/new TS/TSX files, with any device-only file recorded
  as an accepted exception.
* A type-check (`tsc --noEmit`), lint and format result compared to the single pre-change baseline.
* Android, iOS, and Expo native-config stage results where applicable, each passed, failed-and-fixed, skipped as not
  applicable, or unverified with a reason.
* An e2e (Maestro/Detox, optionally XCTest) result run under the shared lock, or unverified with the cause.
* `implementation_plan.md` with each task's checkbox finalized with unit-only coverage, native stages, and e2e
  results reported separately; blocked tasks stay unchecked with their blocker note.
* A report to the caller covering profile, per-task details, coverage exceptions, type-check results, native stages,
  e2e result, lock behavior, and which tasks need a new native build or are not OTA-compatible.
