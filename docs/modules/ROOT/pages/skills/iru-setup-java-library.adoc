Generate (or update) `pom.xml` at the repository root for a Java library from an explicit, genericized example
template, and scaffold the standard Maven source layout for the library's base package.

== Purpose

`iru-setup-java-library` bootstraps a new Java/Maven library's `pom.xml` from a house template embedded in the skill
itself — the same test dependencies (junit-jupiter, junit-platform-launcher, mockito-core,
mockito-junit-jupiter), the same `build-extras` profile, and the same build/reporting plugins, with only
the project-identity fields filled in per repository. Whether the repository is open source, whether it publishes
to Maven Central (gating the `sign` profile and the `central-publishing-maven-plugin`), and whether to wire up a
SonarQube/SonarCloud scan (gating the `sonar.*` properties and the `sonar-maven-plugin`) are also resolved — asked
interactively, deriving `publish`/`sonar` recommendations from the `open-source` answer (and, for Sonar, the
repository's `visibility`), or pre-supplied via `args`.

The skill announces whether it is creating `pom.xml` from scratch or updating an existing setup. If a `pom.xml`
already exists it warns, names any contradiction between the file and this run's answers, and asks Update (merge the
template in, keeping custom dependencies/plugins), Keep as is, Replace from the example, or Stop — unless
`on-existing` in `args` decides. Existing source folders are always left untouched.
It also creates the `src/main/java/<package>`, `src/main/resources/<package>`, and `src/test/java/<package>`
folders for the library's base package.

== Outputs

* `pom.xml` at the repository root: created fresh, updated in place (merging the template into the existing file,
  shown as a diff for approval before writing), replaced entirely, or left as is, depending on the Step 1 choice.
** Conditional blocks: the `sign` profile and the `central-publishing-maven-plugin` plugin entry are included only
   when `publish: yes` (the `build-extras` profile is always kept, regardless of `publish`); the four `sonar.*`
   properties and the `sonar-maven-plugin` plugin entry are included only when `sonar` is `cloud` or `self-hosted`,
   omitted entirely when `sonar: none`.
* `src/main/java/<package>`, `src/main/resources/<package>`, and `src/test/java/<package>` created if not
  already present (empty directories won't show up in `git status` until they contain a file).
* A report starting with whether the run created from scratch or updated, and the action on `pom.xml` (created,
  updated, replaced, kept as is, or stopped; user answer or `on-existing`), then the resolved groupId/artifactId/version, the license chosen (or "none"), the inferred repository
  information, and which source folders were created versus already present (existing ones reported as kept as is), each mismatch
  between a kept `pom.xml` and this run's values, a note that no CI step sends Sonar reports if `ci: no` with Sonar
  configured, plus an explicit statement of which
  conditional blocks were included versus omitted (`open-source`, `publish`, `sonar`) and why — plus an explicit
  warning to review the generated `pom.xml` before building or committing.
