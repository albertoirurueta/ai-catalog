= Setup PHP GitHub Workflows
:description: Creates or updates GitHub Actions CI, release, sync and security workflows for Laravel, WordPress plugin/theme and PrestaShop module repositories.
:keywords: iru-setup-php-github-workflows, claude code skill, github actions, php, laravel, wordpress, prestashop, composer, psalm, dependabot

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Scaffolds or updates the CI/CD and security pipeline for a PHP repository of one of four flavors — a Laravel
application, a WordPress plugin, a WordPress block theme, or a PrestaShop module — driving everything through the
composer scripts that the matching `iru-setup-php-*` scaffold defines.

== Purpose

`iru-setup-php-github-workflows` writes the GitHub Actions files a PHP repository needs, matched to its flavor and to
cost-aware choices made up front:

* `build.yml` — runs on pushes to the integration/stable branches, pull requests, and `workflow_dispatch`. It uses
  `shivammathur/setup-php` with PCOV, `composer validate --strict`, a cached `composer install`, `composer audit`,
  static analysis and coding style, and fast tests with Clover/JUnit coverage across a PHP matrix from the floor to
  the newest supported release. With `ci-tests: full` it adds an integration job per flavor: Laravel against a
  MySQL or PostgreSQL service container, WordPress inside the `@wordpress/env` test environment across a WordPress
  matrix, PrestaShop inside the Docker shop of `tests/Integration/docker-compose.yml`. Each integration job also runs
  the scaffold's Playwright browser UI tests (`npm run test:e2e`, guarded on a `playwright.config.*`) against the
  environment it already starts (Laravel's `php artisan serve`, `wp-env` on the latest-WordPress entry, the running
  PrestaShop shop) and uploads `.ui-screenshots/` as a 7-day artifact, with no extra job or runner. With
  `ci-tests: unit` the browser tests stay local behind `.integration-test.lock` (see
  xref:guides/building-user-interfaces.adoc[Building user interfaces]). It also adds an optional
  SonarCloud/SonarQube job (skipped on fork pull requests) and a docs job (Antora, plus phpDocumentor only when
  `phpdoc.dist.xml` exists) deployed to GitHub Pages or uploaded as an artifact.
* `release.yml` per `distribution` — a WordPress or PrestaShop zip attached to the GitHub Release (with `store`, also
  a WordPress.org deploy or manual PrestaShop Addons upload instructions), or a Laravel image pushed to GHCR. Not
  written with `distribution: none`.
* `sync.yml` plus `.github/scripts/php_version.py` and `.github/scripts/sync_versions.py` — after a release from the
  stable branch, a pull request merges it back into the integration branch with the next `x.(y+1).0-dev` version, the
  convention `iru-php-bump-version` and `iru-release` use.
* The shared security block — `security.yml` (dependency-review, CodeQL for `actions` and, when present, JS/TS,
  a Psalm taint-analysis SARIF upload as the PHP code-scanning substitute because CodeQL has no PHP support,
  OSV-Scanner, gitleaks) and `.github/dependabot.yml`.

It announces whether it is creating the pipeline from scratch or updating an existing one, and asks per workflow file
whether to Update, Keep as is, or Replace. Templates are validated with `actionlint`, and the commands the workflows
contain are run locally first, so nothing is a guess.

== Outputs

* `.github/workflows/build.yml` (with `ci-tests: full`, the integration jobs include the browser UI test steps and the
  `ui-screenshots-integration*` artifact uploads) (no accessibility reports when `.ui-quality.yml` says `accessibility: none`), and `release.yml` unless `distribution: none`.
* `.github/workflows/sync.yml` with `.github/scripts/php_version.py` and `.github/scripts/sync_versions.py`
  (made executable).
* `.github/workflows/security.yml`, `.github/psalm/` configuration, and `.github/dependabot.yml`.
* A report with the required secrets (`SONAR_TOKEN`, WordPress.org `SVN_USERNAME`/`SVN_PASSWORD`), repository
  settings to check, the choices made, per-unit created / updated / replaced / kept as is, and every open gap
  (missing composer scripts, no Antora setup, unverified integration jobs and browser UI test steps), including whether
  the integration jobs run the browser UI tests and upload `.ui-screenshots/`.

The generated files' bytes come from template files under `templates/` (and, where a template needs variant-specific notes, `reference/`) in `.claude/skills/iru-setup-php-github-workflows/`; the skill reads only the files for the variant it resolved, not the whole set, which keeps its `SKILL.md` small.
