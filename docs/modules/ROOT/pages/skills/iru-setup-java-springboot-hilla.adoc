= Setup Java Spring Boot Hilla
:description: Scaffolds a Hilla React frontend into a Spring Boot reactor's web module: Vaadin/Hilla poms, file-based-routing views, vitest, eslint and Sonar wiring.
:keywords: iru-setup-java-springboot-hilla, claude code skill, hilla, vaadin, vitest, eslint, prettier, react, maven, sonar

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Scaffolds a Hilla (Vaadin) React frontend into the module of a Spring Boot hexagonal reactor that runs the web
server: the Vaadin BOM and starter dependencies, the `vaadin-maven-plugin` build-frontend execution, a file-based
router with a sample view and test, a `vitest`/`@vitest/coverage-v8` toolchain, ESLint flat config plus Prettier,
the `.gitignore` additions the frontend needs, and — only when Sonar analysis is enabled — the `sonar.sources`/
`sonar.tests`/lcov properties on the root pom.

== Purpose

`iru-setup-java-springboot-hilla` fills in the one part of a Spring Boot reactor that `iru-setup-java-springboot-pom`
and `iru-setup-java-springboot-modules` don't cover on their own: an actual Hilla React frontend, wired end to end
and verified against a real build rather than assumed to work. Two findings behind it were confirmed empirically by
building and running a real Spring Boot 4 + Hilla project: `hilla-spring-boot-starter` alone does not build, because
the auto-generated Flow compatibility shim under `src/main/frontend/generated/flow/` always references a Flow
client resource that only `vaadin-spring-boot-starter` provides — both starters are always added, regardless of
whether hand-written Flow `@Route` views are wanted; and `routes.tsx`/`generated/file-routes.ts` are derived by
Hilla's file-based router on every `prepare-frontend`/`build-frontend` run, so this skill writes `views/@index.tsx`
and `views/@layout.tsx` only and never touches anything under `src/main/frontend/generated/`.

== Outputs

* `<web-module>/pom.xml` — `vaadin-spring-boot-starter`, `hilla-spring-boot-starter`, and optional `vaadin-dev`
  dependencies, plus the `vaadin-maven-plugin` execution (`prepare-frontend`, `build-frontend`).
* Root `pom.xml` — the `<vaadin.version>` property, `vaadin-bom` `dependencyManagement` import, `vaadin-maven-plugin`
  `pluginManagement` entry, and `production` profile, only when they aren't already there (normally owned by
  xref:skills/iru-setup-java-springboot-pom.adoc[]).
* `<web-module>/src/main/frontend/views/@index.tsx`, `views/@layout.tsx`, and `index.html` — never anything under
  `src/main/frontend/generated/`.
* `<web-module>/vitest.config.ts` (extending Vaadin's generated Vite config), `src/main/frontend/test/setup.ts`, and
  a colocated sample test `views/@index.test.tsx`.
* `<web-module>/package.json` `test`/`test:watch`/`coverage`/`lint`/`format` scripts and devDependencies (vitest,
  `@vitest/coverage-v8`, Testing Library, ESLint, Prettier and their plugins).
* `<web-module>/eslint.config.js` (flat config), `.prettierrc.json`, `.prettierignore`.
* `.gitignore` additions for `<web-module>/node_modules/`, `src/main/frontend/generated/`, and
  `vite.generated.ts` — shown as a diff and confirmed before writing.
* Root pom `sonar.sources`/`sonar.tests`/`sonar.test.inclusions`/`sonar.javascript.lcov.reportPaths` merged in, and
  `sonar.exclusions` extended with `**/frontend/generated/**`, only when `sonar.mode` isn't `none`.
* Optional example Flow `@Route` Java class and component starter, only if Step 1's Flow-views question was
  answered Yes.
