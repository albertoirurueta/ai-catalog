Scaffold a Quarkus service, or bring an existing one up to date, so the coding, gate and workflow skills of this
catalog find the layout, test levels, coverage engine and quality tools they expect.

== Purpose

`iru-setup-quarkus-service` is the interviewer and scaffolder for the service itself (not the Antora site,
`.gitignore`, workflows, changelog, README or license, which `iru-setup-quarkus-repository` chains). It announces
whether it is setting up from scratch or updating an existing Quarkus build, with an inventory of every artifact it
owns, and hard-stops for a non-Quarkus build (Spring Boot, Android, other JVM). It interviews once: identity, language
(Java or Kotlin), build tool (Maven or Gradle Kotlin DSL), layout (single module or DDD/hexagonal multi-module), Java
version (21 minimum), open source, visibility, CI, Sonar, CI test depth, Pages, distribution and every technology choice.

The platform version comes from the live code.quarkus.io streams API (falling back to registry.quarkus.io) and every
extension id is validated against the live catalogue, never a remembered list. After a confirmation step it writes a
`quarkus-stack.yml` manifest, scaffolds with `quarkus-maven-plugin:create` in a scratch directory, and post-processes to
catalog conventions: Kotlin all-open and no-arg plugins, the `quarkus-jacoco` plus JaCoCo setup with an 80% line check,
Checkstyle/PMD/SpotBugs/Javadoc or detekt/ktlint/Dokka, integration-test wiring, configuration profiles, Sonar, Jandex and
an ArchUnit test for hexagonal builds, and a sample feature tested at four levels. It then verifies the result builds,
passes unit and container stages, and clears quality gates. Each existing artifact gets an Update, Keep as is or Replace
choice.

== Outputs

* A `quarkus-stack.yml` manifest at the repository root.
* Build files, wrapper, `application.properties`, container files, quality and coverage configuration, and a sample
  feature with tests (only where no sources exist); a hexagonal module tree when chosen.
* A report: setup mode, per-component action (created, updated, replaced, kept as is), recorded pipeline choices, each
  verification gate's result, unverified items and open gaps.
