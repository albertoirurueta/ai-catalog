Run this project's TypeScript static-analysis and formatting tools — ESLint (flat config, plus Oxlint when it's
set up alongside ESLint), `tsc --noEmit` type-checking, Prettier `--check`, and Stylelint for CSS/SCSS when
configured — then report every issue found (file, line, rule id, message), grouped by tool and classified by rule
id. This is a read-only reporting skill: it runs the configured tools and reports results, it does not fix issues
unless asked to as an explicit follow-up.

== Purpose

`iru-typescript-code-quality` gives a single, framework-aware lint/type-check/format pass across the npm
ecosystem's fragmented tooling. It detects the project's framework (npm/TypeScript library, React, Angular, React
Native, Ionic, Hilla frontend) from `package.json` to pick the right invocation (e.g. `ng lint` vs a direct
`npx eslint`) and the right rule-id prefixes to classify against, verifies each tool's own config file actually
exists before trusting a "zero issues" result from it, and — unlike Java's Checkstyle/PMD/SpotBugs trio, which
always analyze the whole project — every tool here except `tsc` accepts a glob directly, so a scoped invocation
narrows what actually runs rather than just what gets reported.

== Outputs

* A plain-text summary in the conversation — never a written file.
* Findings grouped first by tool (ESLint, Oxlint, `tsc`, Prettier, Stylelint), then by rule id/diagnostic code
  within each tool.
* Per issue: file:line, rule id (or `TS<code>`), and message; Prettier findings are filed under a single
  `formatting` bucket since it has no rule ids.
* A total issue count per tool and an overall total; a tool whose config isn't found is reported as "not
  configured, skipped" rather than a misleading clean pass.
* When the prompt supplies a baseline (a prior per-rule-id count, e.g. from `iru-typescript-code-one-task-group`),
  only the new-vs-baseline regressions per rule id — not the full current list.
* No source, ESLint, `tsc`, Prettier, or Stylelint configuration is ever modified.
