= Android Code One Task Group
:description: Implements one bucket of Android/Kotlin tasks per Gradle module, then validates the whole group once for license headers, KDoc, tests, coverage, quality.
:keywords: iru-android-code-one-task-group, claude code skill, android, kotlin, gradle, jacoco, dokka, detekt, lint, code quality, implementation plan

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Implement one bucket of Android/Kotlin tasks from a plan's task group end to end: detect which Gradle module(s)
(`lib`/`app`) the bucket touches, capture a single pre-change quality baseline, run `iru-android-code-one-task`
once per task (in parallel when the group allows it), then validate the entire bucket once per touched module —
license headers, KDoc, scoped unit tests, an 80% unit-test line-coverage bar, a full-suite run, and a code-quality
regression check.

== Purpose

`iru-android-code-one-task-group` is the Gradle/Kotlin counterpart to `iru-java-code-one-task-group` and
`iru-typescript-code-one-task-group`: it consolidates per-task validation into a single pass per bucket, scoped
per Gradle module the bucket actually touched, since an Android repository may span both a `lib` and an `app`
module. It captures one pre-change quality baseline covering every class the bucket's tasks are expected to
touch, then implements each task via `iru-android-code-one-task` (concurrently, in a single batch of `Agent`
calls routed through `iru-isolated-skill-executor`, when the plan marks the group `Parallelizable: yes`; one at a
time otherwise). `iru-android-code-one-task` itself checks off each task's box in `implementation_plan.md` the
moment that task finishes cleanly, with a "group validation pending" note — this skill just re-reads the file as
each task's agent reports back to confirm the box landed, backfilling it only if a rare concurrent-write race
clobbered it, and notifies the user that implementation landed. Once every non-blocked task has landed, it
validates the whole bucket in one pass, per touched module: license headers, KDoc (via `iru-android-dokka`), the
affected unit-test classes, unit-test line coverage against an 80% bar (instrumented coverage is reported for
information only and never counted toward it), a full `./gradlew test` run, and a quality-regression check
against its one baseline. A failure traced to a specific task sends that task back for a fix and a re-run of the
affected checks, rather than re-validating the whole bucket.

== Outputs

* Source and test files created/modified per task, via `iru-android-code-one-task`, scoped to the `lib` and/or
  `app` module each task touches.
* License headers and KDoc kept current across every file/class the bucket touched, checked once for the whole
  bucket rather than once per task.
* Unit tests achieving at least 80% line coverage (unit-test only) for the bucket's changed/new classes, per
  module, verified against the real JaCoCo/Kover report; any already-on-disk instrumented coverage is reported
  for information only.
* `implementation_plan.md` with each task's (and sub-task's) checkbox checked and a progress note — first an
  "implemented, group validation pending" note written by `iru-android-code-one-task` itself as each task lands
  (backfilled here only if a rare concurrent-write race dropped it), then replaced with the final coverage/quality
  outcome once bucket-wide validation passes.
* User-facing notifications at both phases: per task as its implementation lands, and once when group validation
  completes.
* A summary handed back to the caller (`iru-code-one-task-group`): per task, its module, files touched, tests
  added/updated, unit-test coverage achieved, code-quality outcome, which of `./gradlew test`/`testDebugUnitTest`
  actually ran, and any task that stopped on a blocker.

== Dependencies

=== Invokes

* xref:skills/iru-android-code-one-task.adoc[] — Step 2, once per task in the bucket (concurrently or
  sequentially per the group's `Parallelizable` verdict), via the
  xref:agents/iru-isolated-skill-executor.adoc[`iru-isolated-skill-executor`] agent — that skill implements
  exactly what the task specifies, writes/updates its tests, and checks off its own checkbox in
  `implementation_plan.md` with a "group validation pending" note before reporting back.

Each of the following is invoked via the xref:agents/iru-gate-runner.adoc[`iru-gate-runner`] agent rather than
directly, so verbose report output stays out of this skill's own context:

* xref:skills/iru-android-code-quality.adoc[] — Step 1 (pre-change baseline for the bucket) and Step 3.6 (final
  regression check against that baseline), scoped per touched module.
* xref:skills/iru-check-license.adoc[] — Step 3.1, license headers for every file the bucket touched.
* xref:skills/iru-android-dokka.adoc[] — Step 3.2, KDoc for every class the bucket touched.
* xref:skills/iru-android-test.adoc[] — Step 3.3, scoped unit tests for every class the bucket affected, per
  touched module.
* xref:skills/iru-android-coverage.adoc[] — Step 3.4, unit-test line/branch coverage for every changed/new class,
  per touched module.
* Step 3.5 runs the plan's literal `./gradlew test` (or `testDebugUnitTest` as a lighter-weight substitute)
  directly for full-suite regression coverage — not a catalog skill.
