= .NET Generate All Tests
:description: Scans a .NET codebase for classes lacking tests or below 80% coverage, writes unit tests to clear the bar, and adds UI tests for screens that have none.
:keywords: iru-dotnet-generate-all-tests, claude code skill, dotnet, csharp, unit testing, windows desktop, code coverage, ui tests, flaui, generate tests

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Bring an entire .NET/C# codebase's unit test coverage up to a minimum bar — 80% line coverage — in one pass:
find every class with no test class at all or with measured coverage below the bar, then write or extend tests
for each until it clears it. .NET/C# only; it does not run against, or fall back to, any other language.

== Purpose

`iru-dotnet-generate-all-tests` answers "bring this whole codebase's test coverage up to a bar" rather than "write
tests for this one class/task," which is what `iru-dotnet-code-one-task` and the `iru-code` pipeline already handle
per task. It explores the whole codebase to build an inventory of testable classes, delegates to
`iru-dotnet-coverage` for the exact, measured percentage per class (never an estimate), and only writes or extends
test code — it does not add license headers, doc comments, or run a code-quality pass, and it only touches
production source code when a class is genuinely untestable as written (e.g. no seam to substitute a hard
dependency), which it reports explicitly rather than silently redesigning the class.

With several `.sln`/`.slnx` files and no obvious target it asks which to use. For a Windows desktop app repository
(a `WinExe` project with `UseWPF`/`UseWinUI`/`UseWindowsForms`; plan key `windows`) the skill applies only to the
UI-free Core project (`src/<App>.Core`) and its portable test project (`tests/<App>.Core.Tests`): classes in the app
project (windows, pages, forms, code-behind, converters) are listed as "excluded — UI layer, not measured" in the
final report rather than given tests that need a UI thread, logic found there is named as a candidate to move into
Core. The coverage pass never writes UI-thread unit tests for them; instead, when the repository already has a UI-test
project, Step 7b generates UI tests for the screens and components that have none (see below).

Step 7b follows the catalog's UI contract (see xref:guides/building-user-interfaces.adoc[Building user interfaces]): when
the repository already has a UI-test project -- FlaUI `tests/<App>.UITests` for a Windows desktop app, or Terminal.Gui
view tests for a command-line tool with a `ui: tui` terminal UI -- it inventories every screen and component, finds
those with no UI test, and has one sub-agent per screen/component write one. Each test captures every visual state ×
the `.ui-quality.yml` directions × themes into `.ui-screenshots/` (terminal captures are `.txt`) and runs the
accessibility check (Axe.Windows on the desktop, the asserted `tui-*` checks in a terminal UI). A repository with no
UI-test project is reported "no UI-test project -- UI tests not generated"; this skill never scaffolds one.

== Inputs

None — no arguments are accepted. It always scopes to the whole repository's .NET solution(s)/project(s).

== Outputs

* New or extended test files for every class found with no matching test class, or with line coverage below
  80% — following this project's own existing test framework (xUnit/NUnit/MSTest), mocking library, and
  naming/folder convention.
* Occasionally, a minimal testability change to a class under test (e.g. extracting an interface, injecting a
  dependency) — only when a class is genuinely untestable as written, and always called out explicitly rather
  than folded silently into "tests added."
* A report: total candidate classes found (and any excluded as having no testable logic), how many already met
  the bar, before/after coverage per class touched, any class still below 80% after two extension attempts
  (with its exact remaining uncovered lines), and the full-suite test result.
* For a repository with a UI-test project (Step 7b): new UI test classes for every screen and component that lacked
  one, the `.ui-screenshots/` captures they write, and a report of the screens/components inventoried, those newly
  covered (states covered), the `ui` run result (or "unverified (needs Windows)"), screenshot counts per kind,
  malformed names, the `.ui-quality.yml` accessibility level (`none` reported as "accessibility: opted out", `off` as "accessibility checks off") with its violations (count + rule ids), and any view
  changed only to add an automation id.
* No license headers, doc comments, or code-quality fixes — those remain `iru-check-license`, `iru-dotnet-docfx`, and
  `iru-dotnet-code-quality`'s jobs.

== Dependencies

=== Invokes

* xref:skills/iru-dotnet-coverage.adoc[] — Step 3, and again in Step 6 to re-measure after generation: delegated
  through the `iru-gate-runner` agent so its full `coverage.cobertura.xml`-derived report never lands directly in
  this conversation, and so the whole suite runs once per batch rather than once per class.
* xref:skills/iru-dotnet-test.adoc[] — Step 7, once, to confirm the full suite still passes after every class's
  tests have been written or extended; also delegated through `iru-gate-runner`. Step 7b runs it again with the `ui`
  selector for the newly generated UI tests (Windows-only for desktop apps, otherwise unverified; any host for
  terminal UI tests).

=== Invoked by

None — meant to be run directly by a person who wants coverage brought up across the whole codebase in one
pass, independent of the `/iru-code`/`/iru-issue` pipeline (which handles per-task test-writing via
`iru-dotnet-code-one-task`).
