= Setup Repository
:description: Catalog-wide bootstrap front door: announces new vs existing setup, asks cost-aware shared inputs, and delegates to one of five stack orchestrators.
:keywords: iru-setup-repository, claude code skill, bootstrap, project type detection, java, typescript, android, swift, orchestrator, askuserquestion

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

The catalog's single entry point for bootstrapping any repository. It does not scaffold anything itself — it
detects or asks which of twelve supported project types applies, announces whether the run is a from-scratch setup
or an update of an existing repository, collects the handful of questions genuinely shared across every stack, and
hands off to exactly one of five existing stack orchestrators.

== Purpose

`iru-setup-repository` exists so a user doesn't need to already know which of this catalog's stack-specific
orchestrators (`iru-setup-java-library-repository`, `iru-setup-java-springboot`,
`iru-setup-typescript-repository`, `iru-setup-android-repository`, `iru-setup-swift-repository`) applies to their
repository. It surveys the working directory (running `iru-explore` when it already holds code) to detect the
project type, asks only the cross-cutting questions the detected/chosen type still needs, and delegates the
actual scaffolding — the downstream orchestrator asks its own project-identity questions and does the real work.
Run against a repository that already has code, it forces `mode: existing` and prints an inventory of every
component the pipeline owns (build manifest, source layout, Antora docs, `.gitignore`, each CI workflow,
Dependabot, Sonar config, changelog, README, license) marked absent / present / partial. `mode: existing` no longer
means "update silently": every delegated component warns about each pre-existing artifact it finds and asks
whether to keep, update, or replace it (this front door never asks that on their behalf), unless `on-existing`
pre-answers it for scripted runs.

The shared questions are visibility-aware and cost-aware, stated per GitHub's current pricing (the user should
double-check their plan): standard Actions runners are free for public repositories while private/internal ones
consume included minutes (2,000/month on Free, 3,000 on Pro/Team, 50,000 on Enterprise Cloud), macOS minutes cost
roughly 10x Linux, SonarCloud is free only for public/open-source projects, and GitHub Pages on a private
repository needs Pro/Team/Enterprise Cloud and is publicly reachable unless private access control is used.

== Invocation

[source]
----
/iru-setup-repository
----

Optionally followed by an `args` block of `key: value` lines, e.g.:

[source]
----
/iru-setup-repository
project-type: android-app
mode: new
open-source: yes
visibility: public
ci: yes
ci-tests: full
pages: yes
distribution: store
sonar: cloud
----

== Outputs

* No files are written directly by this skill — every artifact (source scaffold, Antora docs, `.gitignore`,
  CI workflows, `CHANGELOG.md`, `README.md`) is produced by whichever single stack orchestrator Step 4 delegates
  to, exactly as that orchestrator's own page describes.
* An up-front announcement (Step 1): "from scratch" or "updating an existing repository", the latter with the
  absent / present / partial component inventory.
* A final report (Step 5): the resolved `project-type`, the setup mode and where it came from, and every shared
  input as actually applied (`visibility` and how it was resolved, `ci`, `ci-tests`, `pages`, and so on); a
  per-component table of what the delegated orchestrator did (created / updated / replaced / kept as is / skipped
  (`ci: no`)) with every mismatch it flagged between a kept file and this run's choices; cost notes tied to the
  visibility; a `ci: no` note when workflows and the security block were skipped; any key that could not be
  forwarded; one consolidated secrets/environments table; and an explicit warning block (review every generated
  file; every listed secret and matching external account must already exist; which values were inferred rather
  than asked).
* When the detected or chosen type is `dotnet`/`other`/unsupported: a plain report that no bootstrap orchestrator
  exists in this catalog for it, with no delegation attempted.

== Dependencies

=== Invokes

* xref:skills/iru-explore.adoc[] — Step 1, directly (not via a sub-agent), and only when the working directory is
  non-empty: reads its `## Tech stack` report's `- Project type:` line to pre-select Step 2's option and set
  `mode: existing`.
* Exactly one of the following five, via the xref:agents/iru-isolated-skill-executor.adoc[`iru-isolated-skill-executor`]
  agent in Step 4, chosen by the resolved `project-type` — never more than one per run outside the `multiple`
  case:
** xref:skills/iru-setup-java-library-repository.adoc[] — for `java-library`.
** xref:skills/iru-setup-java-springboot.adoc[] — for `java-springboot` / `java-springboot-hilla` (via its own
   `frontend` arg).
** xref:skills/iru-setup-typescript-repository.adoc[] — for `typescript-library`, `react-web`, `angular-web`,
   `react-native-app`, `ionic-app` (via its own `flavor` arg).
** xref:skills/iru-setup-android-repository.adoc[] — for `android-library`, `android-app` (via its own `flavor`
   arg).
** xref:skills/iru-setup-swift-repository.adoc[] — for `swift-library`, `apple-app` (via its own `flavor` arg).
