= Rust Code One Task Group
:description: Implements a bucket of Rust tasks, then validates it once for license headers, rustdoc, tests, 80% coverage and clippy, serializing container tests.
:keywords: iru-rust-code-one-task-group, claude code skill, rust, cargo, clippy, cargo-llvm-cov, testcontainers lock, validate task group, code coverage

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Implement one bucket of Rust tasks from a plan's task group end to end: capture a single pre-change quality
baseline, run `iru-rust-code-one-task` once per task (in parallel when the group allows it), then validate the whole
bucket once — license headers, rustdoc, scoped tests, 80% line coverage, the full suite, and a clippy/rustfmt/cargo-deny
regression check — with any container-backed tests serialized behind a repository-wide lock.

== Purpose

`iru-rust-code-one-task-group` is the Cargo package/workspace counterpart to the other `<key>-code-one-task-group`
skills (notably `iru-go-code-one-task-group` and `iru-windows-code-one-task-group`), built on
`iru-rust-code-quality`, `iru-rust-test`, `iru-rust-coverage` and `iru-rust-rustdoc`. It detects the shape once —
workspace members and lib/bin targets, features, the CLI contract, end-to-end test files, golden/snapshot files,
`#[ignore]`d container-backed tests, an `xtask` docs generator, and the wired quality tools — and captures one
pre-change quality baseline for every file the bucket is expected to touch.

It then implements each task via `iru-rust-code-one-task`, concurrently through `iru-isolated-skill-executor` agents
when the plan marks the group `Parallelizable: yes`. Tasks that share `src/cli.rs`, the dispatch or `mod` declarations
in `lib.rs`, the exit-code/output modules, `Cargo.toml`/`Cargo.lock`, or a golden file always run sequentially,
whatever the verdict. Each task checks off its own box with a "group validation pending" note; this skill confirms or
backfills it and notifies the user.

Validation runs once, cheapest first, every check through an `iru-gate-runner` agent: license headers, rustdoc (plus
regenerating committed CLI docs through the crate's `xtask` when the command tree changed), scoped tests, an 80%
per-file line-coverage gate (cargo-llvm-cov, container-free tests only, end-to-end runs of the binary included — the
test helper must forward `LLVM_PROFILE_FILE` after `env_clear()` or `main.rs` reads 0%), the full suite with doctests,
and clippy/rustfmt/cargo-deny diffed against the baseline. When the bucket added or changed terminal-UI screens or
components (Ratatui), a UI stage (3.5a) also checks that each has `.txt` captures in `.ui-screenshots/` for every state
× `.ui-quality.yml` direction × theme, and applies the accessibility level (`enforce` fails the bucket, `report` lists
the rule ids); see xref:guides/building-user-interfaces.adoc[Building user interfaces]. Last, and only when the repository has them, `#[ignore]`d
container-backed tests (testcontainers) run behind the shared atomic-`mkdir` `.integration-test.lock`; Docker being
unavailable makes that stage "unverified", never silently skipped. Plain CLI end-to-end tests need no lock. With `accessibility: none` in `.ui-quality.yml` (opted out entirely), the accessibility rules and checks are neither applied nor required and are reported as "accessibility: opted out" in the group report, never unverified or failed; `off` still applies the rules but skips the automated checks. When `.ui-quality.yml` is missing in a repository that already has UI code, it doesn't assume `enforce`: before the first UI task it asks once, pre-selected from `iru-explore`'s `Accessibility:` line, and writes the file.

== Outputs

* Source, test, golden/snapshot files created or modified per task, via `iru-rust-code-one-task`.
* License headers and rustdoc kept current across every `.rs` file the bucket touched, checked once for the bucket;
  committed generated CLI docs regenerated through `xtask` when the command tree changed.
* Tests reaching at least 80% line coverage on every changed or added production source file (accepted exceptions —
  `xtask`/`build.rs`, a truly thin `main.rs`, terminal-bound lines — are named, never silent).
* For terminal-UI work: captures under `.ui-screenshots/<kind>/<Id>/<state>--<direction>--<theme>.txt`, malformed names
  fixed, and the accessibility result at the `.ui-quality.yml` level (the asserted TUI checks, not an automated audit).
* A transient `.integration-test.lock/` directory (with an `owner` file) held only while the container-backed stage
  runs, added to the root `.gitignore` if missing, and always released before the skill finishes.
* `implementation_plan.md` with each task's checkbox checked and its "group validation pending" note replaced by the
  final coverage, quality and container-test outcome.
* User-facing notifications per task as it lands and once when group validation completes.
* A summary handed back to `iru-code-one-task-group`: shape detected, per-task files/tests/coverage/quality, coverage
  exceptions, generated-docs result, the container-backed result (passed, fixed, unverified with reason, or none),
  lock behavior, and any task that stopped on a blocker.

== Dependencies

=== Invokes

* xref:skills/iru-rust-code-one-task.adoc[] — Step 2, once per task in the bucket, via the
  xref:agents/iru-isolated-skill-executor.adoc[`iru-isolated-skill-executor`] agent when the bucket is parallelizable
  (all tasks at once) or directly, one at a time, otherwise — that skill implements exactly what the task specifies,
  writes its tests, formats its own files, compile-checks, and checks off its own checkbox with a "group validation
  pending" note.

Each of the following is invoked via the xref:agents/iru-gate-runner.adoc[`iru-gate-runner`] agent rather than
directly, so verbose report output stays out of this skill's own context:

* xref:skills/iru-rust-code-quality.adoc[] — Step 1 (pre-change baseline) and Step 3.6 (clippy, rustfmt and cargo-deny
  regression check against that baseline).
* xref:skills/iru-check-license.adoc[] — Step 3.1, license headers for every `.rs` file the bucket touched.
* xref:skills/iru-rust-rustdoc.adoc[] — Step 3.2, rustdoc for every item the bucket touched, with `cargo doc` and
  doctests passing.
* xref:skills/iru-rust-test.adoc[] — Step 3.3 (scoped tests), Step 3.5 (full suite with doctests, plus `ui: yes` and the
  UI-capture summary when the project has a terminal UI) and Step 3.7
  (`ignored: only` container-backed tests with `lock: held`).
* xref:skills/iru-rust-coverage.adoc[] — Step 3.4, per-file line coverage (cargo-llvm-cov) for every changed or added
  production source file.

The regeneration of committed CLI docs through the crate's `xtask` (Step 3.2) is run directly by `iru-gate-runner`
rather than through a named skill, so it has no dedicated skill xref.
