= Release
:description: Cuts a release branch from develop, delegates the version bump to the ecosystem's bump-version skill, drafts notes, and opens a pull request.
:keywords: iru-release, claude code skill, gitflow, java, typescript, android, swift, changelog, release notes, version bump, pull request, github, bitbucket, azure devops, tfs

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Convert the current development version into a final release: cut a `release_x.y.z` branch off `develop`,
update every place that names the current release/pre-release version, draft the "what's new" notes, and open a
pull request. This mirrors the repository's existing release history (`release_1.0.0` … `release_1.3.0`, each a
PR into `main`) — it follows that gitflow convention rather than inventing its own.

== Purpose

`iru-release` automates the mechanical parts of cutting a release so nothing gets missed or drifts out of sync,
and it is ecosystem-agnostic: it detects whether the repository is Java/Maven, TypeScript/npm, Android/Gradle, or
Swift/Apple, and delegates the actual version-file edit to that ecosystem's own installed `iru-<key>-bump-version`
skill (`iru-java-bump-version`, `iru-typescript-bump-version`, `iru-android-bump-version`, `iru-swift-bump-version`)
rather than editing build files directly. It still owns every other release step itself: the human-readable release
notes (`whats-new.adoc` and `CHANGELOG.md`), and the pull request — opened against whichever host the repository
actually uses (GitHub, Bitbucket, Azure DevOps, or TFS) — that carries the release branch into `main`/`master`. It
is strict about gitflow — it refuses to run from anywhere but `develop` — so the release branch always originates
from the same integration branch this repository's history already shows it does.

== Outputs

* A pushed `release_<version>` branch, branched from `develop`.
* The version file(s) for the detected ecosystem bumped to the release version by the matching
  `iru-<key>-bump-version` skill (called with `sync-files: yes`), which also refreshes `README.md`,
  `docs/antora.yml`, and any Antora page with a dependency snippet to show the release version as "latest release".
  If no matching bump-version skill is installed, this happens by hand instead and the final report says so.
* `docs/modules/ROOT/pages/whats-new.adoc` with a new, newest-first section for the release, and `CHANGELOG.md`
  with `## [Unreleased]` renamed to the release's dated section (Keep a Changelog format) and a fresh empty
  `## [Unreleased]` above it.
* A commit on the release branch, and a pull request opened against `main`/`master` — using whichever host tooling
  matches this repository (GitHub, Bitbucket, Azure DevOps, or TFS) — titled `Release <version>`, carrying a
  `release` label/tag where the host supports one, and a description filled in from the actual diff.
* A final report naming the detected ecosystem and bump-version skill used, the versions chosen, the branch/PR
  and host, the files touched, and — whenever this repository has a `.github/workflows/sync.yml` (every
  `iru-setup-<stack>-github-workflows` skill generates one, whatever the ecosystem) — a reminder that merging and
  publishing the release triggers that workflow's automatic next-development-version bump back into `develop`;
  otherwise a plain statement that no such automation ran and the next-dev bump is a manual follow-up.
* If run from any branch other than `develop`: no files are touched at all — the skill stops at Step 1.

== Dependencies

=== Invokes

* xref:skills/iru-java-bump-version.adoc[], xref:skills/iru-typescript-bump-version.adoc[],
  xref:skills/iru-android-bump-version.adoc[], xref:skills/iru-swift-bump-version.adoc[] — Step 6, whichever one
  matches the ecosystem detected in Step 2 (Java/Maven, TypeScript/npm, Android/Gradle, or Swift/Apple). The
  installed candidates are discovered with `find .claude/skills -maxdepth 1 -type d -name "iru-*-bump-version"`
  rather than assumed, and the matching one is invoked with `sync-files: yes` so it also refreshes
  `README.md`/`docs/antora.yml`/Antora dependency-snippet pages itself — `iru-release` no longer does that work
  directly. If no matching skill is installed, `iru-release` falls back to bumping the version file(s) by hand and
  says so in the final report.
* xref:skills/iru-pr-description.adoc[] — Step 11, passing the release PR's target branch as a `base-branch`
  argument so the description is drafted against the branch the PR actually targets, to draft and fill in the
  release pull request's description once it has been opened in Step 10.

`iru-release` does *not* invoke xref:skills/iru-setup-changelog.adoc[] even though both skills touch `CHANGELOG.md`.
`iru-setup-changelog` is a one-time bootstrap for a repository that has no changelog yet; `iru-release` composes and
edits `CHANGELOG.md` directly itself on every run (Step 7), since by the time a repository is cutting releases
the changelog already exists and just needs its `[Unreleased]` section turned into a dated release entry.

=== Invoked by

None — `iru-release` is a top-level entry point, run directly by a person via `/iru-release`.

=== Related agents

* xref:agents/iru-change-summarizer.adoc[`iru-change-summarizer`] — Step 7, to summarize the commit/diff range since
  the previous release into user-facing changes for `whats-new.adoc`/`CHANGELOG.md`, keeping the raw `git log`/diff
  content out of this skill's own context — the same agent `iru-setup-changelog` uses, applied here to a single
  range instead of a fan-out across many past releases.
