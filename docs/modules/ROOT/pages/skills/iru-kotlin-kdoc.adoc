= Kotlin KDoc
:description: Audits Kotlin classes, files or packages for complete KDoc, fills the gaps, wires Dokka module docs, and confirms the Dokka build passes.
:keywords: iru-kotlin-kdoc, claude code skill, kotlin, kdoc, dokka, documentation audit, spring boot, quarkus, gradle, maven

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Make sure a set of Kotlin declarations, and the modules and packages they live in, carry complete, well-formed
KDoc, filling in whatever is missing, then prove the result builds through the project's own Dokka tooling. It only
adds or completes documentation comments and Dokka include files — never behavior, signatures or non-KDoc code.

== Purpose

`iru-kotlin-kdoc` covers JVM Kotlin projects — plain libraries, Kotlin Spring Boot and Kotlin Quarkus — on Gradle
(`org.jetbrains.dokka`, Dokka 2 or Dokka 1) or Maven (`dokka-maven-plugin`). It discovers the project's own
documentation bar (detekt `comments` rules, Dokka `documentedVisibilities` and `reportUndocumented`, contributor
guides, observed practice) instead of assuming a fixed style, audits every in-scope declaration, then writes the
missing KDoc grounded in the real implementation: `@property` for constructor-declared properties, `@param`,
`@constructor`, `@return`, `@throws`, plus framework-aware treatment of Spring beans, `@ConfigurationProperties`,
Quarkus CDI beans, `@ConfigMapping`, JAX-RS resources and JPA/Panache entities. It also ensures a `module.md` with
`# Module` and `# Package` sections is wired into Dokka for every touched module and package. A clean Dokka run
does not prove completeness, so the audit remains the completeness gate. Test sources, Java files (use
`iru-java-javadoc`) and Android modules (use `iru-android-dokka`) and Kotlin Multiplatform modules (use xref:skills/iru-kmp-dokka.adoc[]) are out of scope.

== Outputs

* Edited `.kt` files with added or completed KDoc comments (no code, signature or annotation changes).
* A created or extended `module.md` (`# Module` and `# Package` sections) per touched module, and the Dokka
  `includes` wiring added when absent — the only build-file edit the skill makes.
* A Dokka build result per module (Dokka version and mode, task used, output location, in-scope warnings fixed).
* A report: declarations already documented, gaps found and filled, `@suppress`-excluded members, module/package
  coverage status, arguments dropped, and out-of-scope pre-existing Dokka warnings as follow-ups.
