= TypeScript Bump Version
:description: Sets an npm/TypeScript project's version to an exact value, updating package.json and syncing the npm, pnpm, or yarn lockfile in place.
:keywords: iru-typescript-bump-version, claude code skill, typescript, npm, pnpm, yarn, package.json, semver, bump version, sync lockfile

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Set an npm/TypeScript project's version to an exact literal value across every file that needs to agree with
it: `package.json`, the lockfile of whichever package manager the project uses, and — optionally — any
README/Antora mentions of the current version. This skill never computes a version itself; it only applies
the exact string it is given, after checking that the string looks like an attempted version at all.

== Purpose

`iru-typescript-bump-version` is the npm-ecosystem equivalent of a Java `pom.xml` version bump: a small,
deterministic skill that a caller (typically `iru-release`) can invoke twice per release — once to strip the
pre-release suffix for the release itself, once to open the next development cycle — without either caller
having to know npm/pnpm/yarn's differing version commands or lockfile quirks. It detects the package manager
in play, finds the right `package.json` (asking when a workspace or a Hilla-managed frontend makes that
ambiguous), and runs that package manager's own `version` command so the lockfile stays consistent.

== Inputs

[cols="1,1,3,2", options="header"]
|===
|Argument |Required |Description |Default

|`new-version`
|Yes
|The exact target version string (e.g. `1.4.0`, `2.0.0-dev.3`). Validated for shape by the package manager's
own `version` command rather than a separate regex; an empty or whitespace-containing value is rejected
up front.
|None — the skill asks for it if omitted.

|`package` (args)
|No
|Which workspace package to bump, by name or path, when more than one `package.json` with a `version` field
exists.
|None — the skill asks which package (or whether to bump every workspace member in lockstep) when the
repository has more than one and this isn't given.

|`sync-files` (args)
|No
|Whether to also update README/Antora mentions of the version (installation snippets, a "Current version"
line, `docs/antora.yml`'s `version:` field for released versions only).
|Ask — the skill asks once, after checking whether such mentions actually exist, skipping the question if
none do.
|===

== Outputs

* `package.json` updated to the new version.
* The package manager's lockfile updated to match, where that package manager's `version` command touches
  one: npm's `package-lock.json` is updated together with `package.json`; pnpm's `pnpm-lock.yaml` and yarn's
  `yarn.lock` do not embed a root version and need no lockfile change (a stray `package-lock.json` found in a
  pnpm project is flagged instead).
* Optionally, `README.md`, `docs/antora.yml`, and/or Antora pages with a literal dependency/version snippet,
  if `sync-files` was accepted.
* A report of the old and new version, every file actually changed, anything skipped and why, and which parts
  of the process were verified locally (npm, pnpm) versus not (Yarn Classic/Berry) and should be spot-checked.
* No commit or git tag is created — this skill only edits files.
