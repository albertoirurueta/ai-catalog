= Python Docstrings
:description: Audits Python code for complete PEP 257 docstrings, fills the gaps in the project's convention, and verifies with Ruff, interrogate and an API-docs build.
:keywords: iru-python-docstrings, claude code skill, python, docstrings, pep 257, ruff, sphinx, fastapi, django, interrogate

NOTE: This documentation was generated with the assistance of AI. Please report any inaccuracies.

Make sure a set of Python modules carry complete, well-formed docstrings, filling in whatever is missing, then prove
the result is valid through Ruff's docstring rules and the project's own API-docs build. It only adds or completes
docstrings — it never changes behavior, signatures, type hints, decorators or any non-docstring code.

== Purpose

`iru-python-docstrings` detects the project flavor (Django, FastAPI or plain library) and the runner (`uv run`,
`poetry run`, `pdm run`, `pipenv run`, `.venv/bin/`), then discovers the project's real docstring bar: the Ruff
pydocstyle convention (Google by default, or numpy, pep257 or reST when the project says so), Ruff `D` selection and
ignores, `interrogate` settings, the API-docs tool and contributor guides. It audits every public module, package,
class, function, method and property, generates docstrings grounded in the actual code and current changes without
restating what type hints already say, and verifies the result with Ruff `D` rules (forced on even when the project
does not enable them), the advisory preview pydoclint `DOC` rules, `interrogate` when configured, and a Sphinx,
MkDocs plus mkdocstrings or pdoc build with warnings as errors into a throwaway directory.

It is framework-aware: Django migrations are never touched, FastAPI route and Pydantic model docstrings become
OpenAPI descriptions so developer-only sections go after a form feed (handling the resulting Ruff `D301`), and
DRF or Django Ninja view docstrings feed their schema the same way. Test code is out of scope and its existing
docstrings are never stripped.

== Outputs

* Edited `.py` files with added or completed docstrings, plus an API-docs entry (for example an `automodule`
  directive) when the project lists modules explicitly and a new public module was listed nowhere.
* A per-file report: symbols already documented, gaps found and filled (kind and what was added), and any API-docs
  entry added.
* The verification result per tool that ran — Ruff `D`, Ruff `DOC` (advisory), interrogate coverage against
  `fail-under`, and the Sphinx, MkDocs or pdoc build — and which tools were unavailable or not configured.
* The convention used and where it came from, arguments dropped as tests or migrations, and out-of-scope
  pre-existing failures as follow-ups. Raw tool output is never pasted.
