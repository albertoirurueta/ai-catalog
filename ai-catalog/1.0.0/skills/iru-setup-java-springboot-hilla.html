Setup Java Spring Boot Hilla

This documentation was generated with the assistance of AI. Please report any inaccuracies.

Scaffolds a Hilla (Vaadin) React frontend into the module of a Spring Boot hexagonal reactor that runs the web server: the Vaadin BOM and starter dependencies, the vaadin-maven-plugin build-frontend execution, a file-based router with a sample view and test, a vitest/@vitest/coverage-v8 toolchain, ESLint flat config plus Prettier, a Playwright component-testing setup and a root .ui-quality.yml (the catalog’s UI contract), the .gitignore additions the frontend needs, and — only when Sonar analysis is enabled — the sonar.sources/ sonar.tests/lcov properties on the root pom (Gradle: the boot project’s sonar {} block). It reads the manifest’s project.language (java/kotlin) and project.buildTool (maven/gradle) and adapts the build wiring accordingly; the frontend files are identical in every combination.

Purpose

iru-setup-java-springboot-hilla fills in the one part of a Spring Boot reactor that iru-setup-java-springboot-pom and iru-setup-java-springboot-modules don’t cover on their own: an actual Hilla React frontend, wired end to end and verified against a real build rather than assumed to work. Two findings behind it were confirmed empirically by building and running a real Spring Boot 4 + Hilla project: hilla-spring-boot-starter alone does not build, because the auto-generated Flow compatibility shim under src/main/frontend/generated/flow/ always references a Flow client resource that only vaadin-spring-boot-starter provides — both starters are always added, regardless of whether hand-written Flow @Route views are wanted; and routes.tsx/generated/file-routes.ts are derived by Hilla’s file-based router on every prepare-frontend/build-frontend run, so this skill writes views/@index.tsx and views/@layout.tsx only and never touches anything under src/main/frontend/generated/.

Kotlin and Gradle. project.language (absent means java) and project.buildTool (absent means maven; gradle only with kotlin) change only the build wiring and the server-side service code, never the frontend files. On Maven the pom fragment is unchanged for Kotlin (vaadin-maven-plugin runs after kotlin-maven-plugin). On Gradle the com.vaadin plugin is applied to the :boot project, with the Vaadin BOM (also added to developmentOnly), starters and plugin alias resolved from gradle/libs.versions.toml, and vaadinPrepareFrontend run explicitly because it is not part of the build graph. Kotlin @BrowserCallable services rely on Kotlin’s own nullability (String required, String? optional) — no @Nonnull/JSpecify annotations are added. A manifest pairing gradle with java is a stop.

The skill announces whether it is scaffolding the frontend from scratch or updating an existing one. When frontend files or pom wiring it owns already exist, it warns and asks Update (fill gaps only, recommended) / Keep as is / Replace (regenerate everything) / Stop, unless on-existing pre-answers; regenerating the sample view and test is asked as a follow-up rather than assumed.

Purpose group

Spring Boot Service Bootstrap

Plugin

Shipped by the iru-springboot plugin of the ai-catalog marketplace (install with /plugin install iru-springboot@ai-catalog; see Plugins).

Outputs

  • <web-module>/pom.xml (Maven) — vaadin-spring-boot-starter, hilla-spring-boot-starter, and optional vaadin-dev dependencies, plus the vaadin-maven-plugin execution (prepare-frontend, build-frontend).

  • boot/build.gradle.kts (Gradle, Kotlin) — the com.vaadin plugin alias, javaParameters, the BOM platform, both starters and developmentOnly vaadin-dev.

  • Root pom.xml — the <vaadin.version> property, vaadin-bom dependencyManagement import, vaadin-maven-plugin pluginManagement entry, and production profile, only when they aren’t already there (normally owned by Setup Java Spring Boot Poms). On Gradle the equivalent is the version catalog’s vaadin version, vaadin-bom library and com.vaadin plugin alias.

  • <web-module>/src/main/frontend/views/@index.tsx, views/@layout.tsx, and index.html — never anything under src/main/frontend/generated/.

  • <web-module>/vitest.config.ts (extending Vaadin’s generated Vite config), src/main/frontend/test/setup.ts, and a colocated sample test views/@index.test.tsx.

  • <web-module>/package.json test/test:watch/coverage/lint/format scripts and devDependencies (vitest, @vitest/coverage-v8, Testing Library, ESLint, Prettier and their plugins).

  • <web-module>/eslint.config.js (flat config), .prettierrc.json, .prettierignore.

  • UI contract files (Step 4b; see Building user interfaces): .ui-quality.yml at the repository root (accessibility, directions, themes); in the web module a standalone Vite component gallery (playwright/vite.config.ts, playwright/gallery/index.html and main.tsx, since Vaadin’s own Vite config needs prepare-frontend), playwright.config.ts, e2e/support/ui-screenshots.ts (copied from the skill’s reference/ui-screenshots.ts), a stories/HomeView.story.tsx story and e2e/components/HomeView.spec.ts, which captures .ui-screenshots/screen/HomeView/ across left-to-right/right-to-left × light/dark with an @axe-core/playwright check; a test:ui script and the @playwright/test/@axe-core/playwright devDependencies.

  • .gitignore additions for <web-module>/node_modules/, src/main/frontend/generated/, vite.generated.ts, the Playwright test-results/ and playwright-report/ directories and .ui-screenshots/ — shown as a diff and confirmed before writing.

  • Kotlin @BrowserCallable conventions (Step 2a) — no sample service is scaffolded.

  • Root pom sonar.sources/sonar.tests/sonar.test.inclusions/sonar.javascript.lcov.reportPaths merged in, and sonar.exclusions extended with /frontend/generated/, only when sonar.mode isn’t none. Kotlin + Maven uses src/main/kotlin roots; Gradle adds a sonar {} block to boot/build.gradle.kts instead.

  • Optional example Flow @Route Java class and component starter, only if Step 1’s Flow-views question was answered Yes.
