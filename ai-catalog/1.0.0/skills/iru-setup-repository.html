Setup Repository

This documentation was generated with the assistance of AI. Please report any inaccuracies.

The catalog’s single entry point for bootstrapping any repository. It does not scaffold anything itself — it detects or asks which of twelve supported project types applies, collects the handful of questions genuinely shared across every stack, and hands off to exactly one of five existing stack orchestrators.

Purpose

iru-setup-repository exists so a user doesn’t need to already know which of this catalog’s stack-specific orchestrators (iru-setup-java-library-repository, iru-setup-java-springboot, iru-setup-typescript-repository, iru-setup-android-repository, iru-setup-swift-repository) applies to their repository. It surveys the working directory (running iru-explore when it already holds code) to detect the project type, asks only the cross-cutting questions the detected/chosen type still needs, and delegates the actual scaffolding — the downstream orchestrator asks its own project-identity questions and does the real work. Run against a repository that already has code, it forces mode: existing on the delegated orchestrator so it takes its gap-fill/update path instead of assuming a blank slate.

Outputs

  • No files are written directly by this skill — every artifact (source scaffold, Antora docs, .gitignore, CI workflows, CHANGELOG.md, README.md) is produced by whichever single stack orchestrator Step 4 delegates to, exactly as that orchestrator’s own page describes.

  • A final report (Step 5): the resolved project-type/mode and every shared input as actually applied, what the delegated orchestrator reported creating/updating/leaving untouched, one consolidated secrets/environments table, and an explicit warning block (review every generated file; every listed secret and matching external account must already exist; which values were inferred rather than asked).

  • When the detected or chosen type is dotnet/other/unsupported: a plain report that no bootstrap orchestrator exists in this catalog for it, with no delegation attempted.

Dependencies

Invokes

  • Explore — Step 1, directly (not via a sub-agent), and only when the working directory is non-empty: reads its ## Tech stack report’s - Project type: line to pre-select Step 2’s option and set mode: existing.

  • Exactly one of the following five, via the iru-isolated-skill-executor agent in Step 4, chosen by the resolved project-type — never more than one per run outside the multiple case:

    • Setup Java Library Repository — for java-library.

    • Setup Java Spring Boot — for java-springboot / java-springboot-hilla (via its own frontend arg).

    • Setup TypeScript Repository — for typescript-library, react-web, angular-web, react-native-app, ionic-app (via its own flavor arg).

    • Setup Android Repository — for android-library, android-app (via its own flavor arg).

    • Setup Swift Repository — for swift-library, apple-app (via its own flavor arg).

Invoked by

None from inside this catalog — it is a top-level entry point invoked by a person.

Related agents

  • iru-isolated-skill-executor — spawned once in Step 4 to run the chosen stack orchestrator end-to-end in a fresh context, so that orchestrator’s own multi-step exploration/scaffolding transcript doesn’t accumulate in this front door’s context.
