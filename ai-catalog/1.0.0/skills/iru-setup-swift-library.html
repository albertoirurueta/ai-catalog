Setup Swift Library

This documentation was generated with the assistance of AI. Please report any inaccuracies.

Generate the standard Swift Package Manager library toolchain at the repository root — Package.swift, the Sources/<Name>/ and Tests/<Name>Tests/ layout, .swiftlint.yml, a formatter config, a DocC catalog page, and, when opted in, .spi.yml and sonar-project.properties.

Purpose

iru-setup-swift-library bootstraps a new Swift/SwiftPM library from an explicit, genericized house template embedded in the skill itself. Every file starts from swift package init --type library’s own scaffold, then this skill rewrites it: `Package.swift gets // swift-tools-version: 6.0, a platforms: array derived from the selected Apple platforms, a swift-docc-plugin dependency, and swiftLanguageModes: [.v6]; Sources/<Name>/ gets a placeholder Sendable type; Tests/<Name>Tests/ gets both a Swift Testing @Test example and an XCTest example; and .swiftlint.yml, a .swift-format/.swiftformat config, and a DocC catalog page round out the toolchain. It is the Swift/Apple equivalent of Setup Java Library, Setup TypeScript Library, and Setup Android Library for this catalog’s other ecosystems.

Purpose group

Swift/Apple Bootstrap

Invocation

/iru-setup-swift-library

Inputs

Argument Required Description Default

args

No

Pre-resolved parameters passed by an orchestrating skill (e.g. a future Setup Swift Repository) as newline-separated key: value lines covering every field below, parsed in Step 0 so this skill doesn’t ask about any field already resolved this way.

None — if absent or unrecognized, every field is asked interactively.

package-name

Yes (unless supplied via args)

The SwiftPM package identity written to Package(name: …​), e.g. my-example-lib; the PascalCase <Name> used for the product/target/type and every Sources//Tests//DocC directory is derived from it automatically.

None

platforms

Yes (unless supplied via args)

One or more of ios, ipados, macos, watchos, tvos, visionos, linux (multi-select). ios/ipados collapse to a single .iOS(…​) entry; linux adds no platforms: entry at all (and omits the whole key if it’s the only platform chosen).

None

min-deployment-targets

Yes (unless supplied via args)

Minimum OS version per selected Apple platform, e.g. ios=17.0, macos=14.0. Not asked for linux (no deployment-target concept in SwiftPM).

None — no sensible universal default

license

Yes (unless supplied via args)

Resolved via AskUserQuestion: Apache License 2.0, MIT License, No license, or Other (asked for a display name and URL directly).

None — user must choose

developer-name / developer-email / organization-url

Yes (unless supplied via args)

Populates the generated doc-comment license headers (Steps 6). SwiftPM has no POM/package.json-style <developers>/author metadata block, so these are used nowhere else.

None

open-source

No

Whether the repository is open source; drives the recommended defaults offered for publish and sonar.

Asked directly (yes/no) when not resolved via args

publish

No

Whether the library is distributed for other projects to depend on via a git URL/tag; gates whether .spi.yml (Swift Package Index config) is written.

yes when open-source is yes; otherwise asked with no recommended

sonar

No

Whether to wire up a SonarQube/SonarCloud scan (cloud/self-hosted/none), plus sonar-organization/sonar-project-key/sonar-host-url when not none; gates sonar-project.properties.

cloud when open-source is yes; otherwise asked with none recommended

formatter

No

Which formatter config to write: swift-format (the Swift toolchain’s own bundled formatter, verified end-to-end) or swiftformat (the third-party nicklockwood/SwiftFormat tool, unverified locally).

swift-format

mode

No

existing skips Step 1’s stop-or-regenerate question entirely and goes straight to gap-fill, leaving every file that already exists untouched. new follows Step 1’s normal survey.

new

Outputs

  • Package.swift, rewritten in full after swift package init --type library --name <Name>.

  • Sources/<Name>/<Name>.swift (a placeholder Sendable struct), Tests/<Name>Tests/<Name>Tests.swift (Swift Testing @Test), and Tests/<Name>Tests/<Name>XCTests.swift (XCTest), sharing one test target.

  • .swiftlint.yml (opt-in strict rules, excluded: .build) and either .swift-format or .swiftformat, depending on formatter.

  • Sources/<Name>/<Name>.docc/<Name>.md, a DocC catalog page.

  • .spi.yml, only when publish: yes.

  • sonar-project.properties, only when sonar is not none.

  • A report of the resolved package-name/<Name>, platforms and deployment targets, license, and every yes/no/gated choice; which files were created, left untouched (fill-gaps), or replaced (regenerate); whether swift build/swift test succeeded; and explicit warnings (review before build/commit, SONAR_TOKEN and a CI step still needed for sonar-project.properties to mean anything, .spi.yml alone doesn’t submit to the Swift Package Index, no .gitignore touched, SwiftLint/swiftformat/.spi.yml submission unverified locally).
