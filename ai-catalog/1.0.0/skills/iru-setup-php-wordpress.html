Setup PHP WordPress

This documentation was generated with the assistance of AI. Please report any inaccuracies.

Generate (or bring up to date) a WordPress plugin or block theme repository on this catalog’s PHP toolchain: a small real code skeleton plus the build, test, lint and packaging configuration, verified with its own gates before it reports success.

Purpose

iru-setup-php-wordpress treats the repository root as the plugin or theme directory. With flavor: plugin it writes the main plugin file (full header, ABSPATH guard, version constant), a namespaced PSR-4 src/ (composition root, filter service with a documented custom hook, settings page whose admin-post.php handler checks nonce and capability, REST route with a permission_callback), uninstall.php, languages/, a WordPress.org readme.txt and .distignore; blocks: yes additionally adds a blocks/ source directory built by @wordpress/scripts and a first dynamic block. With flavor: theme it writes a block theme (style.css header, theme.json v3, templates, parts, translatable patterns and a minimal functions.php). Both flavors get composer.json with the catalog’s shared scripts, phpcs.xml.dist (WordPress-Extra, WordPress-Docs, PHPCompatibilityWP), phpstan.neon.dist (phpstan-wordpress, level 6), a Brain Monkey unit suite, a WP_UnitTestCase integration suite running in a dedicated @wordpress/env environment, sample tests, Clover/JUnit output under build/logs/, browser UI tests per the catalog’s UI contract (see Building user interfaces) and sonar-project.properties when Sonar is on. The UI tests are a .ui-quality.yml, a playwright.config.ts extending wp-scripts test-playwright against the wp-env tests instance, @axe-core/playwright, the shared tests/e2e/support/ui-screenshots.ts helper, a test-only RTL mu-plugin and a sample spec (the plugin’s ContentNotice component or the theme’s Index screen) that captures .ui-screenshots/ across left-to-right/right-to-left x light/dark with an accessibility check. With accessibility: none no accessibility tooling is installed and the templates omit assistive-technology attributes; otherwise they carry them.

Dependency versions, the PHP floor and the WordPress floor/tested-up-to versions are resolved live (Packagist, npm, php.net, api.wordpress.org) with a documented fallback table; PHPUnit stays on 9.6 because the WordPress test library still targets it. For every owned file that already exists the skill warns and asks Update / Keep as is / Replace.

Outputs

  • The plugin or block theme skeleton and shared tooling files described above (created, updated, replaced, or kept as is per file).

  • .ui-quality.yml, playwright.config.ts, tests/e2e/support/ui-screenshots.ts, tests/e2e/mu-plugins/iru-ui-test-direction.php and the sample spec(s) (ContentNotice.spec.ts, plus a block spec with blocks: yes; or Index.spec.ts for a theme); screenshots land in .ui-screenshots/ as <state>--<direction>--<theme>.png.

  • A generated composer.lock/package-lock.json after installing dependencies, and (with blocks: yes) a built build/ directory.

  • Verification of the fast gates (unit tests, coverage, PHPStan, PHPCS) and, when Docker is available and the user agrees, the wp-env integration suite and browser UI tests (Chromium installed with npx playwright install chromium; unverified without a browser), run under the repository-wide .integration-test.lock/.

  • A report starting with the setup mode (created from scratch or updated) covering identity, floors and their sources, live versus fallback versions, the PHPUnit 9 decision, per-file action, gate results, and explicit warnings (review the files, WordPress.org slug approval and Contributors: for store distribution, namespace prefixing before the first runtime Composer dependency, what iru-setup-php-gitignore and iru-setup-php-github-workflows still own).

  • It never writes .gitignore, README.md, CHANGELOG.md, LICENSE, workflows or docs/.
