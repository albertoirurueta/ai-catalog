Setup Android App

This documentation was generated with the assistance of AI. Please report any inaccuracies.

Generate a complete, buildable Gradle Kotlin-DSL Android application project — wrapper, root build files, and a single app/ com.android.application module — from explicit example templates genericized line for line from a real reference repository’s Gradle toolchain.

Purpose

iru-setup-android-app bootstraps a standalone Android application’s Gradle project: the wrapper, root build.gradle.kts, settings.gradle.kts, gradle.properties, and gradle/libs.versions.toml, plus a single app/ module wired with applicationId/namespace, versionCode/versionName, build-info buildConfigField`s, an env-var-driven `signingConfigs { release {…} } block that never fails configuration when signing secrets are absent, a Compose-by-default UI (or a classic AppCompat + ViewBinding views variant), Robolectric + MockK
JUnit 4 unit-test tooling, an instrumented-test skeleton, and an optional inline sonar { properties {…} } } block. It also scaffolds UI tests per the catalog’s UI contract (see Building user interfaces): a .ui-quality.yml at the repository root, Roborazzi plus the Accessibility Test Framework on Robolectric, a shared testing/UiScreenshots.kt helper, and a sample screen test that captures .ui-screenshots/ across left-to-right/right-to-left × light/dark with the accessibility check; the sample layouts use Start/End constraints and localized string resources. It never writes a Maven Central publishing block — iru-setup-android-library is the companion skill for a library module. Every Gradle/Kotlin/plugin version is looked up at run time against the real package registries, falling back to a recorded, CI-verified combination when a lookup fails. It announces whether it is scaffolding from scratch or updating an existing Gradle project; for each file group it owns that already exists (each build file, the wrapper, the app/ skeleton, .ui-quality.yml, detekt.yml) it warns and asks Update / Keep as is / Replace (and Stop on the first question), even under mode: existing, unless on-existing decides. It never overwrites hand-edited application source.
