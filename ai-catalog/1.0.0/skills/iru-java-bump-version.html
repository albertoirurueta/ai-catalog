Java Bump Version

This documentation was generated with the assistance of AI. Please report any inaccuracies.

Set a JVM (Java or Kotlin) project’s version to an exact value across every file that needs to agree with it. For Maven, a single-module pom.xml has its own <version> rewritten in place, and a reactor (a root pom.xml declaring <modules>) runs mvn versions:set. For Gradle (Kotlin DSL or Groovy), it finds every literal project version declaration and rewrites them all. This skill never computes a version itself — it only applies the exact value it is given, validated for shape, and optionally syncs README/Antora mentions to match.

Purpose

iru-java-bump-version is the JVM-ecosystem leaf that a caller — typically iru-release — delegates the actual version-file edit to, instead of hand-editing build files or duplicating reactor-vs-single-module logic in every skill that needs to change a project’s version. It mirrors the contract iru-typescript-bump-version, iru-android-bump-version, and iru-swift-bump-version define for their own ecosystems, documenting this catalog’s X.Y.Z / X.Y.Z-SNAPSHOT pre-release convention so a caller has one place to read the release/next-dev computation from.

The Gradle path covers Kotlin Spring Boot and Quarkus services and plain JVM libraries. It scans version= in any gradle.properties, version = "…​" in any module’s build.gradle(.kts), and the gradle.properties key or gradle/libs.versions.toml [versions] entry a build script reads its version from. It refuses to write when modules disagree until the user confirms. Android Gradle projects are out of scope and are redirected to iru-android-bump-version.

When the Kotlin Multiplatform plugin is applied anywhere in the build, the skill stops and points to KMP Bump Version instead.

Purpose group

Java Development Tooling

Argument Required Description Default

Yes

Positional. The literal target version string (e.g. 1.4.0 or 1.4.1-SNAPSHOT) to write. This skill applies it verbatim — it does not compute bumps itself.

None — asked for if missing.

sync-files

No

args key. yes|no — whether to also update README/Antora version mentions (Step 7).

next-version

No

args key. The upcoming pre-release version (e.g. 1.5.0-SNAPSHOT) that README/Antora "Latest snapshot"/ "Current development version" markers should show after a release, while "Latest release" markers show <new-version>. iru-release passes it alongside the release version.

Unset — development markers are then only rewritten when <new-version> is itself a -SNAPSHOT value.

dry-run

No

args key. yes|no — print the diff / the command that would run, then stop, instead of writing or running anything.

no

Outputs

  • Maven: pom.xml rewritten in place — the root artifact’s own <version> (single module) or every module’s version via mvn versions:set -DgenerateBackupPoms=false (reactor).

  • Gradle: every literal project-version location rewritten (gradle.properties, build.gradle(.kts), gradle/libs.versions.toml [versions]), and nothing else (dependency/plugin versions are untouched).

  • Optionally, when sync-files is accepted: dependency snippets and "Latest release"/"Latest snapshot" markers in README.md, the version: field in docs/antora.yml (only for a released, non--SNAPSHOT value), and Antora pages showing literal dependency snippets.

  • A report of the build tool, the old and new version, reactor vs single module (or Gradle locations found), every file touched, and the Step 6 sanity-check result.

  • With dry-run: yes, nothing is written and no mutating command is run — only the diff/command is shown.

Dependencies

Invokes

None — iru-java-bump-version is a leaf skill; it only runs Maven (mvn versions:set, mvn help:evaluate), Gradle (./gradlew properties) and Python/regex file rewrites, and reports on the outcome. It does not call any other skill in this catalog (it only points the user at iru-android-bump-version for Android projects).

It also points Kotlin Multiplatform projects at KMP Bump Version but does not invoke it.

Invoked by
