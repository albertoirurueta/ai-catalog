Go Code One Task Group

This documentation was generated with the assistance of AI. Please report any inaccuracies.

Implement one bucket of Go tasks from a plan’s task group end to end: capture a single pre-change quality baseline, run iru-go-code-one-task once per task (in parallel when the group allows it), then validate the entire bucket once — license headers, doc comments, scoped tests, an 80% statement-coverage gate per changed file, a full-suite run with the race detector, a code-quality regression check, for a bucket that added or changed Bubble Tea screens/components a terminal-UI stage (captures and accessibility), and, only when the repository has integration-tagged tests, a container-backed stage serialized behind a repository-wide lock.

Purpose

iru-go-code-one-task-group is the Go counterpart to iru-rust-code-one-task-group and iru-fastapi-code-one-task-group, built on iru-go-code-quality, iru-go-test, iru-go-coverage, and iru-go-godoc. It works in any Go module — an agent-friendly Cobra / Bubble Tea v2 command-line tool scaffolded by iru-setup-go-cli, or any other library, service or CLI. It detects the shape once (module path and go directive, go.work workspace, cmd/<bin>/ plus internal/ layout, CLI framework, testscript .txtar end-to-end tests, teatest, integration-tagged tests, golangci-lint v2 config, cgo availability for -race), captures one baseline for every file the bucket is expected to touch, then implements each task via iru-go-code-one-task — concurrently when the plan marks the group Parallelizable: yes, one at a time otherwise. Tasks sharing root.go, the exit-code/envelope files, go.mod/go.sum, or a golden file are always run sequentially, whatever the verdict.

iru-go-code-one-task checks off each task’s box in implementation_plan.md itself with a "group validation pending" note; this skill re-reads the file as each agent reports back, backfills any box that didn’t land, and later replaces each note with the final outcome. Validation runs cheapest first, every check through an iru-gate-runner agent so no raw report reaches this context. Coverage is measured per changed file from one whole-module run with -coverpkg=./…​, so in-process Cobra tests and testscript re-executions both count; branch coverage is reported as not available in Go. The full suite runs with -race when cgo is available. Only container-backed tests take the shared .integration-test.lock; plain CLI end-to-end tests need no lock, and Docker being unavailable makes that stage "unverified", never silently skipped. When the bucket touched the terminal UI, Step 1 also records the TUI package, the capture helper and the .ui-quality.yml settings (a missing file means accessibility: enforce, directions: [ltr, rtl], themes: [light, dark]), the full-suite run is asked for the UI-capture summary (ui: yes), and Step 3.5a checks that every added/changed screen and component has .txt captures in .ui-screenshots/ for each of its states × directions × themes, with the accessibility level applied (enforce violations fail the bucket, report lists them, off is stated, and none skips the accessibility rules and checks and reports "accessibility: opted out"). Terminal UIs have no automated accessibility audit, so the asserted TUI checks are reported as such, and this stage is never "unverified" for environment reasons. See Building user interfaces. When .ui-quality.yml is missing in a repository that already has UI code, it doesn’t assume enforce: before the first UI task it asks once, pre-selected from iru-explore’s `Accessibility: line, and writes the file.

A failure traced to a task sends that task back for a fix and a re-run of the affected checks. A medium model is used on purpose: the plan carries the hard reasoning.

Purpose group

Go Development Tooling

Plugin

Shipped by the iru-go plugin of the ai-catalog marketplace (install with /plugin install iru-go@ai-catalog; see Plugins).

Invocation

/iru-go-code-one-task-group <bucket text>

Inputs

Argument Required Description Default

Bucket text

Yes

Every Go-tagged task/sub-task in the bucket, each with its own text, plus the group’s Parallelizable verdict and any relevant "Current code state" context.

None — this skill is always invoked with a specific bucket’s text, by iru-code-one-task-group.

Outputs

  • Source, test, .txtar script and golden files created/modified per task, via iru-go-code-one-task.

  • License headers and doc comments kept current across every file/package the bucket touched, checked once for the whole bucket rather than once per task.

  • For a bucket that touched the terminal UI: .txt captures under .ui-screenshots/ for every added/changed screen and component (states × .ui-quality.yml directions × themes, plus no-color), produced by the full-suite run; gaps are fixed through the owning task.

  • Tests achieving at least 80% statement coverage for each changed/added production file (container-free tests only).

  • A transient .integration-test.lock/ directory (with an owner file) held only while the container-backed stage runs, added to the repository’s root .gitignore if missing, and always released before this skill finishes.

  • implementation_plan.md with each task’s (and sub-task’s) checkbox checked and a progress note — first an "implemented, group validation pending" note written by iru-go-code-one-task, then replaced with the final coverage, race, quality, UI and integration outcome.

  • User-facing notifications at both phases: per task as its implementation lands, and once when group validation completes.

  • A summary handed back to the caller (iru-code-one-task-group): the shape detected, per task the files, tests, per-file coverage and quality outcome, the UI stage result (captures per state/direction/theme, malformed names, accessibility level and rule-id counts, or "no UI changes"), interface changes (commands, flags, exit codes, JSON fields), go.mod changes, test and race results, the container-backed result (passed, unverified with reason, or none), accepted coverage exceptions, refreshed golden files, lock behavior, and any blocked task.

Dependencies

Invokes

  • Go Code One Task — Step 2, once per task in the bucket, via the iru-isolated-skill-executor agent when the bucket is parallelizable (all tasks at once) or directly, one at a time, otherwise — that skill implements exactly what the task specifies, writes/updates its tests, formats and compile-checks, and checks off its own checkbox in implementation_plan.md with a "group validation pending" note before reporting back.

Each of the following is invoked via the iru-gate-runner agent rather than directly, so verbose report output stays out of this skill’s own context:

  • Go Code Quality — Step 1 (pre-change baseline for the bucket) and Step 3.6 (final regression check against that baseline).

  • Check License — Step 3.1, license headers for every .go file the bucket touched.

  • Go Godoc — Step 3.2, doc comments for every package the bucket touched.

  • Go Test — Step 3.3 (scoped tests), Step 3.5 (full suite with -race, and ui: yes when the bucket touched the terminal UI so the run clears and refills .ui-screenshots/), and Step 3.7 (container-backed stage with tags: integration and lock: held).

  • Go Coverage — Step 3.4, statement coverage with -coverpkg=./…​ for every changed/added production file.

Invoked by

  • Code One Task Group — Step 2, bucket for key go.

Related agents

  • iru-isolated-skill-executor — spawned once per task in the bucket (Step 2) when the group is parallelizable, so each task’s own implementation transcript doesn’t accumulate in this skill’s context.

  • iru-gate-runner — spawned for the baseline capture (Step 1) and every validation check (Step 3), keeping full reports out of this skill’s context.
