Setup Swift Repository

This documentation was generated with the assistance of AI. Please report any inaccuracies.

End-to-end bootstrap for a Swift repository of either flavor — a SwiftPM library or a native Apple app. It collects the project’s identity and pipeline parameters once, resolves which flavor and branching model apply, and orchestrates six other skills in a fixed order so nothing is asked twice.

Purpose

iru-setup-swift-repository is the top-level entry point (standalone, or as the Swift/Apple branch of iru-setup-repository) for starting or catching up a Swift repository, whichever of its two flavors it is: a redistributable SwiftPM library, or a native iOS/iPadOS/macOS/watchOS/visionOS app generated from an XcodeGen or Tuist manifest, with SwiftUI or programmatic UIKit for its iOS/iPadOS target and an MVVM or MVC core (a macOS-only app is pointed to Setup macOS Repository instead). Rather than duplicating the flavor’s own scaffold logic, documentation scaffolding, .gitignore setup, CI/CD workflows, changelog bootstrapping, and README generation, it gathers the shared inputs — project identity (package name or app name/bundle-id prefix, license, developer name/email/organization URL), flavor-specific inputs (platforms, minimum deployment targets, generator, signing, and for an app ui/architecture), and pipeline parameters (branching model, integration/stable branch, macOS runner, open-source/visibility/publish/distribution/sonar, and the cost-aware CI choices ci, ci-tests and pages) — once, and passes each downstream skill only the args keys its own Step 0 accepts. It announces up front whether it is setting the repository up from scratch or updating an existing one (with an absent/present/partial inventory of every component it owns). It never skips the scaffold itself: every sub-skill warns about and asks Update / Keep as is / Replace for each pre-existing file it owns (or applies on-existing from args in scripted runs), and the final report states per component whether it was created, updated, replaced, kept as is, or skipped (ci: no). Because macOS runner minutes cost roughly 10x Linux minutes on private repositories, the CI questions are asked with visibility-aware cost guidance.

Purpose group

Swift/Apple Bootstrap

Outputs

  • A "Setup mode" announcement (from scratch vs. updating, with a component inventory) before any question.

  • The flavor’s own scaffold: Package.swift + Sources//Tests/ (via iru-setup-swift-library), or the generator manifest + Packages/Core + Targets/ + fastlane/Fastfile (via iru-setup-apple-app) — always invoked; the scaffold skill decides per existing file whether to update, keep or replace it.

  • A root CHANGELOG.md backfilled from git tag/GitHub Release history (via iru-setup-changelog).

  • A root README.md with badges, a project-status table, documentation links, and installation instructions (via iru-setup-readme).

  • A final report summarizing the resolved flavor/branching/mode, identity/license/pipeline parameters (visibility, ci, ci-tests, pages included), a per-component table of whether each was created, updated, replaced, kept as is (with any listed mismatches) or skipped (ci: no), the Sonar coverage conversion (lcov_to_sonar_generic.py for both flavors), the consolidated required-secrets/settings table (including APPLE_TEAM_ID for a distributed app), every decision made on the user’s behalf, and explicit warnings to review every generated file before building, committing, or relying on CI.

Dependencies

Invokes

Each of the following is invoked via the iru-isolated-skill-executor agent rather than a direct Skill call — every sub-skill re-derives what it needs straight from the filesystem this orchestrator has just written to, so only a short completion summary needs to come back, keeping each sub-skill’s own exploration/file reads (and the two scaffold skills' very long template listings) out of this orchestrator’s own context. Every sub-agent runs with run_in_background: false since each step depends on the previous one’s files being on disk:

  • Setup Swift Library — Step 5, flavor: library: writes Package.swift and the source folders, passing Steps 2–4’s answers (package-name, platforms, min-deployment-targets, license, developer fields, open-source, publish, sonar + detail keys, formatter if supplied, visibility, ci, on-existing if supplied, mode) as args. Always invoked, even when Package.swift already exists.

  • Setup Apple App — Step 5, flavor: app: writes the generator manifest, Packages/Core, per-platform Targets/, and an optional signing/distribution-gated fastlane/Fastfile, passing the app-specific identity (app-name, bundle-id-prefix), platforms, generator, ui, architecture, distribution, signing, min-deployment-target if supplied, license, developer fields, open-source, sonar + detail keys, visibility, ci, on-existing if supplied, and mode as args. Always invoked, even when the generator manifest already exists.

  • Setup Antora — Step 6: scaffolds the Antora documentation site, invoked with no args (only on-existing when supplied) since it derives the component name/title/version directly from the manifest Step 5 just wrote (or an initial 1.0.0 if no tags/releases exist yet). Run before Step 8 so that skill’s own docs-site check finds everything in place.

  • Setup Swift Gitignore — Step 7: writes or updates the root .gitignore, passing flavor (so its Package.resolved recommendation matches the project shape) and package-resolved only if supplied, plus on-existing if supplied; mode is deliberately not passed since the skill’s own .gitignore-presence check is the more precise signal.

  • Setup Swift GitHub Workflows — Step 8, skipped entirely when ci: no: writes the CI/CD + security workflows, passing flavor, platforms, branching, integration-branch (gitflow only), stable-branch, runner, xcode-version if supplied, generator/signing (app only), release-please if supplied (library only), open-source, publish/distribution, sonar + detail keys, visibility, ci-tests, pages, security-* if supplied, on-existing if supplied, and mode as args.

  • Setup Changelog — Step 9: bootstraps the root CHANGELOG.md, invoked with no args (only on-existing when supplied) since it works from the repository’s own git tag/GitHub Release history; position relative to Steps 5–8 doesn’t matter functionally.

  • Setup Readme — Step 10, last: bootstraps the root README.md, passing sonar, ci, pages (only when ci: yes) and on-existing if supplied, and otherwise exploring the finished state left by every earlier step.

Invoked by

  • Setup Repository — Step 4, Swift library/Apple app bootstrap, via the iru-isolated-skill-executor agent; it asks its own visionOS follow-up and passes platforms in args, which this skill then doesn’t re-ask for an app.

Related agents

  • iru-isolated-skill-executor — spawned once per sub-skill (Steps 5–10), so all six sub-skills' own exploration/file-read transcripts don’t accumulate in this orchestrator’s context over the course of a single bootstrap run.
