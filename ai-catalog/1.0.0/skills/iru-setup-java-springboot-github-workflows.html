Setup Java Spring Boot GitHub Workflows

This documentation was generated with the assistance of AI. Please report any inaccuracies.

Creates the GitHub Actions workflows a Spring Boot service needs: one that builds, tests, analyses, and publishes documentation (optionally running a Hilla frontend’s tests too); one that deploys; one that stops or destroys an environment; and one that runs dependency/code/secret security scans, plus a Dependabot config.

Purpose

iru-setup-java-springboot-github-workflows is the service-shaped counterpart to Setup Java GitHub Workflows. A service is not published to Maven Central and is not GPG-signed — it is built into a container image and deployed — so the publish, sign, and version-sync stages are replaced by image build, OpenTofu apply, and teardown. The shared stages (test, analyse, Sonar, Antora, GitHub Pages) follow the same house pattern, so the two remain recognisably related.

The skill announces whether it is creating the workflows from scratch or updating existing ones, and asks per existing file whether to Update, Keep as is, Replace, or Stop (or applies on-existing). It also resolves visibility-aware CI choices: visibility, sonar, ci-tests (unit runs Surefire only with -DskipITs; full also runs Failsafe against Testcontainers) and pages (no uploads the built docs as a workflow artifact instead of publishing to GitHub Pages). For private or internal repositories it states the Actions-minutes cost (2,000/month on Free, 3,000 on Pro and Team, 50,000 on Enterprise Cloud; Linux 2-core $0.006/min) and that GitHub Pages needs Pro, Team or Enterprise Cloud and is public on the internet unless Enterprise Cloud access control is used.

The build.yml Sonar step is no longer offered reactively: it reads the manifest’s sonar.mode (cloud/self-hosted/none, defaulting to cloud for a manifest written before the field existed) as the source of truth and drops the step entirely — rather than disabling it with a permanently-false condition — when sonar.mode: none. When the manifest’s frontend field is hilla, build.yml also sets up Node, runs the frontend’s Vitest suite with coverage (after the Maven build, since the frontend’s generated config imports compiled helpers that only exist once Maven has reached vaadin:prepare-frontend), and packages with -Pproduction -Dvaadin.ci.build=true.

Workflow Trigger Does

build.yml

Push to the integration/main branch, and every pull request

Build, unit tests (Surefire), Testcontainers integration tests (Failsafe, only when ci.tests: full), static analysis, aggregated coverage, Sonar (when sonar.mode isn’t none), frontend Vitest tests and coverage (when frontend: hilla), and — on the main branch only — the Antora site plus the generated OpenAPI, protobuf, GraphQL and AsyncAPI HTML, published to GitHub Pages when ci.pages: yes, otherwise uploaded as a documentation workflow artifact

deploy.yml

workflow_dispatch with an environment input, optionally on release published

Build and push the container image, authenticate via keyless OIDC, tofu plan then apply that plan file, then a smoke check that fails the deploy if the service never becomes healthy

undeploy.yml

workflow_dispatch only

Scale to zero (the reversible default) or destroy an environment, behind a typed-confirmation check and a protected GitHub Environment

security.yml

Push to the main branch, every pull request, and a weekly schedule

Dependency review, CodeQL (with a javascript-typescript matrix leg when frontend: hilla), OSV-Scanner, and gitleaks — each job individually omittable via its own args flag

.github/dependabot.yml

n/a — configuration, not a workflow

Grouped weekly updates for the maven (or gradle), docker, and github-actions ecosystems, plus npm (pointed at the real web module) when the manifest’s frontend isn’t none; always generated regardless of the security-* flags

No credential is ever written into a workflow file: cloud access is keyless via OIDC, and everything else is a repository or environment secret referenced by name. Where the registry supports it, even the registry credential is derived from the OIDC session (amazon-ecr-login, gcloud auth configure-docker) rather than stored.

The guards on undeploy.yml are the feature rather than ceremony: stop is the default and is reversible, data-bearing resources are expected to carry deletion protection so destroy fails on them rather than silently deleting a production database, and the skill recommends restricting prod to required reviewers plus a deployment branch rule — and considering omitting prod from the destroy path entirely.

Language and build tool

project.language (java/kotlin, absent means java) and project.buildTool (maven/gradle, absent means maven; Gradle only ever appears with Kotlin) select one of three variants, confirmed against the disk (pom.xml, settings.gradle.kts plus gradlew, src/main/kotlin) — if the manifest and the disk disagree, the disk wins for the run and the report says so.

Variant What changes

java + maven

The base templates, unchanged.

kotlin + maven

Static analysis is detekt plus ktlint instead of Checkstyle/PMD/SpotBugs, and code documentation is Dokka instead of Javadoc; every mvn build, test, Sonar and image command is unchanged.

kotlin + gradle

Every job uses gradle/actions/setup-gradle (open-source basic cache provider) and ./gradlew, never a runner-installed gradle: test/integrationTest, :coverage:testCodeCoverageReport, detekt ktlintCheck, dokkaGeneratePublicationHtml, and the image built with bootBuildImage tagged from the gradle.properties version (<version>-<short sha>). No Maven site is published (the test and coverage reports travel in the test-reports artifact), security.yml gains a dependency-submission job feeding the graph dependency review compares, CodeQL compiles manually with ./gradlew instead of autobuild, and Dependabot uses the gradle ecosystem. The Hilla steps use -Pvaadin.productionMode=true -Pvaadin.ci.build=true.

Outputs

  • .github/workflows/build.yml — a build job (checkout with full history for Sonar blame, JDK with Maven cache, mvn clean verify — or mvn clean verify -DskipITs with ci.tests: unit — the site report, the Sonar scan skipped on fork pull requests, and test reports uploaded even on failure) plus a docs job gated to main-branch pushes (renamed Build documentation and ending in an artifact upload rather than a gh-pages deploy when ci.pages: no, in which case it also drops contents: write and the .nojekyll touch). The docs job generates the Maven site and the OpenAPI/protobuf documentation, then runs the two npm-driven generators as their own steps against the toolchains committed in apis/messaging/docs and apis/graphql-server/docs — validating and rendering the AsyncAPI specification, and rendering the GraphQL SDL through SpectaQL and (optionally) Voyager. It then builds the Antora site and merges everything: a "Merge documentation" step copies the contents of every target/generated-docs directory in the reactor under doc/api/, so rest-server/, grpc-server/, graphql-server/ and messaging/ land side by side without the workflow needing to know which module produced which. The published result includes doc/api/messaging/v1/index.html and doc/api/graphql-server/v1/index.html with the Voyager graph beneath it. Both npm generators are skipped in Maven (-Dasyncapi.docs.skip=true -Dgraphql.docs.skip=true) in this job so the work isn’t done twice — the build job’s mvn clean verify still exercises the frontend-maven-plugin wiring — and each step is guarded by hashFiles(…​), so deleting a contract directory doesn’t require a workflow edit. Their loops over -async-api-v.yaml and -v.graphqls mean a new contract version needs no workflow change either.

    One detail the merge step protects by accident and would break if simplified: Voyager's page loads
`voyager.standalone.js` and `voyager.css` by relative path, so those files must travel with `index.html`. Copying
whole directories preserves that; copying only `index.html` files would publish a blank graph.

Execution flow

flowchart TD A["Start /iru-setup-java-springboot-github-workflows"] --> B["Step 0: Read the manifest; survey the reactor,\nSonar config, Antora setup, infra/envs,\nGitHub Environments, compose stack weight"] B --> BL["Resolve language and build tool:\njava+maven, kotlin+maven or kotlin+gradle\n(the disk wins over the manifest)"] BL --> B2["Resolve CI choices (visibility, sonar,\nci-tests, pages); announce scratch vs update"] B2 -- compose stack too heavy and ci-tests full --> C["Flag now; offer a larger runner\nor a per-module IT matrix"] B2 -- a workflow file already exists --> D{"Per file: Update /\nKeep as is / Replace / Stop?\n(or on-existing)"} D -- stop --> STOP[Stop without changing any file] D -- update, keep or replace --> E B2 --> E["Step 1: Write build.yml\n(unit vs full tests, Pages vs artifact)\n(build job + main-branch-only docs job:\nMaven site, OpenAPI/protobuf docs, AsyncAPI\nand GraphQL html, Antora, merge into ./doc)"] C --> E E --> F["Step 2: Write deploy.yml\n(OIDC, image build, plan then apply, smoke check)"] F --> G["Step 3: Write undeploy.yml\n(typed confirmation, stop vs destroy)"] G --> G2["Step 3b: Write security.yml\n(dependency-review, CodeQL, OSV-Scanner,\ngitleaks - each gated by a security-* flag)\nand always write dependabot.yml"] G2 --> H["Step 4: Assemble the secrets,\nvariables, and environments table"] H --> I["Step 5: Validate — YAML parses, actionlint,\naction versions current, secret names consistent;\nMaven or Gradle commands verified locally via iru-gate-runner"] I --> J["Step 6: Report files, gaps,\nand review warnings"]

deploy.yml and undeploy.yml are deliberately never triggered as a test. The skill instead recommends a dry run of build.yml on a throwaway branch, and a first deploy.yml run against dev only, watched to completion.

Dependencies

Invokes

  • Setup Java Spring Boot Poms — Step 0 (conditional), only offered when the survey finds the pom’s (or Gradle build’s) Sonar wiring missing although sonar.mode isn’t none; the skill reports the drift and offers to re-run it rather than generating a Sonar step that is certain to fail.

Otherwise it reads springboot-stack.yml and surveys the repository, then writes workflow YAML.

Invoked by

  • Setup Java Spring Boot — Step 8, build/deploy/undeploy/security workflows, skipped when ci is no, via the iru-isolated-skill-executor agent.

Also runs standalone (/iru-setup-java-springboot-github-workflows).

Related agents

  • iru-gate-runner — spawned in Step 5 to run the workflow’s Maven (or Gradle) commands locally first, on the principle that a workflow whose commands were never run locally is a guess.
