Setup Java Library Repository

This documentation was generated with the assistance of AI. Please report any inaccuracies.

End-to-end bootstrap for a Java/Maven library repository, new or existing. It collects the project’s identity, pipeline parameters, and open-source/publish/Sonar choices once, then orchestrates six other skills in a fixed order so nothing is asked twice.

Purpose

iru-setup-java-library-repository is the stack orchestrator for starting (or catching up) a Java/Maven library repository — runnable standalone or delegated to by Setup Repository. Rather than duplicating the logic of pom.xml generation, documentation scaffolding, .gitignore setup, CI/CD and security workflows, changelog bootstrapping, and README generation, it gathers the shared inputs — project identity (groupId, artifactId, base package, developer name/email/organizationUrl, license), pipeline parameters (integration branch, Java version, publishing server id, sign/extras profile ids, Maven settings file), and whether the project is open source, publishes to Maven Central, and runs SonarCloud, self-hosted SonarQube, or no Sonar analysis — once, and passes each downstream skill only what it needs.

A new Step 0 first parses an optional args block (mode, open-source, publish, sonar plus its sonar-organization/sonar-project-key/sonar-host-url detail keys) so a caller like Setup Repository can pre-resolve these and skip the matching questions. In mode: existing it skips regenerating an already-present pom.xml and tells every downstream step to take its own update/gap-fill path instead of assuming a brand-new repository.

Purpose group

Repository Bootstrap

Invocation

/iru-setup-java-library-repository

Optionally with an args block (key: value lines) to pre-resolve mode, open-source, publish, sonar (plus its detail keys) and skip the matching questions — this is how Setup Repository drives it.

Outputs

  • pom.xml and the src/main/java/src/main/resources/src/test/java source folders for the base package (via iru-setup-java-library) — skipped when mode: existing and pom.xml already exists, leaving it untouched.

  • A scaffolded Antora documentation site under docs/ (via iru-setup-antora).

  • A root .gitignore covering the build tool, IDE files, and the Antora build output (via iru-setup-java-gitignore).

  • develop.yml/main.yml/sync.yml/security.yml GitHub Actions workflows, .github/dependabot.yml, and the .github/scripts/sync_versions.py script (via iru-setup-java-github-workflows), with the Maven Central publish step and the SonarCloud/self-hosted SonarQube scan step present or absent according to publish/sonar.

  • A root CHANGELOG.md backfilled from git/GitHub release history (via iru-setup-changelog).

  • A root README.md with badges, a project-status table, documentation links, and installation instructions (via iru-setup-readme).

  • A final report summarizing the resolved identity/license/pipeline parameters, the resolved mode, which files were created, updated, or left untouched (because a downstream skill’s own approval step chose to stop, or a mode: existing skip in Step 3), the required GitHub secrets, and an explicit disclosure of the open-source/publish/sonar wiring decisions (what was included in pom.xml and the workflows, and why anything was omitted). Ends with a warning to review every generated file before building, committing, or relying on CI.

Dependencies

Invokes

Each of the following is invoked via the iru-isolated-skill-executor agent rather than a direct Skill call — every sub-skill re-derives what it needs straight from the filesystem this orchestrator has just written to, so only a short completion summary needs to come back, keeping each sub-skill’s own exploration/file reads out of this orchestrator’s own context:

  • Setup Java Library — Step 3, first: writes pom.xml and the source folders, passing Step 1’s answers (groupId, artifactId, package, developer name/email/organizationUrl, license) plus Step 2’s Java version and open-source/publish/sonar (+ detail keys) as args key: value lines so iru-setup-java-library doesn’t ask for them again — and so the pom.xml compiler level and publish/Sonar wiring matches the workflows Step 6 generates. Skipped entirely when mode: existing and pom.xml already exists.

  • Setup Antora — Step 4: scaffolds the Antora documentation site, invoked with no args since it derives the component name/title/version directly from the pom.xml Step 3 just wrote.

  • Setup Java Gitignore — Step 5: writes or updates the root .gitignore, invoked with no args since it explores the repository directly (including what Steps 3–4 just wrote).

  • Setup Java GitHub Workflows — Step 6: writes the CI/CD and security workflows (develop.yml/main.yml/sync.yml/security.yml/.github/dependabot.yml), passing Step 2’s pipeline parameters (integration branch, Java version, publishing server id, extras/sign profile ids, settings file, open-source/publish/sonar + detail keys) plus Step 1’s already-collected groupId/artifactId as args key: value lines, so that skill’s own survey doesn’t need to re-read them from pom.xml and stays in agreement with what Step 3 wrote there.

  • Setup Changelog — Step 7: bootstraps the root CHANGELOG.md, invoked with no args since it works from the repository’s own git tag/GitHub Release history.

  • Setup Readme — Step 8, last: bootstraps the root README.md, invoked with no args since it explores the finished state left by every earlier step.

Invoked by

  • Setup Repository — Step 4, via the iru-isolated-skill-executor agent, when the detected or chosen project type is java-library.

Related agents

  • iru-isolated-skill-executor — spawned once per sub-skill (Steps 3–8), so all six sub-skills' own exploration/file-read transcripts don’t accumulate in this orchestrator’s context over the course of a single bootstrap run.
