# Implementation plan — Blue/green rolling deployments in the generated GitHub workflows

## Task summary

Source: GitHub issue #15
Base branch: main

Issue #15 ("Support blue/green rolling deployments") has an empty body; the scope below comes from the invocation text
and the decisions the user confirmed interactively. Today the only skill that generates a deployment pipeline is
`iru-setup-java-springboot-github-workflows` (`deploy.yml`: one job, OIDC → image build → `tofu plan/apply` → health
check; `undeploy.yml`), backed by the OpenTofu skill `iru-setup-java-springboot-platform` (ECS Fargate / EKS on AWS,
Cloud Run / GKE Autopilot on Google Cloud) and the orchestrator `iru-setup-java-springboot` (`springboot-stack.yml`).
The other `*-github-workflows` skills build/release only and are out of scope.

Confirmed decisions (from the user):

- **Opt-in at repository setup.** Setup asks whether rolling deployments are supported. Once enabled, *every*
  deployment is a staged rollout: new version ("green") is deployed at **0 % traffic**, shifted in steps, the old
  version ("blue") is kept for rollback. Default stays today's single-job deploy (byte-for-byte unchanged).
- **Strategy:** `deployment-strategy: rolling | blue-green | canary | linear`.
- **Advancement:** `advance: auto | manual | hybrid` (hybrid recommended — metric gate passes, then a human confirms
  on `prod`; a failing gate rolls back automatically).
- **Manual "this step is safe" signal:** a separate **`promote.yml`** (`workflow_dispatch`, inputs: environment and
  target percentage or `rollback`). Works on any GitHub plan (GitHub Environment required-reviewers on private repos
  need Enterprise, so they are *not* the mechanism). No runner is held open between steps.
- **Runtimes:** ECS Fargate, Cloud Run, EKS / GKE Autopilot.
- **Switchable later:** a new skill enables/disables rolling deployments in an existing repository.

Decisions made on the user's behalf (challenge in review):

- **Rollout state lives in the cloud, not in GitHub.** `promote.yml` reads the current split from the platform (ALB
  listener weights / Cloud Run traffic / Argo `Rollout` status), so it is stateless and idempotent.
- **Metric sources follow the runtime:** ECS → CloudWatch alarms (names exported by OpenTofu); Cloud Run → Cloud
  Monitoring MQL/PromQL query evaluated in the workflow; EKS/GKE → Argo Rollouts `AnalysisTemplate` on Prometheus
  (Flagger documented as the alternative, not generated).
- **Uniform shifting model:** to make `promote.yml` identical in shape across runtimes the workflow drives the
  shifting (ECS: weighted target groups on the ALB listener; Cloud Run: `--no-traffic` + tag + `update-traffic`;
  Kubernetes: Argo Rollouts `promote`). ECS's native blue/green/canary/linear strategies (with lifecycle hooks and
  alarm rollback) are the documented alternative for `advance: auto` only; the implementer must verify against the
  current AWS docs in a throwaway directory before choosing, and record the outcome in the skill.
- `rolling` (in-place instance replacement) has no second environment and no traffic split: it maps to the runtime's
  native rolling update with `advance` limited to `auto` (health-check gated) and a documented weaker rollback.
- Only the Spring Boot stack is affected; Quarkus/Python/etc. do not deploy today and are not changed.

### Shared contract (all groups must agree on this)

`springboot-stack.yml` (new optional block, absent ⇒ disabled, today's behaviour):

```yaml
deploy:
  rolling:
    enabled: true                 # false/absent ⇒ single-job deploy.yml, no promote.yml
    strategy: canary              # rolling | blue-green | canary | linear
    advance: hybrid               # auto | manual | hybrid
    steps: [10, 50, 100]          # canary/linear shift percentages; blue-green = [100]; omitted for rolling
    bakeMinutes: 10               # soak between steps for auto/hybrid gates
```

Sub-skill `args` (workflows, platform, toggle skill): `rolling: yes|no`, `deployment-strategy:`, `advance:`,
`steps:` (comma list), `bake-minutes:`; the manifest is the source of truth when `stack-file` is given.

OpenTofu outputs per `infra/envs/<env>` when rolling is enabled: `service_health_url` (existing),
`rollout_candidate_url` (green test URL: ALB test listener / Cloud Run tag URL / preview Service),
`rollout_gate` (`cloudwatch` | `cloud-monitoring` | `prometheus`), `rollout_alarm_names` (ECS; list),
`rollout_target_groups` (ECS; blue/green names), `rollout_name` (Kubernetes `Rollout`).

Workflow files when rolling is enabled: `deploy.yml` (deploy green at 0 % → smoke on candidate URL → first step per
`advance`), `promote.yml` (new), `undeploy.yml` (unchanged contract, plus resets the split), `security.yml` and
`dependabot.yml` untouched.
